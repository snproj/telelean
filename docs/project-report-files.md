## packages/core

@telelean/core is the pure-TypeScript heart of telelean. The runner (Node), the extension host and the React webview all share it. tsconfig.json limits it to lib ES2023 with no DOM or Node typings, so it does no I/O: every function takes texts, parsed files or models and returns data. It holds no LLM code: the gate rules here are the non-LLM judge of Claude's work. Other packages do not use dist/; their tsconfig/vite/vitest configs alias `@telelean/core` to src/index.ts. The only runtime dependency, zod, is used solely by export/schema.ts. index.ts deliberately does not re-export that file, which keeps the webview bundle free of zod. The package has 48 vitest files under test/; this survey does not cover them.

Module groups:
- Contracts (marked FROZEN, additive changes only): model.ts (TlNode/TlEdge/TlGraph, D-15 derived statuses, vocabulary, Lean-check state); facts.ts (the LeanFacts the runner's sandboxed `lake build` plus check file produce); actions.ts (BoardAction -> EditPlan -> FileChange, ActionError, history/undo types); run.ts (M2 run, proposal and sidecar record types); protocol.ts (versioned host<->webview messages with hand-written validators); paths.ts and layout.ts (folder and sidecar conventions).
- markup/: a lexer faithful to Lean 4.35, a declaration-header scanner, and the `@@ telelean v1` block parser. The parser reports TL0xx diagnostics and binds blocks (a pinned `lean:` beats adjacency). The group also has the serializer, byte-preserving field/block edits, and LeanOps (D-11 rewrites, D-9 docstring mirror).
- project/: buildProjectModel merges parsed files, file hashes and LeanFacts (FactsIndex: fresh, stale-by-name, unchecked) into a ProjectModel. That covers ids, bindings, declaration ownership, D-3 vocabulary classification, statement closures, proof statuses with footprints, status flags, TL1xx diagnostics and D-13 edges. Verified edges come from `.ilean` references, not from footprints. subjectGraph cuts out one subject's TlGraph and adds foreign vocabulary and the M2 externalUsers.
- edit/ plus kindChange.ts: planAction plans BoardActions through EditSession, which re-parses between steps, keeps other cards' bindings and yields whole-file changes plus layout/attic data. planKind applies the D-11 table using the facts (mark-broken, or a mechanical hypothesis rewrite, with confirmedDependents). kindChange.ts is the graph-only preview the webview shows during a drag.
- export/: graph.json format 1.1, plus its zod schema and the JSON Schema generated from it.
- gate/ (M2): the prototype gate's pure rules. These are the G0 token and file rules, the ghost single-term rule, the D-5 permitted set and freeze snapshot, and evaluateRules (G1 errors read from facts, G3, G5 and the stage/readiness rules over the B/A/S models). Also here: pre-gate normalisation, ghost adoption, lifecycle edits, and plain-language sentences for findings. The sandboxed build itself and G4 (the comparator) run in the runner.
- proposal/ (M2): board diff, accepted-proposal label, codecs for attempts.jsonl and decisions.json.
- samples/ and graph.ts: the frozen Spyro sample, a generated large graph, and M0 helpers that the webview still uses (slugId, createUserNode, columnOrder).

Data flow: the runner parses every model file (parseLeanFile) and builds the model with the latest facts. It publishes subjectGraph boards (attaching attempts itself) and writes toGraphJson output to .telelean/graph.json. The extension posts each board as a `graph` message, which the webview checks with parseHostToWebview. Webview messages go through parseWebviewToHost in the extension and become BoardActions. The runner plans them with planAction and applies them as FileChanges plus sidecars. In M2 the runner builds models of the user's base, the shadow and the adoption commits. At each gate it runs checkFileChanges, evaluateRules and the permitted-set code, phrases failures with attemptNotice, and builds ProposalViews with diffGraphs and the sidecar codecs.

Places where code and docs disagree:
- package.json's description still says the package holds only types, the protocol and samples.
- add-node's `preferredId` is documented as used, but nothing reads it; ids are always derived from the sentence.
- graph.json `attempts` is always []. Its comment says it is filled from M2 on, but neither core nor the runner fills it.
- The schema file is named 1.0, but the format is 1.1; the schema accepts any 1.x.
- The comments in gate/types.ts and gate/index.ts list fewer G0 tokens and ghost keywords than g0.ts checks. docs/m2-plan.md section 3.1 matches the code.
- Some declared values are never produced: the flags unselected-used, broken, depends-on-removed and signoff-stale; the vocabulary flag `new`; Role values other than node; certificates other than none.
- Nothing calls notImplemented() any more. sentenceLabel, nodesOfType and isFormalized are unused, and planKindChange/planDelete are not used outside core.

## packages/runner (lean, semantic, llm)

Scope: the package plumbing plus the runner's three foundation layers (lean/, semantic/, llm/). The other runner directories (workspace/, shadow/, gate/, run/, proposal/) build on these and are mentioned only where they connect.

Plumbing. @telelean/runner is Node-only (no vscode imports). src/index.ts re-exports eight namespaces. The extension instead imports subpaths: its tsconfig paths map @telelean/runner/* to the TypeScript sources, which esbuild bundles. scripts/walkthrough-claude.mjs bundles src/index.ts itself, and scripts/smoke-claude.mjs imports llm/index.ts directly. Nothing is ever emitted. tsconfig.json is noEmit, so `npm run build` is only a type-check of src, and the dist/ entry points named in package.json do not exist. Only zod is declared as a dependency. @modelcontextprotocol/sdk comes from the root devDependencies, and @telelean/core comes from path aliases. Tests run one file at a time with TELELEAN_NO_REAL_CLAUDE=1, the quota tripwire.

lean/ (written as the M0 spike, now production code). runLean is the single path for every Lean-family process. It wraps each run in four layers:
- a systemd user scope with a hard memory cap and no swap;
- a setpriv death signal;
- a keeper shell that keeps the cgroup readable until the runner has read it;
- bwrap with the allowlist from sandboxProfile.ts: no network, fresh /tmp, /run and $HOME, ~/.elan read-only, the project read-only except .lake/, a cleared environment, and LEAN_NUM_THREADS=4.
It fails closed: when it cannot sandbox safely, the status is could-not-start. Otherwise it reports ok, failed, oom, timeout or cancelled, with peak memory from the cgroup. An AbortSignal or cancelRun(runId) cancels a run.

The other lean/ modules:
- toolchain.ts pins leanprover/lean4:v4.35.0 and calls its binaries directly, never elan's proxies.
- leanNames.ts makes names written into generated Lean injection-safe.
- shadow.ts makes copies of a model and refuses symlinks.
- comparator.ts is gate step G4: it freezes a `theorem T.holds : T := sorry` challenge, exports it with leanexport, then runs and classifies `lake comparator`.
- footprint.ts supplies the `lean --json` and `#print axioms` parsers used elsewhere. Its own computeFootprints is now called only by tests.

semantic/ (M1 facts). refreshLeanFacts turns a model root into core's LeanFacts in this order:
1. memory guard;
2. checks for the pinned toolchain and a dependency-free manifest;
3. source hashing;
4. `lake build <library>` in place under runLean;
5. Lake log parsing and module states;
6. declarations and references from .ilean v5, with docstrings read from the source;
7. one generated check file (#check, #print, #print axioms, type_of%), with Lean's messages attributed by line number;
8. a re-hash that marks modules changed during the refresh as stale.
Lean and sandbox failures become statuses, not exceptions. runExclusive is a process-wide queue that runs one Lean job at a time; workspace/, shadow/ and gate/ all share it. spawnMemoryMax lowers a run's memory cap to what MemAvailable allows.

llm/ (the "These suffice" harness). This is a provider-agnostic slot. LlmBackend and LlmSession emit normalized LlmEvents. One AgentToolHost interface offers five tools: check_lean, freeze_statements, ask_user, propose_assumption and finish. Their zod schemas, descriptions and reply renderers live in toolSchemas.ts.

ClaudeCliBackend drives the user's own `claude` binary headless in stream-json mode:
- binary.ts finds a binary of version 2.1.295 or newer;
- env.ts strips API-key, provider and parent-session variables from the environment;
- only Read, Glob, Grep, Edit, Write and mcp__telelean__* tools are allowed;
- confinement.ts writes a PreToolUse path-guard hook (bin/telelean-path-guard.mjs) plus the CLI's own fences, and self-tests the hook before start;
- a preflight refuses anything but a claude.ai subscription login, and refuses if the guard is missing;
- toolServer.ts serves the tool host as MCP over loopback HTTP, protected by a bearer token;
- streamJson.ts normalizes the CLI's output.

FakeBackend replays scripted steps through the same guard decision, schemas and renderers; fakeScripts.ts loads its JSON scripts. StubToolHost is the M0 host, still used by the smoke script and tests; the production host lives in run/. The CLI backend passed M0's single live smoke test (CLI 2.1.314 with StubToolHost). Until turn 13 it ran only against a node test double and recorded 2.1.314 streams. On 2026-11-10 it carried four complete live sessions on Claude Code 2.1.322, all passing: the M2 walkthrough's two readings and two runs of the demo (docs/m2-live-report.md). Options those sessions did not use, such as toolServer's endTurnOnFinish (off by default), are still unverified with a real CLI.

Data flow.
- M1: workspace/ calls semantic.refreshLeanFacts on the real model root; that runs lean.runLean, and the resulting LeanFacts feed core's project model and then the board.
- M2: run/manager opens an llm session in the run's shadow. Tool calls arrive over MCP, or directly from the fake, at run/'s AgentToolHost, which drives gate/engine. The engine re-runs the semantic refresh on the shadow's build mirror and calls lean.freezeChallenge and runComparator for G4. Verdicts return to the model through the toolSchemas renderers.

## packages/runner (workspace, shadow, gate, run, proposal)

These five directories are the Node-side machinery of packages/runner behind one opted-in model root (M1) and behind M2's one-shot "These suffice" runs. None of them imports vscode. The extension (extension/src/vscode/runner.ts, host.ts, registry.ts) builds the objects, supplies a TextSource that reads open buffers first and a WorkspaceEdit-based EditApplier, sets runsDir to `<globalStorage>/runs`, and passes core's view types (TlGraph, RunView, ProposalView) on to the webview. All pure logic comes from @telelean/core, usually behind an injectable `core` test hook: block parsing, the project model, graphs, action planning, gate rules, normalisation, permitted axioms, finding wording, proposal labels, lifecycle edits and sidecar codecs. Lean runs only through lean/ (the runLean sandbox and the lake comparator) and semantic/ (refreshLeanFacts, the process-wide runExclusive queue and the memory guard). Claude is reached only through llm/ (LlmBackend, ClaudeCliBackend, tool schemas).

workspace/ (M1, extended for M2): ModelWorkspace scans and parses the model files and layout sidecars and builds subject graphs. It runs a debounced, coalesced Lean refresh: old facts are kept when a refresh fails and dropped when the board falls back to syntactic mode. It writes `.telelean/graph.json`. Every write (board actions, undo/redo, history revert, accepted proposals) goes through one queued path: base snapshots, the EditApplier with `before` checks, an in-memory undo entry, an action snapshot on private refs `refs/telelean/<rootKey>/...` (git plumbing only), re-read, refresh. initialize.ts implements "Initialize Model Here".

shadow/ (M2): each run gets `<runsDir>/<rootKey>/<runId>/` containing:
- ws/: Claude's working directory. It holds only model and project files, and a symlink, special file or dot-entry makes it fail closed.
- build/: the Lean mirror, synced from ws/ by comparing contents.
- git/: a bare repository written with fast-import. Its commits are typed: base, freeze, adopt, normalise, gate-pass, revert, rebase, accept-base, checkpoint.
- session/, frozen/, gate/ and run.json.
Seeding build/.lake from the user's own build is off by default.

gate/ (M2): the LeanCheckEngine does every Lean step of a run:
- G0 text rules, before any Lean runs.
- G1: build and facts of build/.
- core evaluateRules, comparing the current state with B (the base facts, kept in base-facts.json), the newest adopt commit and the round start.
- freeze: permitted axioms plus an exported comparator challenge.
- normalisation.
- the gate itself: it judges one committed state, with the G4 comparator only for `proved`.
- ghost checks and statement rendering, fed to Lean as scratch sources on stdin.
Results are findings or budget findings (both count against attempts), or environment outcomes (which do not count).

run/ (M2): one RunManager per root owns:
- the state machine: starting, working, waiting-for-answer, gate, review, interrupted, then accepted, discarded, cancelled or failed.
- preflight and the Claude backend factory.
- the static system prompt and the context bundle.
- the AgentToolHost: check_lean, freeze_statements, ask_user, propose_assumption, finish.
- the caps and the A2 gate loop.
- Feedback and ghost-adoption rounds, and Accept.
- persistence (run.json, transcript.jsonl) and recovery after a reload.

proposal/ (M2): ProposalService builds the review: the proposed graph and its diff, changed files, statement and vocabulary reviews, definition questions, the GOAL->DERIVATION lifecycle item and the report card. It measures drift and plans Accept, either as a 3-way merge with no fuzz and 3 context lines or as exactly the re-gated files. It applies the result through ModelWorkspace.applyChanges. DiskSidecarStore keeps attempts.jsonl and decisions.json.

A run flows like this: start -> preflight -> backend -> set-premises via workspace.perform -> createRunShadow from workspace.readText -> engine.checkBase -> session -> context bundle -> tool calls into the engine -> finish -> normalise and gate -> gate-pass commit, retry, or give-up and revert -> buildProposal -> review -> accept -> proposals.apply -> endRun and prune. If the user's files changed during the run, accept first writes accept-base and rebase commits, then re-freezes and re-gates.

Where comments and code disagree:
- workspace/types.ts calls undo patches "fuzzy", but undo.ts uses fuzzFactor 0.
- shadow/types.ts says git/ has ws/ as its work tree; it is a bare fast-import repository.
- shadow/types.ts says scratch/ holds scratch Lean projects. The directory is created but never written: scratch sources go to Lean on stdin.
- The header of gate/types.ts shows an older ghost-check shape and freeze order.
- AcceptRequest documents `facts` and `realFiles` for the re-gate path, but the RunManager passes neither.

Two unrelated functions are both named rootKeyOf: workspace/git.ts makes the git ref key and shadow/index.ts makes the run-directory key. Until turn 13 runs had only been exercised with the fake LLM backend. On 2026-11-10 the real-Claude path (run/backend.ts -> ClaudeCliBackend) ran four live sessions, all passing at the gate's first attempt (docs/m2-live-report.md); the retry loop, the revert, Feedback, Cancel and resume have still met only the FakeBackend.

## packages/extension and repository-level files

This slice covers everything around the core, runner and webview libraries: the VS Code adapter (packages/extension), the monorepo's root configuration and scripts, the sample model, the shared Lean test fixtures and the design and status docs.

packages/extension is the thin host described in m1-plan section 2. It owns no model semantics: parsing, statuses, edit planning, undo and history, Lean checking and Claude runs are delegated to the runner, and through it to core. extension.ts builds a TeleleanHost (vscode/host.ts). The host contributes three commands (Open Board, Initialize Model Here, Refresh Lean Check) and a serializer for the 'telelean.board' webview panel. Activation is triggered by a workspace that contains .telelean/config.json, or by a board restored after a reload, and it is cheap: nothing parses files, runs Lean or resolves a Claude binary until a board opens and the user starts a run. Untrusted and virtual workspaces are not supported.

The source has three module groups:
- **src/logic/** holds vscode-free logic that is unit-tested.
  - BoardSession dispatches messages for one board. Board edits go through one FIFO queue and run messages through a second, so a run start or an Accept never blocks typing. Cancel and read-only requests skip both queues. Publishes are coalesced, a subject that vanishes makes the board switch to another, and dependentCards are added to needs-confirmation answers.
  - Around it sit actionMapping (protocol message to BoardAction), editApplier, changeBatcher, modelPaths, textSource, settings, runs, initialize, restore, roots, groups and the history and proposal preview helpers.
  - editApplier (CheckedEditApplier) checks each file's current text against the planned before-text, writes minimal line edits, undoes a partially applied edit, and saves.
  - changeBatcher debounces events and recognises echoes of telelean's own writes.
  - modelPaths keeps paths inside the root and refuses symlinks that point out of it.
  - settings clamps the telelean.* values into the runner's settings.
  - runs holds the consent texts, the lazy Claude backend factory (which refuses in Test mode) and the busy check.
- **src/vscode/** holds the VS Code adapters.
  - host.ts: the commands, one BoardPanel per root, restore after reload, the consent modal (only a yes is remembered, per root, in globalState), RunManager construction, and the TeleleanApi with Test-mode hooks.
  - registry.ts: one ModelWorkspace and one RunManager per root, kept until the window closes. Typing, saves and file-watcher events become invalidate calls, plus Lean refreshes while the root's board is open.
  - editor.ts: the WorkspaceEdit port and a TextSource that reads open buffers first.
  - historyProvider.ts: read-only telelean-history: and telelean-proposal: multi-file diffs, opened beside the board.
  - runner.ts: a replaceable record of the runner's factory functions.
- **src/board/** holds BoardPanel: the webview lifecycle, strict nonce-CSP HTML from html.ts, validation of every inbound message with core.parseWebviewToHost, queueing until the session attaches, and the static sample boards.

The data flow runs both ways:
1. A gesture in the webview reaches BoardPanel, which validates it and passes it to BoardSession. BoardSession calls ModelWorkspace.perform, undo, redo or revert, or RunManager.start, answer, accept and so on.
2. The workspace writes through the extension's CheckedEditApplier (one WorkspaceEdit, then a save) and fires onDidChange. The registry forwards that to the session, which republishes workspace and graph. RunManager.onDidChange produces run and proposal messages.
3. Typing, saves and writes by other programs come back through the registry's watchers, with echoes of telelean's own writes suppressed.

**Build and test.** tsconfig paths resolve @telelean/core and @telelean/runner/* to their TypeScript sources. esbuild bundles src, including the runner's llm, run, gate, shadow and proposal modules, the MCP SDK and diff, into a CommonJS dist/extension.js with an injected import.meta.url. The build copies the runner's PreToolUse path guard to dist/bin and checks that the bundle loads under a stub vscode module. packages/webview builds dist/webview separately. Unit tests run in vitest against a vscode stub. Smoke and e2e suites run in an isolated xvfb VS Code 1.140 profile that scripts/smoke.mjs prepares, or (turn 13, `npm run test:smoke:snap`) in the user's own snap VS Code started through its electron-launch (scripts/snap-env.mjs). Every layer sets TELELEAN_NO_REAL_CLAUDE=1 and uses the FakeBackend. Turn 13 also added the demo driver (scripts/demo-driver.mjs with demo-ui.mjs and demo-vscode.mjs, `npm run demo`; its dry run uses test/demo/), which plays the own-example demo in an isolated VS Code: --dry-run, --rehearse, or --live with a double opt-in.

**Root and support files.**

When this survey was written it was not a git repository; since the user's commit "initial generation" of 2026-11-05 it is one (with a GitHub remote), and turn 13's changes are uncommitted on top of it.

## packages/webview

@telelean/webview is the board UI: React 19, a single zustand 5 store and @atlaskit/pragmatic-drag-and-drop, bundled by Vite 8 (entry src/main.tsx) into packages/extension/dist/webview. The output is webview.js, webview.css, assets/codicon.ttf, and public/boot.js copied verbatim. There is no packages/webview/index.html, by design: the extension writes the real HTML itself (packages/extension/src/board/html.ts, strict nonce CSP), and test/harness/index.html copies it for Playwright. The package declares no dependencies of its own (they are all devDependencies of the root package.json) and imports @telelean/core straight from its TypeScript source through an alias in vite, vitest and the tsconfigs.

The host (extension plus runner) is the source of truth, and the board never computes Lean results. It shows what the host sends and turns the user's gestures into typed protocol messages.

Module groups:
- Startup and host link: public/boot.js records CSP violations from the moment the page starts loading. host/bridge.ts is the only caller of acquireVsCodeApi; it checks every incoming message with core's parseHostToWebview and forwards CSP violations as diagnostics. main.tsx connects the bridge, the store and React, adds undo/redo shortcuts, posts `ready`, and after each graph posts a `rendered` diagnostic once the edge engine has measured it.
- State: state/store.ts holds the graph data, host data, UI state and M2 run state. state/context.tsx exposes it to React through useBoard and useBoardActions.
- Pure model code, unit-tested in Node: model/format.ts, model/cardData.ts, model/run.ts and labels.ts.
- The board: Board, Column, NodeCard, CardDetails, LeanCode, UsesLine, VocabularyGroup and GhostCards. Drag and drop is in dnd.ts and dragGuard.ts. Arrows are drawn outside React by EdgeEngine.ts on top of the pure geometry.ts, with edges.ts supplying the edges.
- Around the board: header/, tray/, prompt/, dialogs/, toasts/, and the common/ widgets (Popover, Modal, InlineEdit, AgentText/UserText for marking who wrote a text, InlineCode, ExternalUser, useNow).
- M2 run UI: run/ (RunPanel, Questions, Review, ReportCard, GhostSuggestion, ProposalBanner, RunBadge).

Data flow: a checked `graph` message goes to applyGraph. That function drops older versions, keeps unconfirmed adds as provisional cards and matches them to the host's cards, carries the selection over, and rebuilds the proposal overlay. Every other message (workspace, history, actionResult, notice, run, proposal) goes to receive. Store actions update the board optimistically (moves, re-orders, adds and edits, but never deletes) and post a message with request id r<n>; the counter is kept in the persisted webview state. The host's actionResult either confirms the change, rolls it back with an error toast (unless a newer graph has arrived), or reopens the dependents or delete dialog when the answer is needs-confirmation. The run and the proposal never go through applyGraph. The proposed view is a read-only overlay with diff marks, and proof results stay hidden until the review reveals them (D-19). Run actions (startRun, answerQuestions, feedback, acceptProposal, discardProposal, adoptGhost/rejectGhost, cancel/resume/stop/dismiss) are tracked through runBusy. The webview does not depend on which LLM backend runs; according to the project status, M2 has only been verified with the fake backend.

CSP rules: no style attributes anywhere (positions and the run-panel size are set through the CSSOM), and colours come only from --vscode-* variables. test/unit/theme.test.ts checks those variables against the extension manifest.

Tests (not listed file by file here): Vitest in test/unit covers the store and the pure modules. Playwright in test/e2e drives the built bundle in test/harness with a mock acquireVsCodeApi.

Where the code differs from the docs or from what you might expect:
- packages/webview/index.html does not exist (by design, as above).
- `ready.lastVersion` is always null, because the store is brand new when `ready` is posted.
- PersistedState.subject is written but the webview never reads it back (the host's panel serializer may).
- EdgeEngine.onFrame has no callers.
- ReportCard repeats COST_TITLE's text instead of importing the constant.
- subjectNameProblem, pruneCount, dependentsTexts, revokeVocabularyText, askInsteadText and staleChip are exported but only used in their own files.
- The 25/80/3 figures in RunPanel's comment match core's DEFAULT_RUN_CAPS, but the UI reads the caps from RunView rather than using those numbers.

## Tests (all packages)

Four independent suites, one per package, all deliberately sequential (vitest fileParallelism: false, one Playwright worker, one VS Code instance at a time) because of the RAM rule. File headers cite acceptance-test ids from docs/m1-plan.md or docs/m2-plan.md; the two plans reuse AT1.x-AT6.x for different work packages (M1: markup, model/planner, semantic, workspace, extension, webview; M2: gate rules, engine/shadow, RunManager, proposals, extension, webview).

core (pure TS; `cd packages/core && npm test` = tsc -p tsconfig.test.json, then vitest run). Unit tests of markup (lexer, parser, serializer, values, edits, Lean ops; ported research cases, property, robustness and scale tests), the project model (statuses, edges, vocabulary, stale facts, subjects, diagnostics), the planner (D-11, delete, conditional proofs, carry-overs), graph.json and its committed schema, the protocol, and the M2 gate rules (G0, permitted set/freeze, evaluateRules incl. cheats, carriers, notices, normalisation, ghost adoption) plus proposal codecs/diff. Lean facts are hand-written JSON (test/fixtures/project), derived from text (project/helpers/fakeFacts.ts) or recorded from real Lean 4.35 (gate/realFacts). Fixtures are read through Vite `?raw` (core has no Node types).

runner (Node; `cd packages/runner && npm test` = vitest run with TELELEAN_NO_REAL_CLAUDE=1 and 180 s timeouts; `npm run typecheck` checks src and tests). Three layers. (1) Parsers on recorded Lean/Lake output and pure helpers (semantic/*, gate/pure, llm/streamJson, llm/argvEnv, lean/profile-shadow). (2) Real-Lean integration under runLean (systemd-run --user scope, bwrap, MemoryMax, toolchain v4.35.0 from ~/.elan, LEAN_NUM_THREADS=4) on scratch copies of test-fixtures/ or mental_model/, git only in scratch repos: lean/*, semantic/refresh, gate/engine and gate/rules (Claude played by test-fixtures/gate/edits.json), shadow, workspace, proposal/build, integration/*, and run/walkthrough.e2e, where the FakeBackend plays test-fixtures/walkthrough/*.json: both readings plus a 20-script cheat catalogue (added axiom, sorry, weakened abbrev/type, unselected premise, rebind-target, helper lemma, definition-belief, redefined vocabulary, #eval, proof before freeze, edited words, give-up, goal-premise axiom/belief, derivation-premise proof, private lemma, two carrier cases, example). These assert that no telelean-<runId>-* systemd unit is left; several skip below 12 GB MemAvailable. Turn 13 added run/fresh.e2e (nine scenarios on freshly initialised models with typed cards, played from test-fixtures/fresh/), proposal/boardEdits (pure: the board's edits put back by card id at Accept) and lean/userns (the preflight's bwrap user-namespace probe and its hint). (3) Fakes: run/manager.* via run/helpers (FakeEngine, FakeShadow, fake services, TrackingBackend, fake timers); llm/* against the FakeBackend, the CLI double fixtures/fake-claude.mjs with a real loopback MCP server, and the path-guard hook. Knobs: TELELEAN_TEST_TMP, TELELEAN_KEEP_TMP=1, TELELEAN_ALLOW_REAL_CLAUDE_VERSION=1.

extension: `npm run test:unit` (vitest; `vscode` aliased to test/unit/vscodeStub.ts) covers host logic, the edit applier, manifest/settings, the bundle, host restore and run wiring. `npm run build:all && npm run test:smoke`: scripts/smoke.mjs makes an isolated profile under $TELELEAN_TEST_TMP/vscode-<pid> (HOME, XDG_*, user-data, extensions, a ws with model copies) and runs `xvfb-run npx vscode-test` (VS Code 1.140.0, mocha tdd) as two instances: smoke (activation, board, boards with a fake workspace via testing.useRunner, model with the real workspace and Lean, runs with a FakeBackend) and e2e (e2e.test.ts, e2e-runs.test.ts driving the real board over CDP). Afterwards it fails on changes in the real ~/.config/Code, ~/.copilot, Chrome dirs or trash and on leftover processes or units. TELELEAN_SMOKE_GREP filters; `npm test` runs typecheck, build, unit and smoke. `npm run test:smoke:snap` (turn 13) runs the same two instances in the user's own VS Code snap, started through its electron-launch with the variables of `snap run` (scripts/snap-env.mjs); run it from a terminal of the snap VS Code, whose AppArmor label lets bwrap create its namespaces on this Ubuntu. The smoke instance of both modes also runs the host-environment suite (test/suite/hostEnv.test.ts, turn 13), and the unit tests cover the snap wiring (test/unit/snapEnv.test.ts). scripts/demo-driver.mjs (`npm run demo`, docs/DEMO.md) plays the whole own-example demo in an isolated VS Code: --dry-run (a scripted Claude, test/demo/), --rehearse (the live UI path up to the consent, refused by the quota tripwire) and --live (double opt-in).

webview: `npm run test:unit` (DOM-free store, run model, geometry, edges, formatting, card data, theme CSS); `npm run build && npm run test:e2e` runs Playwright (installed Chrome, headless, one worker) on the built bundle served at 127.0.0.1:41739 with a mock acquireVsCodeApi and the real CSP. Every spec fails on console, page or CSP errors; home-guard and chrome-tmp keep Chrome out of the real home. Root `npm test` runs every package's script.

Quota tripwires (plan 10.4): (1) TELELEAN_NO_REAL_CLAUDE=1 in both vitest configs, .vscode-test.mjs and smoke.mjs: createClaudeBackend refuses without a scratch resolve, and ClaudeCliBackend.startSession launches only node plus a test-fixture double (llm/tripwire, run/backend). (2) The Test-mode extension never builds the real backend; only testing.useRunBackend installs one (unit/runBackend, hostRuns, realRuns). (3) The live scripts are dry by default and refuse half-armed or tripwired runs (run/smokeScript, walkthroughScript, quotaTripwire). The demo driver (turn 13) follows the same rule with TELELEAN_DEMO_LIVE=yes, and its --rehearse mode must be refused by the tripwire before any Claude binary is looked up. No test runs real Claude.

Docs vs code: core edit/conditional.test.ts cites a missing runner integration/conditional.test.ts (its real-Lean counterpart is integration/fixes.test.ts); helper headers (fakeMarkup, scenarios, parseFixture, gate/helpers, run/helpers/*, proposal/helpers, m2-carryover.spec) still describe stubs and gated blocks, but nothing is gated now; no test reads llm/fixtures/recorded-cli-2.1.314 although docs/m2-plan.md says tests use it; the walkthrough README says the RunManager unit tests use its scripts, but they script inline.
