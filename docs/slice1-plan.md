## 2. Contracts (integrator's changes; builders implement them as written)

### 2.1 core `model.ts`
- `NodeType = 'AXIOM' | 'PROPOSITION'`, and `NODE_TYPES = ['AXIOM', 'PROPOSITION']`. `isNodeType` accepts only these.
- New `parseNodeType(raw: string): { type: NodeType; alias?: 'ASSUMPTION' | 'DERIVATION' | 'GOAL' } | undefined`. It is case-insensitive, as today: lower case keeps TL019's hint. It maps ASSUMPTION → AXIOM, and DERIVATION and GOAL → PROPOSITION.
- `ProofStatus`: `{ kind: 'pending' }` replaces `{ kind: 'pending-promotion' }`.
- `StatusFlag` changes:
  - remove `proved-goal` and `claimed`;
  - rename `rests-on-claimed` to `rests-on-pending`;
  - add `established` (B.5).
- `TlNode`: add `fromNothing?: boolean`. It is true when the block has the field `follows_from: nothing` (AR-5, B.6).

### 2.2 core markup
- `type:` takes AXIOM or PROPOSITION. ASSUMPTION, DERIVATION and GOAL are read as aliases, with no diagnostic, and never rewritten.
- telelean writes AXIOM or PROPOSITION only when it writes a `type:` line: for add-node, and for a kind change.
- "Follows from nothing" is its own known field, `follows_from: nothing` (B.6, decided after the soundness review's S-12, AP-15). It goes in FIELD_ORDER right after `premises`.
  - Any other value is a markup error (new code TL022, "follows_from takes only the value nothing"), and the field is then ignored.
  - With non-empty `premises:` it is an error too (TL023, "a card cannot both follow from nothing and have arrows"); the arrows win and the mark is ignored.
  - A `premises:` line with no valid id stays what it is today. It is never the mark.
  - The field is data telelean keeps (CF-3): G5 compares it, so Claude cannot write it.
- G5's byte comparison of the markup is unchanged.

### 2.3 core `layout.ts`
- `columns: { AXIOM: string[]; PROPOSITION: string[] }`. Old layouts are parsed leniently: ASSUMPTION → AXIOM, and DERIVATION + GOAL → PROPOSITION, concatenated.
- Add `positions?: Record<string, { x: number; y: number }>`: canvas coordinates of propositions (1c).
- Serialisation stays stable, as today.

### 2.4 core `actions.ts` (BoardAction) and planners
- `add-node` gains an optional `position` (1c).
- `change-kind`:
  - `to: 'AXIOM'` (proposition → axiom) removes the `premises:` line, as part of the same plan (AR-7). The `.holds` handling is D-11's old D→A / G→A row.
  - `to: 'PROPOSITION'` is refused with `invalid`: "To make an axiom a proposition, draw an arrow into it, or mark it 'follows from nothing'." (AR-6)
- New `{ kind: 'add-arrows'; target: string; sources: string[]; confirmed?: boolean }`.
  - It adds the sources to the target's `premises:`, keeping the existing order and appending new ones; duplicates are ignored.
  - It refuses, with `invalid` and a message naming the cycle or the problem:
    - a cycle (over declared premises and verified proof edges);
    - another subject;
    - a self-arrow;
    - an unknown id.
  - It removes `fromNothing`.
  - **Into an axiom:** the same plan also changes the target's kind to PROPOSITION, by D-11's old A→D row: the `.holds` axiom stays, now **pending**. When cards rest on it (`kindChangeImpact`), the planner answers `needs-confirmation`, with the text "N cards that rest on it will lose their green glow until it is proved", unless `confirmed`.
- New `{ kind: 'remove-arrows'; arrows: { source: string; target: string }[]; confirmed?: boolean }`. It removes the entries. If the target's proof uses a removed source (a verified edge), it answers `needs-confirmation` (spec A16) unless `confirmed`.
- New `{ kind: 'set-from-nothing'; id: string; on: boolean; confirmed?: boolean }`.
  - `on` on a proposition with no premises writes `follows_from: nothing`; on a proposition with premises it is refused.
  - `on` on an axiom also changes its kind to PROPOSITION, as add-arrows does, with the same confirmation.
  - `off` removes the `follows_from` line.
- New `{ kind: 'claim-pending'; id: string }` (AR-8, ★D7 (b)). It applies to a PROPOSITION with a Lean statement and no `.holds`, and adds `axiom n.holds : n` (D-11 `add-holds-axiom`). It is refused otherwise.
- New `{ kind: 'move-cards'; positions: Record<string, { x: number; y: number }> }`. It is layout only, like `reorder`, and one Undo step labelled "Move: …".
- `set-premises` stays in the type for old History entries, but nothing sends it any more (1e).
- Each new action is one Undo step and one History entry.

## 3. The canvas (1c)

- **Structure:** a viewport `div` (overflow hidden, focusable) holding one transformed layer (`transform: translate(tx, ty) scale(s)`, via CSS custom properties set from a class; no inline style attributes, because of the CSP: use `element.style.setProperty` from code, which the CSP allows, as EdgeEngine already does with attributes). Cards are absolutely positioned at their layout positions.
- **Zoom:**
  - `wheel` with `{ passive: false }`; `s′ = clamp(s · exp(−deltaY · k), 0.1, 4)`, with k larger when `ctrlKey` is set (pinch deltas are small);
  - keep the point under the cursor fixed: `t′ = c − (c − t) · s′/s`.
- **Pan:** right-button `pointerdown` → pointer capture → pan.
- **The right-click menu:**
  - suppress `contextmenu` on the viewport, the column and the cards (on Linux the event fires on the press);
  - on right `pointerup`, if the total movement is under 4 px, open the menu (common/Popover) at the pointer, for the thing under it, selecting it first unless it is already selected.
- **Left-drag:**
  - on a card: move it (pointer events, not pragmatic-drag-and-drop), committing `move-cards` on release;
  - released over the AXIOMS column: run the "Move to axioms" flow instead (AR-7, with its confirmation);
  - an axiom dragged onto the canvas is refused, with the drop text "Draw an arrow into it to make it a proposition";
  - on empty canvas: a selection rectangle.
- **Keyboard:**
  - Tab and Shift+Tab move focus over the cards in order (column, then canvas top-to-bottom, left-to-right), and the canvas follows the focused card;
  - `+`, `−`, `0` (Fit all), and the arrow keys pan when the viewport has focus.
- **Toolbar:** Fit all, Zoom to selection, Tidy layout.
- **Placement:** propositions without a stored position get a layered layout. The x coordinate comes from the longest declared-premise path from a source; the y coordinate stacks cards in file order within a layer, avoiding stored cards. It is computed in the webview, and never written until the user moves the card.
- **Above the board:**
  - the Vocabulary and Definitions columns (BD-1), split from `VocabularyGroup`;
  - a draggable divider, whose height is kept in webview state;
  - a collapse to one line with counts and flags.
- **The AXIOMS header** counts presuppositions and hidden assumptions, linking to the Vocabulary column.
- **EdgeEngine** is generalised from three scrolling lists to the AXIOMS list plus the canvas:
  - card boxes from `getBoundingClientRect` in board space;
  - canvas-internal arrows clipped to the viewport;
  - column ends clamped to the column's visible band, with today's stub badges;
  - a recompute on scroll, pan, zoom and resize, at most once per frame.
- **Arrow hit paths:** a transparent wide stroke under each path with `pointer-events: stroke`, for selection and the menu.
- **Reveal** pans and zooms to the card.

## 4. Glows, bands and arrows (1d)

- **Glows:**
  - the blue aura (`data-formal='formalized'`) stays;
  - a new `[data-established]` gives the green glow (`--tl-proved`), which replaces the blue one;
  - proved but not established keeps blue, plus a chip: "rests on pending: ‹card›", "given: ‹card›" or "uses a hidden assumption";
  - pending shows "pending proof".
- **Band:** for each proved or conditional proposition, the verified edges into it form its band.
  - It is drawn as an arc across the ends of those arrows near the target, in `--tl-proved`, with a "✓" label and the tooltip "Together these suffice (checked by Lean) · consistency unchecked".
  - A "from nothing" proof draws the band on the ∅ stub.
  - If the target's statement closure uses definitions, or its footprint has `presup:` entries, the band's tooltip adds "also by definition: …" and "also presupposes: …".
  - In the proposed view, bands are hidden like verified arrows until the result is revealed (the existing D-19 overlay logic).
- **Arrow looks** (BD-5):
  - declared arrows are dotted (`stroke-dasharray` with round caps, e.g. `1 5`);
  - verified arrows are solid;
  - conditional arrows keep the hollow head;
  - TL109 (declared but unused) is no longer drawn in the warning colour: plain dotted, with the tooltip "not used by the current proof";
  - TL107 (used but undeclared) stays in the warning colour.
- **Legend:** declared, verified by Lean, conditional, mismatch, formalised, established, band, pending proof.
- **High contrast:**
  - the band is an outlined bracket with "✓";
  - the green glow becomes a 2 px outline in `--tl-proved` with a "✓ established" chip.
