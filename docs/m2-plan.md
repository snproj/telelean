## 0.1 Reviewer corrections (turn 9)

What the review changed, so builders know which parts are new (each is folded into the sections named; contract changes are in section 14):
1. **Gate holes closed** (section 3.3). (a) `footprint` now applies to `gate-other` too, and a new rule `status-mismatch` refuses a `not_proved` finish while the files hold a new or changed proof of the target: before, a "not proved" round could carry a lemma or a target proof resting on an unselected assumption into the user's files. (b) `markup` now forbids changing or removing any `lean:` line and re-binding any card formalised before the run: before, Claude could re-point a formalised target's pin to a new weaker abbrev, freeze that, and pass G4. (c) `statement-changed` exempts the target's `.holds` (a pending promotion would otherwise always fail). (d) `existing-changed` counts a removed declaration as changed and compares docstrings too (a rewritten gloss would otherwise show as the user's wording). (e) A **base check** builds the user's files right after the shadow is created: Lean errors there end the run before any prompt (Claude could never pass G1 on them), and B's facts let `existing-changed` compare the user's declarations by meaning as well as by text (an `open … in` or a new instance could otherwise change what unchanged text means). (f) The readiness rules apply to `freeze` and `gate-proved` only, so an honest "could not formalise" can end as `not_proved`; a selected derivation resting on the target's own claimed `.holds` is unusable (circular) and never adds that axiom to the permitted set.
2. **Ghost text** (sections 3.8, 4.9): the single-term rule (core `ghostTextProblems`) and the pinned check (facts 7 and 8); adoption writes exactly the checked text.
3. **G0 judges only Claude's lines** (section 3.1): a user's own `set_option … in` or `#eval` line in a file Claude edits no longer fails every attempt; stray non-Lean files Claude writes are findings (`outside-subject`, or `bad-path` inside the subject's folder), not environment failures (section 4.2).
4. **What the proposal shows is always a judged state** (sections 2, 3.7): edits Claude makes after `finish` are discarded at the end of the turn; after a revert telelean normalises again, so the accepted formalisation is pinned and docstringed.
5. **Accept after drift** (section 7.1): the re-check uses the user's files at Accept as B (`accept-base` commit), so the user's own edits during the run are not judged as Claude's; the freeze copy drops the target's `.holds` and everything that uses it; drift includes files the user added or deleted; Accept then applies exactly the re-gated files.
6. **Premises declaration after preflight** (sections 2, 8.1): `RunManager.start` declares the premises itself, only after preflight passed and the backend was obtained; the extension only asks for consent. A refused start changes nothing.
7. **Quota tripwires** (sections 8.4, 10.4): `TELELEAN_NO_REAL_CLAUDE=1` in every test runner (already in `packages/runner/vitest.config.ts`) makes `createClaudeBackend` and `ClaudeCliBackend.startSession` refuse; the extension never constructs the real backend in Test mode; the backend is created lazily through a factory at the first start; `createClaudeBackend` has test hooks so tests never scan the real PATH or home.
8. **Parallel building** (section 9): the engine, RunManager, proposal service and sidecar store take `core` test hooks (as M1's workspace did), so each WP can test against fakes; acceptance tests that need another WP are marked **[gated]** and run by the integrator; the exact singular texts of carry-over 2 are frozen in section 1.3, so WP1 and WP6 agree.
9. **Smaller fixes**: the cost estimate is the latest `result`'s value, never summed across `--resume` (the CLI's own figure is cumulative for the conversation, m0 smoke test); a cap reached during a tool call takes effect when the call returns; an environment failure in the gate is retried once after 30 s before the run fails; the cheating scripts' retries replace the cheat instead of adding a second theorem; the system prompt no longer forbids vocabulary axioms by mistake and names the subject folder from the first message; the CLI's own session files under `~/.claude/projects/` are reported as an effect of the live walkthrough.

## 3. The prototype gate, exactly

Closing round 1: sections 3.1 to 3.3 were checked line by line against the code (core `gate/g0.ts`, `gate/permitted.ts`, `gate/rules.ts`, `gate/decls.ts`, `gate/normalise.ts`; runner `gate/engine.ts`, `gate/findings.ts`) and describe what it does; the fixer-round notes they collected are folded into the rules. Closing round 2 corrected four more places against the code (text only): stray files and `lakefile.lean` in 3.1, the `build` row of 3.3 (with its fail-closed sentence, also in the order above), and the ghost's name in 3.8 (also checked against core `gate/adoption.ts` and runner `run/manager.ts` `ghostName`).

The gate runs on the shadow after `finish`; `check_lean` and `freeze_statements` run subsets of the same rules (core `evaluateRules`, purposes `check`, `freeze`, `gate-proved`, `gate-other`). Inputs: the run base B (exactly the user's files at run start, the shadow's `base` commit, with B's Lean facts from the run's base check; for Accept's re-check after drift, the user's files at Accept, the `accept-base` commit, without facts: section 7.1), the adoption reference A (the shadow at its newest `adopt` commit, when a ghost was adopted: telelean's own ghost blocks and declarations are checked against it, never against B), the round start R (the shadow when the round began; B in round 1), the shadow now S (after normalisation, as committed: the gate judges one committed state) with the build mirror's fresh Lean facts of S, the round's freeze F, the selection Sel (target T, premises P, adopted ghosts), the finish status.

**Why these checks make "proved" mean "proved from exactly the selection"** (the Prototype profile's central claim): the target's statement and every selected statement are frozen before any proof exists (`proof-before-freeze`, which also catches a proof carried inside a definition, instance or structure, and the freeze); a formalised card's statement cannot be swapped (`markup`: no `lean:` line changed, no card re-bound); `existing-changed` keeps every declaration the user had, by text and, with B's facts, by meaning; G4 checks the target theorem against the freeze with the permitted set computed from the freeze; `footprint` holds for every declaration the run adds or changes, whatever its kind or type (a definition, instance or structure can carry a proof too) and whatever the finish status; no `example` (a proof without a name, which no rule could check) is ever left in the files; and what the proposal shows is always a judged state (gate-pass files, or a reverted, normalised and re-checked passing state).

**Order and short-circuits** (runner `engine.runCheck`, then `engine.gate`): G0 (text only, core `checkFileChanges`) → if any G0 finding, stop: Lean never elaborates text that fails G0 → sync the build mirror (a working copy that cannot be synced is an environment outcome, section 3.6) → G1: one Lean job, `semantic.refreshLeanFacts` on `build/`; a runLean `timeout`/`oom` is a `budget` finding and stops the check there, and `could-not-start`, `low-memory`, a cancellation or an unsupported project stop it as environment outcomes → core `evaluateRules` on S's project model with the fresh facts: G1's Lean-error findings, G3, G5 and the readiness and stage rules (failing closed, when the rules reported no `build` finding, the engine adds one for each Lean error of the build, or one for a build that failed without an error message) → in the gate, `finish(proved)` without a freeze always carries `not-frozen` → only when there is no finding at all, the status is `proved` and the round has a freeze: G4 (lake comparator).

### 3.1 G0: token denylist and file rules (core `scanForbidden`, `checkFileChanges`)

Only paths that differ between B and S are judged; S here is every regular file in ws/ (`ShadowWorkspace.currentFiles`), so a stray file Claude wrote is a finding (counted), not an environment failure: `notes.md` at the root of ws/ (the path guard allows writing there) or anywhere else outside the subject is `outside-subject`, and `<library>/<S>/notes.md` inside the subject's folder is `bad-path`. Each such path first gets the file rules below (at most one file-rule finding per path); then every added or changed `.lean` file except `lakefile.lean` (a project file: it gets `project-file` only), inside the subject or not, is scanned for forbidden tokens, and in it only Claude's lines: a forbidden token on a line whose exact text also occurs in B's version of the file is the user's own and is not reported (line-multiset comparison, `scanForbidden(file, text, ctx, baseText)`; extra copies of such a line are reported), so a user's `set_option … in` or `#eval` line never fails Claude's attempt just because Claude edited the same file. Tokens come from core's `lexLean` (comments, strings, docstrings and telelean blocks never count) and match by their text or their canonical name (`«sorry»` is `sorry`). A symlink, special file or dot-entry in ws/ never reaches G0: the shadow refuses it first (an environment outcome, section 3.6; Claude's confined tools cannot create one).

| Code | Forbidden (code tokens), or the file rule |
|---|---|
| `hash-command` | `#` immediately followed by an identifier whose first component is not `check` or `print` (`#eval`, `#exit`, `#reduce`, `#synth`, …) |
| `metaprogramming` | `initialize`, `builtin_initialize`, `run_cmd`, `run_elab`, `run_meta`, `run_tac`, `macro`, `macro_rules`, `syntax`, `notation`, `infix`, `infixl`, `infixr`, `prefix`, `postfix`, `elab`, `elab_rules`, `declare_syntax_cat`, `declare_simp_like_tactic` |
| `native-code` | `native_decide`, `bv_decide`, `implemented_by`, `extern`, `csimp`, and the identifier `native` wherever it occurs (`decide +native`); `ofReduceBool`, `ofReduceNat`, `reduceBool`, `reduceNat` however qualified (`Lean.ofReduceBool`) |
| `unsafe` | `unsafe`, `partial` |
| `set-option` | `set_option` (every option: limits such as `maxHeartbeats`, `maxRecDepth`, `synthInstance.*`, `debug.*`, `autoImplicit`, …) |
| `sorry` | `sorry`, `admit` |
| `import` | an `import` (also `import all`) whose module is not in `G0Context.projectModules` (the library's modules in S), or an `import` with no module after it |
| `project-file` | file rule: `lakefile.toml`, `lakefile.lean`, `lean-toolchain` or `lake-manifest.json` added, changed or deleted (no other file rule applies to these four, and `lakefile.lean` is not scanned for tokens) |
| `deleted-file` | file rule: a file of B missing from S |
| `outside-subject` | file rule: a changed or added file, of any name or extension (a stray `notes.md` at the root too), outside `<library>/<S>/**` and `<library>/<S>.lean` (a deleted one is `deleted-file`) |
| `bad-path` | file rule: an added file inside the subject that is neither `<library>/<S>.lean` nor `<library>/<S>/<A>/…/<Module>.lean` with ASCII identifier components (letters, digits and `_`, not starting with a digit) |

### 3.2 The permitted set (core `computePermittedAxioms`, from the frozen model)

Computed at every freeze from the project model of S **as frozen** (its facts) and B (the runner always passes B: the base commit with B's facts, or Accept's accept-base), kept in the freeze (`FrozenSnapshot.permitted`), passed to comparator as `permitted_axioms`, shown to the agent in the freeze reply and on the report card:

```
permitted(F) = ( STD ∪ signature ∪ selected ∪ presuppositions ∪ derivation footprints ) \ { T.holds, sorryAx }
  STD                   = { propext, Classical.choice, Quot.sound }
  signature             = { a | a is an axiom (facts kind) bound to no card (never a card's statement or .holds),
                                facts.typeSort(a) ≠ "Prop", and either a is vocabulary of kind sort, predicate, function or
                                constant (never `other`, never `unmarked-axiom`), or a is no vocabulary item, Lean typed it and
                                it lies outside every subject's modules (the library root, which only the user writes) }
                          (sorts `axiom T : Type`, predicates `… → Prop`, function and constant axioms)
  selected              = { n.holds | n ∈ P ∪ ghosts has a statement and a .holds that states exactly it (no `holds-mismatch`),
                                and n.holds is an axiom }
  presuppositions       = ⋃ { lean.presupposes(x) | x ∈ {T} ∪ P ∪ ghosts }   (D-3b, via #print axioms of the statements;
                                every selected card counts, usable or not)
  derivation footprints = ⋃ { axioms(d.holds) \ {sorryAx} | d ∈ P ∪ ghosts has a statement and a .holds that states it, d.holds
                                is not an axiom, d's core status is `proved` (not conditional, no sorry) with a known axiom list,
                                T.holds ∉ axioms(d.holds), and the proof is the user's own: d had the same statement in B and
                                d.holds is a declaration of B with the same source text (B's axiom list when B has facts) }
unusable     = { p ∈ P ∪ ghosts | p contributes nothing: no statement or no .holds, a .holds that does not state p, a proof that is
                         not `proved` (code-less, an unproved goal or derivation, conditional) or has no axiom list, one resting on
                         T's own claimed .holds (circular), or a proof that is not the user's own unchanged proof from B }
```

Spyro, normative reading, all three selected: `propext`, `Classical.choice`, `Quot.sound`, and `Spyro.` + `Character`, `Game`, `HasDarkPast`, `IsPG`, `GoodAddition`, `cynder_dark_past.holds`, `new_spyro_pg.holds`, `pg_no_dark_past.holds`, `Character.exists`, `Game.exists`: 13 names, exactly the M0 comparator test's `permitted(ALL_SELECTED)`. Zero premises ("Self-evident?"): STD ∪ signature ∪ presuppositions of the target. The target's own `.holds` axiom (a pending-promotion derivation) is never permitted: it is removed from every part, and a derivation footprint containing it makes that premise unusable. A round that finishes with any status but `proved` without having frozen still has its additions checked (rule `footprint`): against `permittedAxioms(current model, Sel, B)`, the same formula over the files as they are (nothing is claimed proved, so no freeze is needed for that). Why the signature never takes a declaration bound to a card (fixer round 1, M2 verification, gate lens): an `axiom side_goal : Empty` directly below a selected code-less GOAL's block is that card's "statement" and would prove anything. Why a derivation footprint comes only from a proof the user already had in B: a proof Claude writes (or changes) for a selected GOAL/DERIVATION premise would otherwise widen the very set it is judged against, and, after Feedback, the next freeze; Claude's proof of a premise can still be used as a lemma, whose own footprint must then be permitted. A presupposition axiom Claude creates (`axiom T.exists : Nonempty T` for a new sort T, M1's `presupposition` kind) is allowed before the freeze (rule `new-axiom`: it is vocabulary) and enters the set only through the statements that mention T; it is always a definition question (D-3).

### 3.4 Normalisation before every gate (core `normalisationChanges`, WP2 `engine.normalise`)

For T, selected premises and ghosts whose statement declaration is new in this run (a statement declaration in S, none in B) and well-formed (no TL101/TL113): pin it (for an adjacent binding write `lean: <fully-qualified statement>` into the block, D-8; writing the block also writes the derived id back if the block had none, TL112; a pinned binding only gets the id), and set the statement's docstring to `escapeBodyText(natural_name)` when it differs (D-9 mirror). Uses only WP-markup primitives (byte-stable elsewhere); commits `normalise` when anything changed; idempotent. So the agent never edits blocks, and G5 never fails for a pin or a docstring.

### 3.5 Findings to the agent, the board and the M0 verdict

Every finding has `message` (exact, for Claude: names, `file:line:col`, Lean's whole message, what to do) and is described on the board by core `describeFinding` in one plain sentence; the A2 notice is core `attemptNotice`:
- "Attempt 1 didn't pass: it used “The new Spyro game is PG” (`new_spyro_pg.holds`), which you didn't select. Asking Claude to retry."
- "Attempt 2 didn't pass: it left a gap (`sorry`) in `cynder_not_good.holds`. Asking Claude to retry."
- "Attempt 2 didn't pass: it changed the statement it had to prove (a definition the frozen statement depends on changed: `cynder_not_good`). Asking Claude to retry." (M0 lesson 2 wording)
- "Attempt 1 didn't pass: it used a forbidden command (`#eval`) in Model/Spyro/Main.lean line 12. Asking Claude to retry."
- "Attempt 1 didn't pass: it added an axiom (`shortcut`), and only you can add beliefs. Asking Claude to retry."
- "Attempt 1 didn't pass: it changed your words on “Cynder is a character who has a dark past”. Asking Claude to retry."
- after the cap: "Claude's attempts didn't pass the checks 3 times: each time it used `new_spyro_pg.holds`, which you didn't select. telelean reverted its working copy to “Statements frozen (round 1)”."

Mapping of finding codes to the M0 `GateFailure.check` (what `renderGateVerdict` prints): G0 codes → `lint`; `build`, `budget` → `build`; `footprint`, `new-axiom` (after freeze), `comparator-illegal-axiom` → `footprint`; `sorry`, `sorry-axiom` → `no_sorry`; `not-proved`, `statement-changed`, `existing-changed`, comparator statement/definition/kind/missing codes → `statement_unchanged`; `vocabulary-shape`, `new-axiom` (before freeze) → `vocabulary`; `markup` → `markup`; `not-frozen` → `not_frozen`; anything else (incl. `status-mismatch`) → `other`. Board sentences for the reviewer's additions: `status-mismatch` → "it said the goal was not proved but left a proof of it in the files"; `markup` for a re-pointed pin → "it re-pointed “<sentence>” to a different Lean statement".

### 3.6 Environment failures

`could-not-start` (sandbox), `low-memory`, a mirror that cannot be synced (`ShadowLayoutError`: a symlink, special file or dot-entry in ws/, which Claude's confined tools cannot create), comparator `could-not-start`, cancellation: not the agent's fault and **not counted** as an attempt or a check. In `check_lean`/`freeze_statements` the tool returns the reason (`CheckResult.environment`), and the agent may finish. In the gate telelean first waits 30 s and runs the same gate once more inside the same tool call (a transient memory dip should not cost the round's work); if that is an environment outcome too, the verdict is `give_up` with `environment` set, the run ends `failed` with the reason on the board, and the shadow is kept. A failed run is terminal: the user fixes the cause and starts a new run. A runLean `timeout`/`oom` of the agent's own build is a `budget` finding (counted).

### 3.7 The gate loop and the revert (A2)

Attempts count `finish` calls per round (`RunCounters.gateAttempts`, cap `maxGateAttempts`, default 3, setting `telelean.run.maxGateAttempts`). Pass → commit `gate-pass` with exactly the judged files, verdict from the status (`proved`, `not-proved`; `insufficient` and `inconsistent` are shown as "not proved" / "Claude reports a conflict (unverified until M3)"). Fail below the cap → `retry`. Fail at the cap → `give_up`: after the turn ends, ws/ is restored to the newest commit of kind `gate-pass`, `freeze` or `base` (`ShadowWorkspace.revertTo`), telelean's normalisation runs on it (a `freeze` commit has no pins or docstrings yet; section 3.4), that state is re-checked (one Lean job, not counted) so the proposal has facts, and the proposal is built from it (often "the formalisation, not proved": the user can still Accept the statements). The same revert, normalise and re-check ends a `no-finish` or `cap-reached` round. The attempt is kept in attempts.jsonl either way. The user's real files are never touched by any of this.

**What the proposal shows is always a judged state.** The CLI runs telelean's MCP tool calls one at a time and never concurrently with Edit/Write (telelean's tools declare no `readOnlyHint`, so the CLI does not treat them as concurrency-safe; WP3 keeps it that way), so nothing changes ws/ while a check or the gate runs. Claude can still edit files after `finish` returned, before its turn ends: at the turn's end the RunManager compares ws/ with the `gate-pass` commit and resets ws/ to it when they differ (notice `info`: "changes made after finish were discarded"). For a `give_up`, `no-finish` or cap round the revert above does the same.

### 3.8 The ghost check (WP2 `checkGhost`, D-6)

Requires the round's freeze (else the tool refuses: "freeze first; the gap is judged against the frozen statements"). First the **single-term rule**, without Lean: core `ghostTextProblems(lean_statement, proof)` must be empty (no G0 token, no comment delimiter or `#` command, no command keyword such as `axiom`/`theorem`/`def`/`example`/`namespace`/`end`/`@[`, and, in the statement, no `:=` or `|` outside brackets and every bracket balanced): Claude's text then cannot close the generated declaration and start another one (fact 8 of section 0 shows what that would allow). The statement is used with whitespace runs collapsed to one space, and that collapsed text is what the ghost card shows and adoption writes. Then the engine makes sure the mirror holds a clean check of ws/ as it is (`check`: G0, sync, build; problems there refuse the ghost with them). Then a scratch check on the standard input of `lake env lean --stdin --json` in the mirror (nothing is written, never into ws/): `import <library>` … `namespace <S>` `abbrev telelean_ghost_stmt : Prop := <statement>` `theorem telelean_ghost_check : telelean_ghost_stmt → <T statement> := <proof>` `end <S>` `#print axioms <S>.telelean_ghost_check` (fact 7). It passes when the file elaborates **without any error**, the axioms of `telelean_ghost_check` (read from the message naming exactly that declaration) ⊆ permitted, and there is no `sorryAx`. `aloneEntails` = none of its axioms is a `.holds` of the selected premises or of their derivation footprints (flagged: "this suggestion alone gives the goal; it may simply restate it"). A suggestion can only use vocabulary that exists (after the freeze no new vocabulary may be added; the system prompt says so). The ghost's Lean name is chosen twice. When Claude suggests it (runner `ghostName`; the tool result names it): Claude's `lean_name` when it is a plain identifier (`[A-Za-z_][A-Za-z0-9_']*`), not a Lean keyword, neither `<S>.<name>` nor `<S>.<name>.holds` is declared in the project and no other suggestion of the run has it; else the natural name's first six words, lowercased without accents and joined with `_` (prefixed `ghost_` when that does not start with a letter or is a keyword), suffixed `_2`, `_3`… while taken. At adoption (core `adoptionPlan`) that name is kept when it is a valid identifier, not a Lean keyword or command word, not used as an identifier anywhere in the project's code (the first component of any identifier token of any model file), and neither `<ns>.<name>`, `<ns>.<name>.holds` nor `<name>` itself is declared (`<ns>`: the target block's namespace); else `deriveId(natural_name)` with both `-` and `.` turned into `_` (prefixed `ghost_` when that does not start with a letter or is not a valid name), suffixed `_2`, `_3`… while taken. The adoption turn tells Claude the name used (section 5.3). Counts as one check.

## 4. The runner: flows

### 4.1 Preflight (WP3 `runPreflight`; before anything is created or sent)

In order, each refusal a plain sentence (`PreflightOutcome`): (1) busy: another non-terminal run of the root; (2) selection: T is a GOAL or DERIVATION card of the subject (an ASSUMPTION is something the user holds: "make it a Derivation first (D-11), then prove it"), every premise is a card of the subject, T ∉ P; (3) workspace: the ModelWorkspace implements the M2 members and the subject loads; (4) toolchain: `lean-toolchain` is `leanprover/lean4:v4.35.0` (D-7) and the project has no Lake dependencies (as M1); (5) sandbox: `lean.checkSandboxSupport()` (turn 13: then `lean.checkUserNamespaces()`, one `bwrap` run on `/usr/bin/true` with the real profile's namespace flags, cached after a success, because a kernel with AppArmor's user-namespace restriction lets `bwrap` set up its namespaces only under a profile that allows it, such as the VS Code snap's; `docs/m2-live-report.md` §5.5); (6) memory: MemAvailable ≥ the guard. Only when all six pass does `start` obtain the backend (the factory, first start only; it runs nothing but `claude --version`) and then declare the premises (`set-premises`, when non-empty and different from the declared ones); a refusal at any of these steps leaves the user's files, the runs dir and the processes exactly as they were. Right after the shadow is created, `engine.checkBase` builds the user's files as they are (one Lean job, not counted): Lean errors anywhere in them end the run as `failed` before any prompt (Claude may not change the user's files, so every attempt would fail on them), and the facts are kept as B's facts. The CLI's own checks follow at session start (guard self-test, `initialize` account = claude.ai subscription, `get_hooks_listing` shows the guard): all before the first prompt, so a refusal costs no quota.

### 4.2 The shadow (WP2; layout in `runner/src/shadow/types.ts`)

`<runsDir>/<rootKey>/<runId>/{ws, build, git, session, frozen/<n>, gate/<n>, scratch, run.json}`; `runsDir` = `<globalStorage>/runs` in the extension (03 section 8.4), a scratch dir in tests.
- **ws/** (Claude's cwd and the guard's root): the base texts from the TextSource view (`ModelWorkspace.readText`, open buffers first) of every model file and the project files. No `.lake`, `.telelean`, `.git`, `.gitignore`: the root holds no dot-entry, so the M0 guard allows Grep/Glob on it (m0-report lesson 4).
- **build/**: the Lean mirror (the model files + `.lake/`, the run's own Lean build). Closing round 1 (decisions-log section 30; `runner/src/shadow/seed.ts`): the mirror starts **without** the user's `.lake/build`, so the run's first Lean job (the base check) builds the model from scratch, about a second for Spyro. Lake may be writing the user's `.lake/build` while a run starts (the board's refresh after a save, an Undo or the start's own premises declaration; the Lean extension; a terminal), and fixer round 3's checks of the live tree could not rule out copying a build in progress: with an outside `lake build` running, 98 of 99 seeds the final verifier's probe used were partial or mixed snapshots (Lake's own hash check made every result correct anyway). Seeding is kept only behind the setting `telelean.run.reuseLeanBuild` (default off; `RunSettings.reuseLeanBuild`, passed as `CreateShadowOptions.copyBuild`), and then the seed is what the user's `.lake/build` held right after the board's last refresh, untouched since: the model workspace's refresh calls `noteRefreshOutput` inside its own Lean job (`semantic.runExclusive`), which records the tree (every directory and regular file: device, inode, size, mtime, ctime) only after a refresh with status `ok` and every module fresh, and only when the tree looks like a complete build (each fresh module has its `.olean`, `.ilean` and `.trace`, no artifact newer than its trace, no Lake lock, no temporary file younger than 10 minutes); any other refresh forgets the record. These checks see which files exist and their times, not which version of the sources a module was built from: a module that another program (a terminal, the Lean extension) finished rebuilding from other versions of the files while the refresh ran, outputs and trace alike, passes them, so a record can hold modules of two versions (closing round 2: the closing round 1 verifier wrote one module's outputs from another version during 24 refreshes, as Lake writes them; 10 of the 14 seeds then used held that module from the other version, the write landing in the refresh's check phase in 9 of them). `createRunShadow` then copies the tree inside `semantic.runExclusive` only when a listing taken now equals the record, re-checks every file after its copy and lists the tree again, which must still equal the record (any write, create, remove or rename changes a file's or its directory's ctime), so nothing written after the record or during the copy is ever seeded. Correctness rests on Lake's per-module check, not on the seed: Lake compares every module's trace with the run's own sources (which can differ from the refresh's anyway: open buffers, the start's premises declaration) and rebuilds each module that does not match (on the verifier's two-version seeds it rebuilt the odd module, and every `.olean` then equalled a clean build). Lake does not re-read a module's outputs when its trace matches, so two Lake builds writing the same module at the same moment (Lake 4.35 takes no build lock) could leave outputs it wrongly trusts, in the user's own `.lake/build` as in a seed of it; with the setting off, nothing of the user's build enters a run. In every other case nothing is seeded (`ShadowWorkspace.buildSeed.skipped` says why; the RunManager logs it): never a refusal, never a gate finding, only a slower first build. A symlink or special file in `.lake/build` only means no seed (nothing of it is copied; it no longer refuses the shadow). Before every Lean job `syncMirror()` copies changed model files (content compare, mtimes of unchanged files kept, removed files deleted) and refuses symlinks, special files and dot-entries in ws/. Files in ws/ that are not model files (a stray `notes.md`) never reach build/; `currentFiles()` still returns them so G0 can report them (counted: `outside-subject` at the root of ws/ or anywhere else outside the subject, `bad-path` inside the subject's folder; section 3.1). Lean runs there with M1's in-place refresh (`semantic.refreshLeanFacts({ root: build, … })`: sources read-only, `.lake` writable) and M0's `freezeChallenge`/`runComparator`; facts are root-relative, so their paths are ws/ paths. No sandbox or runLean change is needed.
- **git/**: `GIT_DIR` of the shadow's history (work tree ws/), isolated config; commits `base`, `freeze`, `adopt`, `normalise`, `gate-pass`, `revert`, `accept-base`, `rebase`, `checkpoint`.
- **session/**: the CLI's run dir (confinement files, MCP config with the bearer token, system prompt) and `transcript.jsonl` (every user turn verbatim, every event, tool call and result, state change, with timestamps: "exact texts saved", 03 section 14).
- **Pruning**: after a run ends, keep the newest 10 run dirs of the root (`telelean.run.keepRuns`), never deleting a non-terminal one.

### 4.3 The tool host (WP3 `RunToolHost implements AgentToolHost`)

| Tool | Allowed in | Counts | Behaviour |

After the cap: tool error "check budget used up (25 of 25): call finish" |

### 4.4 Caps, the clock and usage (WP3)

- **Turns**: one per `usage` event (API response, deduplicated by message id: M0 `UsageTracker`); at `maxTurns` the manager interrupts the session; also passes `maxTurns` as the CLI's per-user-turn `--max-turns` (belt and braces).
- **Checks**: counted by the tool host (section 4.3).
- **Agent-active time**: a stopwatch running in `working` and `gate`, paused in `waiting-for-answer`, `review`, `interrupted`; at `maxAgentMs` the manager interrupts. Uses `services.now` so tests use fake timers.
- **Caps during a tool call**: a turn or time cap reached while a check, freeze, ghost check or gate runs takes effect when that call returns; its result is honoured (section 2).
- **Lean job**: `leanJobMs` passed to every runLean job (build, check file, export, comparator).
- **Per round**: Feedback and adoption reset the counters (D-25's caps bound one stretch of agent work; each round is user-initiated). Usage totals accumulate over the run.
- **Usage**: requests and token sums from `usage` events; `costEstimateUsd` = the latest `result`'s `total_cost_usd`, which the CLI reports cumulatively for the whole conversation, including what came before a `--resume` (M0 smoke-test note), so it is never summed across processes; the latest `rate_limit` event condensed to `{status, resetsAt?}`. The board labels the cost "estimate at API list prices; your subscription is not billed per token".

### 4.5 Building the proposal (WP4 `ProposalService.build`; called by WP3)

From the check of exactly the shown shadow state: the proposed subject graph (core `buildProjectModel` over ws/'s parsed files + the mirror's facts → `subjectGraph`, `version` = any number), `diffGraphs(current board, proposed)`, changed files with line counts (`diff` 9.0.0), review items (one `StatementReview` per statement abbrev that is new or changed vs B, with the sentence, `engine.renderStatements` pretty/explicit, closure from `lean.uses` with glosses; one `VocabularyReview` listing new pure-signature items), definition questions (flagged definitions, ids `d1…`), lifecycle items (a proved GOAL target → `{change-kind GOAL→DERIVATION, recommended:true, reason:"Lean proved it from the selected premises"}`, id `l1`), ghosts, the report card (verdict, footprint from the proposed target's `ProofStatus`, unused premises, self-evident, consistency unchecked, Claude's summary/gap/conflict/assumed-without-asking, gate attempts, usage, durations, `reverted`), `baseChanged` (= drift ≠ ∅), `empty` (no changed file). The proposal is persisted in run.json.

### 4.6 Persistence and recovery (WP3)

`run.json` (`PersistedRun`) is rewritten atomically after every state change. On `recover()` (the extension calls it when a root's workspace is created) the newest run of the root whose state is non-terminal is loaded (any older non-terminal run, left by a crash, is marked `failed` with "superseded by a newer run" and its session id dropped): `waiting-for-answer` and `review` come back as they were (the question card, the proposal); `working`/`gate`/`starting` become `interrupted` with `canResume` when a session id exists (else `failed`). Answering a restored question starts a resumed session (`resumeSessionId`) and sends `renderAnswersAsUserTurn(args, answers)` (M0, verified live in the smoke test). "Resume" on an interrupted run sends the resume turn (section 5.3). On `dispose()` (window closing) an active run is persisted as `interrupted` (or kept as `waiting-for-answer`/`review`) and its session closed.

### 4.7 Cancel

`cancel(runId)`: interrupt the session (control `interrupt`), `lean.cancelRun(runId)` (kills every `telelean-<runId>-*` scope), reject pending tool calls, close the session (force after the grace period), state `cancelled`, attempt recorded (verdict `cancelled`). No proposal; the shadow and transcript stay until pruned.

### 4.8 Feedback

Only in `review`. Round+1; caps reset; stage `formalise` (the agent may change statements; a new freeze is required before `finish(proved)`, and `proof-before-freeze` counts only theorems added or changed since the round's start commit, so the previous round's proof does not block); the previous proposal is withdrawn (`proposal` null) and the attempt resolved `superseded`; the session is resumed if it was closed; the feedback turn (section 5.3) is sent.

### 4.9 Ghost adoption ("I hold this")

Only in `review`, for a ghost in state `suggested`. (1) core `planGhostAdoption` (block + docstring + abbrev + `.holds` axiom before T's block; `worded_by: agent`, `origin: agent`, `session: <runId>`, `asserted: today`, the user's optional rationale; the statement is exactly the checked, collapsed text, and the plan is refused when `ghostTextProblems` or `scanForbidden` finds anything in what it would write; fixer round 1: the new card's id is appended to T's `premises:` in the same change, so the adopted premise joins the declared selection and the accepted proof shows no TL107; G5 accepts exactly that line, held to A) → `shadow.writeFiles` → commit `adopt` (A, the reference the rules hold the ghost's block and declarations to from then on). (2) `engine.freeze` with the ghost's node id added to `selection.adoptedGhosts`; a refusal reverts to the pre-adoption commit and shows the reason (stays in review). (3) Round+1, caps reset, stage `prove`, ghost state `adopted` (`nodeId` set), the adoption turn (section 5.3) is sent. The ghost's text enters the user's files only if the user later accepts the proposal, and stays marked as Claude's wording (`worded_by: agent`, italic on the board) until the user edits it.

### 5.1 The system prompt (static; WP3 `buildSystemPrompt` returns exactly this text, ending with one newline)

```
You are the formalisation assistant of telelean. In telelean a person keeps their mental model as cards: ASSUMPTIONS (what they hold), DERIVATIONS (what follows) and GOALS (what they want to know follows). Each card is a Lean 4 comment block starting with `@@ telelean`; its `natural_name` is their sentence. A formalised card has `abbrev <name> : Prop := <statement>` directly below its block; an assumption also has `axiom <name>.holds : <name>`, and a proved card has `theorem <name>.holds : <name> := <proof>`.

Your working directory is a private copy of their Lean project. Nothing you write reaches their files unless they accept it after reviewing it.

Your task in this run: decide whether the TARGET card follows from exactly the SELECTED premises, by formalising faithfully and proving in Lean. The first message lists the target, the selection, the other cards of the subject, the vocabulary and the person's earlier answers, and names the subject's folder (normally Model/<Subject>/).

Workflow
1. Read the files you need, in the subject's folder.
2. If a sentence can be read in ways that change the result (modality, genericity, strength of a negation, scope, word sense, vagueness, presupposition), ask with ask_user before formalising. Do not ask about differences that do not matter.
3. Formalise the target if it has no Lean yet, and every selected ASSUMPTION that has none (cards typed on the board sit in the subject's Inbox.lean: formalise them there). Directly below its block, with no blank line in between, write:
   /-- <the card's sentence> -/
   abbrev <snake_case_name> : Prop := <statement>
   axiom <snake_case_name>.holds : <snake_case_name>     (assumptions only)
   telelean then adds the `lean:` pin to the block and keeps the docstring equal to the sentence. New vocabulary goes into the subject's Vocabulary.lean, inside `namespace <Subject>`. A selected GOAL or DERIVATION premise without Lean may be formalised the same way (no `.holds` axiom) and proved after the freeze.
4. Call check_lean until the files build without violations, then call freeze_statements with the target's id.
5. Prove `theorem <target>.holds : <target> := …` right after the target's statement (or lower in the file, below everything it uses), using only the selected premises' `.holds` and lemmas you prove. Call check_lean.
6. Call finish. If the target does not follow, finish with status not_proved, remove any proof of the target, and say in `gap` what is missing; before that, if a premise the person might plausibly hold would close the gap, propose it with propose_assumption, with a proof that it closes the gap. A suggested premise is one Lean proposition on one line and may use only vocabulary that already exists.
7. After finish has passed (or told you to stop), stop: later edits are discarded.

Rules (a program checks them after finish; failures come back to you)
- Their words are the specification. Never change any field of a block (including `lean:` lines), never add or delete blocks, never change a declaration that existed before the run (except the target's `.holds`), and formalise no card other than the target and the selected premises.
- Vocabulary may only be: sorts `axiom T : Type`; propositions `axiom P : Prop`; predicates and relations `axiom P : T₁ → … → Prop` over sorts; constants `noncomputable opaque c : T`, where T needs `axiom T.exists : Nonempty T` and `instance : Nonempty T := T.exists`; functions `noncomputable opaque f : T₁ → T₂`. The person confirms each new `T.exists`. Any other `def`, `structure`, `inductive` or `instance` is shown to the person as a question: avoid them, and never encode a belief in a definition.
- Besides vocabulary, the only axioms you may add are the `.holds` of selected ASSUMPTION cards you formalise. A missing premise is proposed with propose_assumption, never written into the files. Everything you add may rest only on the selected premises: every theorem and lemma, and every definition, instance and structure (a field's default value too).
- Forbidden in what you write: sorry and admit; example (it has no name, so nothing can check it: use #check or a named lemma); any # command except #check and #print; set_option; macro, syntax, notation, infix, elab, initialize, run_cmd and other metaprogramming; native_decide, decide +native, bv_decide, implemented_by, extern; unsafe and partial; imports from outside the project; changes to lakefile, lean-toolchain or lake-manifest.json; files other than .lean files of the subject's folder, except importing a new module of the subject in the subject's root module (Model/<Subject>.lean).
- After freeze_statements, do not change the frozen statements or the vocabulary. Proofs are rejected before the freeze.
- Lean 4 core only, no Mathlib: simp, omega, decide, grind and exact? are available. autoImplicit is off. Stay in the subject's namespace.
- In finish, list every interpretive choice you made without asking in assumed_without_asking ([] if none).
- Be brief: the person reads your messages next to the Lean.

### 5.2 The context bundle (round 1's user turn; WP3 `buildContextBundle`)

Template (sentences, rationales and Lean verbatim; one card per bullet; line numbers 1-based; empty sections say "(none)"). `telelean.run.contextScope = neighbourhood` lists under OTHER CARDS only cards whose statement the target or a premise mentions.

```

## 7. Accept: the shadow's diff onto the real files, through M1's edit and history machinery

### 7.1 Steps (WP3 orchestrates; WP4 plans and applies; WP2 re-checks)

1. **Preconditions**: state `review`; `proposalId` is the current proposal; every `DefinitionQuestion` id is in `definitions` (else `invalid`: "answer every definition question: a “no” is feedback"); lifecycle ids exist.
2. **Drift**: `proposals.baseDrift(shadow, ws.readText, ws.modelFiles())` = model files whose real text (open buffer first) differs from the base, including files the user added or deleted during the run.
3. **Plan**: `proposals.planAccept` → for every model file: base→shown patch (`diff` 9.0.0 `structuredPatch`, default 3 context lines) applied to the real text with no fuzz (`applyPatch`), exactly M1's undo technique; a patch that does not apply → `conflict` naming the file ("your edits to <file> since the run started overlap Claude's; Discard, or undo those edits and Accept again"; turn 13: it used to offer Feedback, which continues on the working copy and meets the same conflict). Because of the context lines, an edit of the user's within 3 lines of a change of Claude's counts as overlapping. Turn 13: when that patch cannot be placed, the board's own edits made during the run (cards added at the end of a namespace with add-node; rationales written or changed) are taken out of the real text, the patch is applied to the rest, and they are put back by card id (runner `proposal/files.ts` `boardEditsOf`); every other edit within 3 lines is still a conflict. Files only the user changed keep the user's text. Then the ticked lifecycle items (core `lifecycleChanges`: G→D changes only `type:`).
4. **Re-check on drift (D-21)**: when drift ≠ ∅: remember the current head (the shown state); write the user's real model files into ws/ and commit `accept-base`; write `shadowState` (merged, without lifecycle items) and commit `rebase`; run `engine.normalise`, `engine.freeze` and `engine.gate` (with the round's status) with `baseCommit` = the `accept-base` commit (so B = the user's files at Accept: their own edits during the run are never judged as Claude's) and `roundStartCommit` = the `rebase` commit (the existing proof is not "a proof before the freeze"). The freeze copy drops the target's `.holds` and every declaration that uses it, transitively from the facts' refs (other cards' proofs included), so the challenge `theorem T.holds : T := sorry` neither clashes nor breaks a dependent (the same rule serves a pending-promotion target whose claimed `.holds` other proofs use). A failure restores ws/ to the remembered head, refuses Accept with the findings (core `describeFinding`), and leaves the proposal open (Feedback can redo it). On success `planAccept` runs again with `shownState` = ws/ as re-gated, so exactly the re-gated files (plus the ticked lifecycle items) are applied.
5. **Apply**: `proposals.apply(plan, workspace, subject)` → `ModelWorkspace.applyChanges({ label, action: 'accept-proposal', subject, nodes, changes })`, which uses M1's recorded write path unchanged (`applyRecorded`): **"Manual edits" / "Initial state" snapshots of the touched scopes first** (private refs, D-33/A3), then the EditApplier (the extension: WorkspaceEdit + save; its `before` check refuses if a file changed between plan and apply → `conflict`, nothing applied), then the undo entry (one entry for the whole proposal: **Undo reverts the Accept**), then the action's snapshot (history entry "These suffice → proved: Cynder would not be a good addition…"), re-read, graph.json, a Lean refresh of the real files.
6. **Afterwards**: attempt resolution `accepted`, session closed, state `accepted`, `proposal` null; the board's next refresh shows the real statuses (e.g. cynder-not-good proved, in the Derivations column).

### 7.2 What Accept never does

It never writes a file outside the subject's scope and the project's model files, never applies part of a proposal, never applies a lifecycle item the user did not tick, never runs while the real files conflict, and never skips the snapshot-first step (a revert of the Accept through History is possible as for any M1 action).

### 7.3 Sidecars (WP4 store; formats core `run.ts`; paths core `paths.ts`)

- `.telelean/subjects/<S>/attempts.jsonl`: one `AttemptRecord` per round end (verdict, premises, footprint, ghosts, Claude's summary cut to 500 characters, gate attempts, model, effort, usage), plus `AttemptResolution` lines (`accepted`/`discarded`/`superseded`). Append-only (`O_APPEND`), never undone, not in history snapshots (M1's `isSubjectSidecarFile` still covers only layout.json and attic/), not gitignored (D-12: committed by the user's own commits). `ModelWorkspace.reloadAttempts(S)` re-reads it; `graph(S).attempts` lists them newest first.
- `.telelean/subjects/<S>/decisions.json`: one `DecisionRecord` per answered question, written when the user answers (atomic replace inside `.telelean/`), same storage rules. Decisions with scope `subject` (and `nodes` meeting the selection) are "in force" for later runs (context bundle); revoking them is M3.

### 12.1 The script (built by WP3)

`node scripts/walkthrough-claude.mjs [--dry-run] [--live] [--reading normative|literal|both] [--model claude-opus-5-5] [--effort high] [--work-dir DIR] [--max-turns 80] [--max-checks 25] [--max-agent-minutes 20] [--binary PATH] [--approve-definitions]`. It bundles the runner into the work dir, copies `mental_model/` to `<work>/model-<reading>/`, initialises git there (isolated config), runs one Lean refresh, and drives the RunManager like a user: answers a question whose phenomenon is `modality` or whose text mentions "cannot" with free text (normative: "I mean it as a rule: PG games should not include characters with dark pasts. I do not mean it is impossible for a PG game to contain one."; literal: "I mean it literally: a PG game cannot contain a character with a dark past at all."), answers any other question with "Decide for me", adopts the first ghost with `closesGap` in the literal reading, accepts proved proposals with the recommended lifecycle items (definition questions only with `--approve-definitions`; otherwise it stops and reports them), then refreshes the copy and records the final statuses. Live = ClaudeCliBackend, only with `--live` and `TELELEAN_WALKTHROUGH_LIVE=yes` (either alone refuses before any binary is resolved). The live run stops (cancels) at the first `rate_limit` event whose status is not `allowed`.

1. Record, per reading: `summary.json` (verdict per round, gate attempts with failures, notices, questions asked and the answers given, ghosts, flagged definitions, the final diff of the copy, final statuses), `transcript.jsonl`, usage (requests, input / output / cache-read / cache-write tokens, the CLI's cost estimate, rate-limit events), durations (wall, agent-active), CLI and model versions, the guard log (denials, if any). ## 15. Decisions log

### 15.1 Minor decisions taken (for the user to review later)

1. **The agent's root holds only model files; Lean builds in a separate mirror** (`ws/` vs `build/`), synced before every Lean job. No sandbox change was needed, and Grep/Glob work on the whole root (m0-report lesson 4).
2. **The shadow's git lives outside the agent's root** (`git/` with work tree `ws/`), with an isolated git config.
3. **Every model file of the project goes into the shadow** (all subjects), so cross-subject imports build; the context bundle covers only the run's subject. Claude can read the other subjects' files.
4. **"These suffice" first declares the selected premises (M1's undoable `set-premises`, D-13), then starts the run.** "Self-evident?" declares nothing. (Reviewer: the RunManager makes the declaration itself, only after preflight passed, so a refused start changes nothing in the user's files.)
5. **Targets must be GOAL or DERIVATION cards**; an ASSUMPTION is made a Derivation first (D-11), and a pending derivation's axiom `.holds` may be replaced by the proof (D-11 promotion).
6. **Caps and gate attempts are per round** (first run, each Feedback, each adoption), so a Feedback round is not starved by the first; usage is shown for the whole run.
7. **telelean normalises before every gate**: it pins `lean:`, writes derived ids and sets docstrings to the sentence; the agent never edits blocks.
8. **G3 also refuses changes to declarations that existed before the run** (except the target's `.holds`): a cheap textual stand-in for H's formal immutability; it catches "existing vocabulary turned into a definition", whose footprint looks clean (section 0, fact 6).
9. **The permitted set's signature = every non-Prop axiom of the project's modules**; new ones must already pass the shape rule before the freeze. *(Superseded by fixer round 1: the signature is vocabulary of kind sort, predicate, function or constant, and never a declaration bound to a card; see section 3.2 and `docs/decisions-log.md` section 27.)*
10. **Lemmas may not rest on unselected assumptions either** (not only the target's proof). *(Fixer round 2: nor may any other declaration Claude adds, such as a definition, instance or structure that carries a proof; section 3.3 `footprint`, `docs/decisions-log.md` section 28.)*
11. **`propose_assumption` carries the gap proof** (`proof`, a term `statement → target`) and an optional `lean_name`; telelean checks it in a scratch module, never in the agent's files.
12. **Ghosts can be adopted only in review** (after the round's turn ended); adoption is a new round that starts frozen.
13. **Environment failures (sandbox, low memory) are not counted** as attempts or checks; in the gate telelean retries once after 30 s, and a second one ends the run as failed with the reason (reviewer: the retry keeps a transient memory dip from costing the round's work).
14. **A turn that ends without `finish` gets one nudge**, then the round ends as `no-finish` (reverted to the last passing state, normalised and re-checked).
15. **"Insufficient" and "inconsistent" are shown as "not proved" / "Claude reports a conflict (unverified until M3)"** (D-6).
16. **A not-proved round can still be accepted** (its statements and vocabulary), labelled "These suffice → not proved: …".
17. **Every definition question needs an explicit "yes" before Accept**; a "no" is Feedback.
18. **Accept rebases onto the user's current files with M1's no-fuzz patches, re-freezes and re-gates when the files drifted**, and refuses overlapping edits (D-21).
19. **One Accept = one history entry and one Undo step** (`accept-proposal`), snapshot first (A3).
20. **attempts.jsonl and decisions.json are written directly, never undone, not in history snapshots** (they are logs of what happened and what the user answered), and are committed with the user's own commits (D-12).
21. **Claude's guesses never reach the webview before the answer** (D-20), not just hidden by the UI.
22. **The system prompt is static and byte-identical across runs** (prompt caching); everything project-specific is in the first user turn.
23. **Egress consent is asked once per model folder** (D-23 egress), naming exactly what is sent.
24. **At most one active run per model root**; a run continues when its board closes (D-25).
25. **The CLI runs under `setpriv --pdeathsig KILL`** so a crashed extension host takes it down.
26. **Run ids double as runLean scope groups**, so Cancel kills every Lean job of the run with one `systemctl --user kill`.
27. **`AcceptProposalAction` stays a separate type until integration** (the webview's history label table is exhaustive); the integrator merges it.
28. **The ModelWorkspace's M2 members are optional in the type until integration** (the M1 test fakes keep compiling).
29. **The live walkthrough is driven by a script with a scripted user** (free-text answers per reading, adopt the first gap-closing ghost), dry-run by default and live only with a flag plus an environment variable.

Added by the reviewer (same turn):

30. **A "not proved" round is checked too**: every theorem it adds must rest only on the selected premises, and it may not leave a proof of the target in the files (`status-mismatch`): Claude then either claims `proved` (freeze + comparator) or removes the proof. Otherwise an unchecked proof resting on an unselected belief could reach the user's files through "Accept (not proved)". *(Fixer round 2: every declaration it adds, not only its theorems; section 3.3 `footprint`.)*

37. **Sidecars are per subject**: `.telelean/subjects/<S>/attempts.jsonl` and `.telelean/subjects/<S>/decisions.json`, next to M1's `layout.json`, rather than D-12's single `.telelean/attempts.jsonl` / `.telelean/decisions.json`; still committed with the user's own commits.
38. **The cost estimate shown is the CLI's latest figure**, which already covers the whole conversation across `--resume` (M0), never a sum.
39. **A cap reached while a tool call runs takes effect when the call returns**, so a passing gate is never thrown away by a cap hit during its Lean job.
40. **Runner factories take `core` test hooks** (as M1's workspace did), so the six work packages can each test their own logic while the others are still stubs; cross-package tests are marked [gated] and run at integration.
41. **A run starts only on files that build**: right after the shadow is made, telelean builds the user's files once; Lean errors anywhere end the run before Claude is contacted ("fix or save them, then start again"). The same build lets the gate check that the user's declarations still mean what they meant.
42. **An honest "could not formalise" is allowed**: the readiness rules (target and selected assumptions formalised, `.holds` present) apply to the freeze and to `finish(proved)`, not to a `not_proved` finish.
