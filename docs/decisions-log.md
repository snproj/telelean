## 2. Markup reading and writing

- **Strict D-2(b): a block bound to anything but `abbrev n : Prop := …` is flagged TL113 (ill-formed).** telelean reads and writes only the approved form; guessing would make statuses unreliable. *(plan)*
- **An adjacent binding is pinned (`lean:` written) on the next telelean edit of its block.** D-8: once formalised, inserted declarations must not rebind a card. *(plan)*
- **The host always derives new ids itself (`deriveId`, `n-<hex>` for non-Latin text).** The webview's provisional id only matches its own optimistic card. *(plan)*
- **The lexer follows Lean 4.35: the comment nesting scan starts after the third character, and Lean skips whitespace and comments right after `/--` and `/-!`.** Verified with probes; the research prototype got both wrong. *(WP1)*
- **`escapeBodyText` also writes a leading `--` as `\--`.** Otherwise a docstring starting with `--` would swallow the rest of the file (found by a probe). *(WP1)*
- **`escapeJsonValue` also escapes U+2028/U+2029 and C1 control characters.** Editors treat them as line breaks; the property test caught a parse failure. *(WP1)*
- **Lexer details: interpolated strings skip `{…}`, `'\''` is one char literal, an unterminated `«` is a symbol, CRLF spans exclude the `\r`.** Closer to Lean's tokenizer and robust in broken files. *(WP1)*
- **Command starts = the plan's column-0 list plus indented declaration headers, `deriving instance` and a few missing commands.** Otherwise `deriving Repr` would be cut off its inductive and indented declarations would be invisible. *(WP1; the comment rule changed, see section 10)*
- **A `mutual` block runs to its matching `end`; `|` counts as a value start only at a line start or in an inductive.** Avoids namespace corruption and false value starts on `|x|`. *(WP1)*
- **A docstring attaches across blank lines and plain comments (also across telelean blocks), as in Lean.** `set-docstring` then replaces the docstring Lean really uses. *(WP1)*
- **`fullName` drops unnecessary `«»` and honours `_root_.`; attributes keep their raw `@[…]` text.** Names then match Lean's output and the `.ilean` files. *(WP1)*
- **Binding details: an adjacent anonymous instance, `example` or `mutual` gives no binding (TL014); TL013 only for a named declaration after a blank line.** WP2 never sees an adjacent binding without a statement name. *(WP1)*
- **An invalid written id stays the node id with a TL004 error; invalid enum values are dropped with TL004; list items may be JSON strings.** Card identity stays stable while you fix typos; no error cascades. *(WP1)*
- **Block-level diagnostics sit on the marker line; TL010 is reported for any unterminated comment.** Quieter squiggles, and an explanation when blocks vanish. *(WP1)*
- **The serializer writes an empty value as `""`, known extra keys take their standard place, `kind` in extras is dropped.** Every rendered block re-parses exactly. *(WP1)*
- **`deriveId` transliterates a few letters (ß→ss, æ→ae, ø→o, ł→l) before NFKD; fallback `n-` + 6 hex digits of FNV-1a.** Better slugs for Latin text; deterministic. *(WP1)*
- **Field edits replace only the value span, keep indentation and a written `kind:`, and remove at most one blank line.** Minimal, byte-stable diffs. *(WP1)*
- **`applyLeanOps` refuses rather than guesses** (removing a declaration that contains a telelean block, adding a `.holds` that exists, overlapping operations, …). All or nothing, never a corrupted file. *(WP1)*
- **`lineIndex` treats only `\n` as a line break; a file keeps its own line endings.** Same lines as Lean; CRLF files stay CRLF. *(WP1)*

## 3. Checking with Lean

- **The refresh builds in place in the model folder (sources read-only, `.lake` writable, `.git` masked), not in a shadow copy.** As 03 §8.4 specifies; a shadow is the fallback if races with your Lean server ever bite (R2). *(plan)*
- **Per-card "uses:", hover glosses and click targets come from Lake's `.ilean` files; kinds, types, footprints and `sorry` from a generated check file.** No compiled tool needed in M1; the toolchain is pinned. *(plan)*
- **Hidden assumptions are recognised by Lean's own sort check (`#check type_of%` = `Prop`).** Guessing from the type text cannot tell them from vocabulary. *(plan)*
- **The build runs `lake build <library>` (e.g. `lake build Model`), not a bare `lake build`.** It builds exactly the library being checked, whatever `defaultTargets` says. *(WP3)*
- **The `type_of%` probe runs for every declaration; an error there counts only for axioms and opaques.** The kind is not known beforehand; the extra cost is trivial. *(WP3)*
- **`value` is recorded for `def`s and instances only (whitespace normalised); empty attribute lists are omitted.** Helps recognise presupposition instances; keeps facts compact. *(WP3)*
- **Modules that change during a refresh keep their facts (marked stale).** Core uses a stale file's facts by name, so statuses do not flicker. *(WP3)*
- **Sandbox failures (could-not-start, timeout, out of memory, cancelled) return no facts; the workspace keeps the previous ones.** "No facts" is unambiguous, and the board keeps its last known statuses. *(WP3, WP4)*
- **If the build fails without naming a module (e.g. a lakefile error), only modules reported as built count as fresh.** Older artifacts may not match the sources: no data rather than wrong data. *(WP3)*
- **A missing import, an import cycle or an import of a failed module makes the importer dependency-failed.** Lake lists dependents only for bad imports. *(WP3)*
- **The project check also requires a lakefile; an unparsable manifest is "unsupported project".** Lake would fail anyway; this gives a clear reason. *(WP3)*
- **`.git` is masked only when it is a directory (a worktree's `.git` file is left alone).** bwrap can only cover a directory. *(WP3)*
- **A missing root is "could not start"; an unreadable MemAvailable lets the refresh proceed (the memory cap still applies).** None of these are Lean failures and the refresh must never throw. *(WP3)*
- **Facts list modules in import order and declarations in source order; structure fields and constructors get their own facts with a `parent`.** Deterministic, and field glosses work. *(WP3)*
- **Recorded real Lean facts for the Spyro fixture and an "extras" overlay are kept as test fixtures and re-checked on every run.** They are the reference for the hand-written facts (the integrator's test confirms both agree). *(WP3, int)*
- **The Lean error count = build errors + declarations whose probe failed.** Otherwise "check failed" could show 0 errors. *(WP4)*
- **After an action, a Lean refresh is requested only when a `.lean` file changed** (layout and attic changes skip it). Saves pointless builds. *(WP4)*
- **TL110 (`autoImplicit` on) is computed from the lakefile and shown on every board: on unless `autoImplicit = false` is set (comments ignored).** With it on, a typo in a statement silently becomes a variable; no TOML parser is installed, so a small reader handles the scaffold's form. *(int)*

## 4. Statuses, arrows and vocabulary

- **Declared-vs-verified mismatches are judged at the assumption level, and only for proved or conditional cards.** A proof through a derivation of the declared premises is fine; an unproved goal's premises are never "unused". *(plan)*

- **"uses:" = the vocabulary in the statement's closure (through other cards' statements and definitions), first occurrence first; sorts only where written.** What the statement really talks about, without repeating every sort. *(plan)*

- **Blocks outside any subject (TL120) and later duplicates of a written id (TL006) are not cards; with TL017 the first block owns the declaration.** A card needs a subject and a unique id. *(WP2)*
- **A board shows its own subject's vocabulary and diagnostics, plus project-level problems; an unknown subject gives an empty board.** Project problems stay visible; no crash when a subject disappears. *(WP2)*

## 6. Undo and history

- **One history chain per subject (`refs/telelean/<rootKey>/subjects/<S>`) plus a project chain, written with git plumbing only.** Revert touches one subject; your branches, index and hooks are never touched. *(plan)*
- **Re-ordering alone is undoable but not snapshotted; it rides along with the next snapshot (also a hand edit of layout.json alone).** Layout carries no meaning, and an entry per drag would flood the history. *(plan, WP4)*
- **"Keep last N" does not run `git gc`.** gc on your repository is invasive; the counter drops at once, the disk space returns at git's next housekeeping. *(plan)*
- **A model workspace lives until the window closes.** Undo survives closing and reopening the board; Lean still runs only while a board is open. *(plan)*
- **A "Manual edits" snapshot is labelled "Initial state" when the subject has no chain yet** (e.g. you ran `git init` yourself after opening the board). There is no base to call them hand edits against. *(WP4)*
- **Undo outcomes offer no Undo button; redo and revert outcomes do.** An Undo on an undo's toast would undo the next older action; Redo is the way back. *(WP4, WP5)*
- **Undo and Redo both apply the top entry backwards, exactly or by a no-fuzz reverse patch; a file already in the target state is a no-op.** One algorithm for both directions; all or nothing. *(WP4)*
- **History preview: "parent" shows what the entry changed, "current" what changed since the entry (older left, newer right).** The plan left the direction open. *(WP4)*
- **The history list shows 50 entries (up to 1000); listing failures show as a TL202 warning and an empty list.** The board can always render something, and errors still surface. *(WP4)*
- **A failing snapshot never fails the action** (it is applied and undoable; TL202 is shown). "Actions still work without history." *(WP4; a revert is the exception since the fixes, see section 10)*
- **TL201/TL202 are appended to every board and to graph.json; TL201 has no file.** They concern the project. *(WP4)*
- **"Initialize git" inside an existing repository just starts the histories.** The button can race a `git init` done outside telelean. *(WP4)*
- **Reverting when nothing differs says "Nothing to revert" and takes no snapshot; a tree path that is not a plain relative path is refused.** No empty entries; a cheap integrity guard. *(WP4)*
- **A snapshot's ref update retries once if another window moved the tip; snapshot temp files go to a private temp directory** (since the fixes: inside the git directory, see section 10). Concurrency safety without touching your index. *(WP4)*
- **git is started without a stdin pipe unless telelean sends it input.** Otherwise VS Code's extension host logs "Unexpected SIGPIPE" when git exits first (harmless, but noise in your logs). *(int)*
- **Graph versions come from one process-wide counter seeded from the clock.** Strictly increasing across subjects and re-created workspaces. *(WP4)*
- **An undo entry is never recorded under an empty subject name** (a new subject's creation is undone from its own board). A board undoes on its own subject's stack. *(int)*
- **"Revert to this" is offered for every entry, including the newest.** Reverting to the newest discards unsnapshotted hand edits, which are snapshotted first, so it stays undoable. *(WP6)*

## 10. Fixes after the verification (core, runner, sample, docs)

- **A column-0 comment ends the declaration above it only when the next code after it starts a command (or there is none).** Lean treats comments as whitespace: a `--` or `/- -/` at column 0 inside a tactic proof or a multi-line statement, followed by more indented code, belongs to the declaration. The old rule cut such declarations in half, so D→A, A→G and delete broke files that compiled. *(fix)*
- **Two extra guards against cutting a declaration: `applyLeanOps` refuses when the line after a span is an indented continuation, and the planner refuses when Lean's own range of a freshly checked declaration ends after the span.** Defence in depth: a refusal ("edit it by hand") is always better than a half-removed proof. *(fix)*
- **Neighbouring declarations removed together are deleted in one piece.** One blank line stays where they were, not two. *(fix)*
- **Delete with its Lean asks first when other declarations would stop compiling, listing them (cards, then lemmas without a card and other subjects' proofs); the board resends with `confirmed: true`.** D-18 asks for a confirmation listing the dependents; the board alone sees only this subject's arrows. *(fix; the board's half, "Delete anyway", was added in the closing round, section 12)*
- **D→A / G→A on a proof that takes hypotheses asks first; "rewrite" drops the arguments (`(n.holds h)` becomes `n.holds`), "mark broken" leaves them.** The axiom states `n` directly; the drop zone used to promise the proofs "stay valid" while they broke. Only direct users change (their own types do not). *(fix)*
- **A→G / D→G "rewrite" of a proof that takes hypotheses replaces each whole application `(n.holds h …)` by the new hypothesis `h_n : n`.** The user then rests on `n` and keeps its other hypotheses; replacing only the name gave `(h_n h)`, which does not compile. *(fix)*
- **The mechanical rewrite only touches applications in parentheses with plain identifiers as arguments (`(n.holds h)`, `((n.holds a) b)`); anything else is refused with "choose mark broken".** Recognising every way to apply a function is not worth the risk; the refusal names the place. *(fix)*
- **Lean's double references (`@c` with and without the `@`, `(c)` with and without its parentheses) are merged to one span per identifier, and a leading `@` is accepted.** Found with real `.ilean` files; the rewrite refused these harmless forms before. *(fix)*
- **While files are not freshly checked, a use counts when its name resolves through the declaration's namespaces or any namespace `open`ed earlier in the file, or when it ends with two or more components of the target (`cynder_dark_past.holds`).** Generous on purpose: one question too many is harmless, one missed use removes a `.holds` others use. *(fix)*
- **"Self-evident" requires no card and no hidden axiom in the footprint.** A proof resting on an unmarked axiom (TL103/TL104) is not proved from nothing. *(fix)*
- **A plan never changes another card's binding: a comment-only card left directly above a declaration gets a blank line after it; any other change is refused.** Deleting the card below it used to make it silently bind to that declaration. *(fix)*
- **Editing a field that a block repeats (TL005) changes only the first line and keeps the others; removing such a field is refused.** The later lines are text you typed; deleting them silently, or promoting a hidden one, would surprise. *(fix)*
- **A board lists the vocabulary items of other subjects that its cards use, read-only, under their full names.** Hover glosses and click-to-highlight then work for explicit imports (D-10). *(fix)*

Any write, create, delete or rename changes a file's or its folder's change time, and on Linux 6.13 and newer (this machine runs 6.17 with ext4) a change made after telelean looked always gets a new change time, so a tree that anything touched after the record, or while it was copied, is never used. What another program wrote while the refresh itself ran is part of the record, though, and the checks cannot tell a module built from another version of your files from the others (section 31); Lake's own check of every module against the run's files keeps the result right. Chosen over a better check of the live tree because the record leaves only the refresh itself as a window: anything written after it rules the copy out, and a run never copies while telelean's own refresh is writing; kept rather than removed because a larger model may take much longer than Spyro to build from scratch, and recording costs one small walk of `.lake/build` per refresh. Anything else just means no copy (logged, never a refusal): a symlink inside `.lake/build` no longer refuses the run either, since nothing of it is copied. *(fix; corrected in section 31)*
- **A Lean job cancelled just as it starts no longer leaves an empty `telelean-*` unit behind in your systemd session.** Cancelling killed `systemd-run` while systemd was still creating the job's scope; systemd then moved the dying process into the new scope, the kernel skipped it, and the scope stayed "active" with no process until you logged out (or failed with "resources" and was never cleaned up), while `systemctl kill` cannot end an empty scope. Now the kill waits until the sandbox reports that it started (by then the scope exists and holds the job), at most 3 seconds, and a scope still there afterwards is stopped with `systemctl --user stop` and a failed one reset. A new test cancels 42 jobs 0 to 20 ms after their start and finds no unit left (the old code left one in that test). *(fix)*
- **The board tells "Accepted" from "Recorded" by the run's own record of the Accept (`accepted`), never by the wording of the runner's notice.** Every board, including one that did not send the Accept, now reads the same field, so the notice texts can change without breaking the run panel; the plan's change log marks that dependency as resolved. *(fix)*
- **A new VS Code end-to-end test presses "These suffice" while the board's Lean check is rebuilding `.lake/build` (forced: the board shows "checking" when the button is pressed), and the run proves as usual.** Users can do exactly this (the tray does not block the button while Lean checks); the other end-to-end tests still wait for idle Lean only so that their assertions see fresh facts. *(fix)*
- **The plan's description of the gate (section 3: G0, the permitted set, every rule, carriers, new axioms, examples) was checked line by line against the code and now says what the code does.** Corrections of the text (the code did not change): `run_tac` is refused with the other metaprogramming commands; any `native` token is refused, not only `+native`; a deleted model file is `deleted-file`, also outside the subject; the permitted signature also takes a non-Prop axiom of yours outside every subject's modules (the library root); a selected premise whose `.holds` does not state it, or whose proof has no axiom list, is unusable; a new `unmarked-axiom` (a belief) is `new-axiom`'s finding, not `vocabulary-shape`'s; `statement-changed` also catches a changed declaration kind; a comparator run that hits the time or memory limit is a counted `budget` finding; the ghost check passes its scratch file to Lean on standard input. *(fix)*

## 31. Closing fixes for M2, round 2 (docs, code comments and one new test)

- **The description of `telelean.run.reuseLeanBuild` no longer promises more than its record guarantees (section 30 corrected; nothing in telelean's behaviour changed).** The record is a listing of your `.lake/build` taken right after the board's refresh, so whatever another program (a terminal `lake build`, the Lean extension) finished writing while that refresh ran is part of it. The verifier of the first closing round wrote a second version of one module into `.lake/build` during 24 refreshes, the way Lake writes it (temporary name, then rename, its record last): every refresh was recorded, and 10 of the 14 copies runs then used held that module from the other version, 9 of them written during the refresh's check phase. The checks see which files exist and their times, not which version of your files a module was built from, so two complete versions look alike. Results stay right because Lake compares every module's record with the run's own files and rebuilds each module that does not match: the verifier built three such copies, Lake rebuilt the odd module, and every compiled file then equalled a clean build. The setting's description, the user guide, the plan (section 4.2) and the code comments now say what is true: a run copies what `.lake/build` held right after the board's last Lean check, untouched since, and Lake decides what it can reuse. One limit belongs to Lake itself: when a module's record matches, Lake does not re-read its compiled file, so two Lake builds writing the same module at the same moment (Lake 4.35 takes no lock) could leave a compiled file that Lake trusts wrongly, in your own `.lake/build` as in a copy of it; with the setting off (the default), nothing of your build enters a run. Kept as it is rather than adding a `lake build --no-build` check to every refresh, which would cost one more Lake process each time and still could not see that limit, or removing the setting. *(fix)*
- **The plan's section 3 now matches the gate's code in four more places (text only: the gate did not change, and none of these affected what it decides).** A stray file Claude writes at the root of its working copy (`notes.md`) or anywhere else outside the subject is "outside the subject" (`outside-subject`); only one inside the subject's folder is "bad path" (also corrected in section 16 and in the plan's sections 0.1, 4.2 and 15.1). `lakefile.lean` is never scanned for forbidden tokens: as a project file it only gets `project-file`. The per-module `build` finding (a module that failed without a Lean message) appears only when the build reported no error message at all, and the engine's fail-closed `build` findings are added only when the rules reported none (a new core test pins the per-module rule). The ghost's Lean name is chosen twice: when Claude suggests the premise (Claude's own name if it is a plain identifier, not a keyword, neither it nor its `.holds` is declared in the subject and no earlier suggestion of the run has it, else one made from the sentence's first six words) and again at adoption, which also refuses a name used as an identifier anywhere in the working copy's Lean files (or declared at the top level) and then derives one from the sentence, turning both `-` and `.` into `_`; the message that continues Claude's session after the adoption names the result. *(fix)*
