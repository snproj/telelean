## summary
The extension's VS Code suites now run inside the user's own snap VS Code (VS Code 1.145.2, Electron 43.8.3, /snap/code/278) through `npm run test:smoke:snap`, and they all pass. Two full snap runs each passed 40 smoke tests and 21 e2e tests, with no isolation failures. How the instance is started: through the snap's own electron-launch, with the SNAP_* variables `snap run` sets and the snap's per-user folders inside the isolated HOME. The extension host therefore gets exactly the variables the user's real window has: SNAP*, GTK_*, GDK_*, GIO_MODULE_DIR, GSETTINGS_SCHEMA_DIR, LOCPATH, FONTCONFIG_*, *_VSCODE_SNAP_ORIG, the snap-prefixed XDG_DATA_DIRS, and ELECTRON_RUN_AS_NODE=1. VS Code sets ELECTRON_RUN_AS_NODE itself.

No snap-specific failure in packages/extension needed fixing. I added a host-environment suite. It records what the extension host inherited and checks four things under that environment: the Lean sandbox, the Claude env sanitiser, the PreToolUse guard under ~/.local/bin/node, and the guard under the snap's Electron-as-Node fallback. I also fixed a harness leak: the agent's own CLAUDE_CODE_* session variables, including a messaging token, were reaching the test instances.

Static review of the real-backend path (binary resolution, env sanitising, consent, preflight) found nothing that breaks in the snap.

Key environment finding: this Ubuntu 24.04 machine has kernel.apparmor_restrict_unprivileged_userns=1. An unconfined bwrap fails with "setting up uid map: Permission denied". It works only because the snap VS Code's processes, and everything started from them, run as `snap.code.code (complain)`. So telelean's Lean sandbox works in the user's snap VS Code but would fail in a non-snap VS Code or from a plain terminal, and the preflight does not catch it today.

## problems_found
- Environment, important for the demo: bwrap only works here under an AppArmor label that allows user namespaces (kernel.apparmor_restrict_unprivileged_userns=1, Ubuntu 24.04.5). Unconfined, as in a transient systemd service, `bwrap --unshare-all` exits 1 with 'loopback: Failed RTM_NEWADDR: Operation not permitted' and 'setting up uid map: Permission denied'. Processes of the snap VS Code run as 'snap.code.code (complain)' in a snap.code.code-*.scope cgroup, and there bwrap works; this Claude session and everything it starts inherit that label. So the Lean sandbox works in the user's snap VS Code, but would fail in a non-snap VS Code or for scripts started from gnome-terminal or ssh. lean.checkSandboxSupport() does not detect this, so such a setup would fail only at the first Lean job.
- The snap extension host's environment (confirmed in the snap test instance; it matches the real window): ELECTRON_RUN_AS_NODE=1, ELECTRON_NO_ATTACH_CONSOLE, SNAP* (including SNAP_COOKIE/SNAP_CONTEXT), GTK_PATH/GTK_EXE_PREFIX/GTK_IM_MODULE_FILE/GTK_MODULES, GDK_PIXBUF_*, GIO_MODULE_DIR, GSETTINGS_SCHEMA_DIR, LOCPATH=/snap/code/278/usr/lib/locale (core20 locale data), FONTCONFIG_*, XDG_DATA_DIRS with snap folders first plus *_VSCODE_SNAP_ORIG, and XDG_RUNTIME_DIR=/run/user/1002 (not snap.code). Lean refresh, run checks, git history and systemd-run all work with this environment. sanitizeClaudeEnv removes every snap variable and leaves no path into /snap/code/278 (verified inside the snap host); it leaves only FONTCONFIG_PATH/FILE=/etc/fonts and the shell's `_`, both harmless.
- The snap's Electron binary uses ELF interpreter /snap/core20/current/lib64/ld-linux-x86-64.so.2. The hook runtime's Electron-as-Node fallback (/usr/bin/env ELECTRON_RUN_AS_NODE=1 /snap/code/278/usr/share/code/code) still passes the guard self-test with Claude's sanitised environment. In the snap the hook runtime actually chosen is /home/zhengyew/.local/bin/node.
- Test harness (fixed): the agent's own Claude Code session variables (CLAUDECODE, CLAUDE_CODE_SESSION_ID, CLAUDE_CODE_MESSAGING_SOCKET, CLAUDE_CODE_MESSAGING_TOKEN, …) were reaching the test instances' extension host in both modes.
- Snap VS Code 1.145.2 left one Chromium shared-memory file, /dev/shm/.org.chromium.Chromium.0dwpFI (256 KB, not open or mapped by any process), at the shutdown of a test instance in snap run 2. I removed it, and smoke.mjs now detects and removes such leftovers with a warning. It did not recur in the later runs.
- VS Code 1.145.2 prints an internal 'InstantiationService has been disposed' stack when the raw Lean diff (multi-diff) tab is closed. This is VS Code's own bug; the tests pass.
- Not covered by any test, so worth a line in the demo instructions: the extension declares untrustedWorkspaces.supported=false, and the test instances run with --disable-workspace-trust. In the user's VS Code a fresh folder must be trusted ('Yes, I trust the authors'), or telelean's commands are unavailable in Restricted Mode. The interactive Initialize path (QuickPick folder, input box for the subject, modal git offer) is only exercised with test arguments.
- Static review of the real backend in the snap found no breakage. Binary resolution looks in [dirname of the running Claude extension, ~/.vscode/extensions, ~/.vscode-server/extensions]; the classic snap uses the real HOME, so it finds ~/.vscode/extensions/anthropic.claude-code-2.1.322-linux-x64/resources/native-binary/claude (newest version; the window currently runs 2.1.319 until it reloads). `--version` runs with a minimal env {PATH, HOME} and does not depend on the snap's PATH. Consent is a globalState modal with no snap dependency. Preflight (checkSandboxSupport with the absolute /usr/bin tools, systemctl --user using the snap env, MemAvailable) passes in the snap host. /usr/bin/setpriv for --pdeathsig exists. The MCP tool server binds 127.0.0.1. The hook runtime also finds ~/.local/bin/node when PATH lacks it.

## how_to_run
Run from a terminal of the snap VS Code (or from Claude Code inside it), so the run inherits the snap's AppArmor label that bwrap needs on this machine:
`cd /home/zhengyew/telelean/packages/extension && npm run build && TELELEAN_TEST_TMP=<scratch dir outside $HOME> TMPDIR=<scratch>/tmp npm_config_logs_dir=<scratch>/npm-logs npm run test:smoke:snap`

Variants:
- one instance only: `node scripts/smoke.mjs --snap --label=smoke` (or `--label=e2e`)
- another revision: `--snap-root=/snap/code/267`
- a subset of tests: set `TELELEAN_SMOKE_GREP=<regex>`

The run prints the profile folder and writes `<profile>/smoke-summary.json` (isolation checks, VS Code version, AppArmor label and cgroup) and `<profile>/host-env.json` (what the extension host inherited). `npm run test:smoke` still runs the 1.140.0 test build as before.
