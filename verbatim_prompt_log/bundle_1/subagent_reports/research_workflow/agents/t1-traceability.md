## Implied constraints

- **IC-1** (high) Decide how ASSUMPTIONS are encoded in Lean: as global `axiom`s (the user's word) or as hypotheses (section variables, explicit theorem binders, or a bundled structure of assumptions). Whichever is chosen, each theorem's dependency set (its axiom footprint) must be a first-class, machine-checked fact.  [from: S5, S7, S28, SEM-1, SEM-2, SEM-5, LEAN-2]
  - why: Global axioms are visible to every later declaration, so the type checker alone does not enforce S28's claim that the *selected* assumptions suffice, nor S7's 'purely from the ASSUMPTIONS': any axiom in scope may be used. With axioms the check has to happen after the fact via `#print axioms` / `Lean.collectAxioms`. Verified on the installed Lean 4.35.0: `#print axioms goalProof` printed `[Character, Cynder, a1, hasDarkPast]`, so the footprint is exact but mixes vocabulary constants with propositional assumptions (IC-4). With hypotheses, the theorem statement itself lists what it assumes: sufficiency is visible in the signature, deleting an assumption breaks only the theorems that cite it, and arrows can be read off the binders. The cost is verbosity and threading hypotheses through lemmas. A bundled `structure` of vocabulary plus assumptions also allows a consistency witness (an instance is a model). Suggested default: keep `axiom`, for fidelity to S5 and a simple node-to-declaration mapping, but compute footprints after every build to verify S7/S28 and to derive ground-truth arrows.
- **IC-2** (high) The assumption set may be inconsistent (real belief sets often are), and an inconsistent set makes every GOAL provable. Such proofs must not be presented as meaningful.  [from: S5, S28, SEM-1, SEM-5, IC-1]
  - why: Verified on Lean 4.35.0: adding `axiom bad1 : hasDarkPast Cynder -> False` let `theorem anything : (0 : Nat) = 1 := absurd a1 bad1` check, and the only output was an ordinary axiom list. An LLM asked to 'prove the goal' (S29) will take such a route, possibly without saying so, which makes S28's sufficiency assertion vacuous.   - why: Answers to questions like 'do you want to model characters' (S30), and feedback (S33), fix the granularity and interpretation of the formal model. Store them as project-level 'modeling decisions' or notes attached to nodes, feed them into every later run, and show them in the UI. This fits the user's linguistic framing: pragmatics is unspoken context, and this makes it explicit.
- **IC-29** (medium) Record who wrote each piece of text. The user's NL statements are the specification and must not be overwritten, and descriptions written by the LLM must be marked as such.  [from: S6, S32, DATA-4, DATA-5, LLM-6]
  - why: S40 requires an NL description for every node, including vocabulary nodes the LLM creates (S32), so the LLM will write NL text, and that text is itself a formalization-gap risk (IC-3). The user's own wording (e.g., S18: 'Cynder would not be a good addition to the new Spyro game') is the ground truth the Lean must be judged against, and an assumption's rationale (S6) can only come from the user. The markup should therefore record provenance (written by the user or by the LLM) and keep the user's original text verbatim.
- **IC-30** (medium) Lean's logic is classical, monotonic and crisp, while the beliefs in a mental model are often defeasible, vague or graded. How such generalizations are encoded is a modeling decision the system must make visible.  [from: S5, S20, S24, SEM-1, LLM-3]
  - why: 'PG games cannot have characters with dark pasts' (S24) is a defeasible generalization. Encoded as a universally quantified axiom, it becomes absolute and invites contradiction as soon as exceptions are added (see IC-2). 'What they feel is true' (S5) also suggests degrees of belief, which classical Lean cannot express directly. The options (explicit exception predicates, 'typically' predicates, restricting the claim to the stated context) belong among the pragmatic questions the LLM asks (S30) and should not be chosen silently.
- **IC-31** (medium) Define what each kind of selection means for the button, and which other actions the button may need.  [from: S8, S25, S28, UI-9, UI-10, SEM-5]
  - why: The walkthrough selects assumptions plus one goal (S25). But S8 says goals are reached 'via ASSUMPTIONS and DERIVATIONS', so derivations should be selectable as lemmas; their footprints still contain only assumptions. Other selections need defined behavior or validation: several goals; no goal ('formalize these'); a goal alone ('find the assumptions it needs'); a mix of informal and formal nodes. The tray (S26) is a good place to show the inferred proof obligation, such as 'prove G from {A1, A2, A3}', before running.
- **IC-32** (medium) Context and token budget: as the model grows, the LLM must reuse existing vocabulary while receiving only the relevant part of the project.  [from: S9, S43, LLM-2, LLM-4, LLM-6, NFR-2, IC-11]
  - why: For the model to stay coherent, formalizations must build on existing declarations, e.g., reusing `Character` instead of inventing `Character2` (S29, S32). Yet the project 'might be big' (S43), and the subscription has usage limits (S9). The harness needs a strategy for selecting context: the selected nodes, their transitive Lean dependencies, an index of vocabulary, and the saved modeling decisions (IC-28), rather than whole files. Claude Code handles prompt caching itself.
- **IC-33** (medium) The verbatim prompt log records the development conversation and is kept by the assistant; it is not a runtime feature of the extension. The main session must write it on every turn, including prompts that arrive mid-turn.  [from: S53, S54, PROC-8]
  - why: S53-S55 concern the user's prompts to the implementing assistant, and the assistant's responses and requested documents. Subagents cannot see user messages sent mid-turn, so the top-level session has to do the logging. A convention is already in use: bundle_2 holds `prompt2.md`, `response2.md` and `response2_modelinfo.md` (prompt 2 arrived mid-turn). By that convention, the response to prompt 1 and its requested documents (consolidated requirements, unspoken constraints, architecture, software list) belong in bundle_1. Logging the extension's own LLM transcripts would be a separate, optional feature.
- **IC-34** (low) When Claude is used, the content of the user's mental model and Lean files leaves the machine.  [from: S9, LLM-2, DATA-1]
  - why: The harness sends the user's beliefs (assumptions with their rationales) and Lean code to Anthropic through Claude Code. That is acceptable for personal use, but the scope should be limited to the model project, with no unrelated files and no secrets, and the behavior should be documented. Low significance for a single-user tool.

## Tensions

- S2 asks for an 'interactive map ... (at least clicking and dragging components)', which suggests free 2-D placement, but S11-S14 put nodes in three vertical lists by kind. It is unclear what dragging does and what the 'components' are. [S2, S11, S12, S13, S14]
  - resolution: Treat the columns as the layout. Dragging within a column reorders (the order is saved per IC-9); dragging across columns requests a kind change (S16, gated per IC-22); dragging from a node handle draws an arrow (S15). 'Components' means nodes. A free-form graph view for analysis can be added later.
- Who draws the arrows? 'The extension must be able to draw arrows' (S15) can mean edges the user draws or edges the extension computes from Lean dependencies; S25-S29 suggest dependencies are established by the LLM's proof. [S15, S25, S28, S29]
  - resolution: Support both as distinct edge types, intended and actual (IC-5), and ask the user which one is primary.
- S15 allows arrows only 'from any node in one section to a node in another section', but S8 says goals are reached via derivations (chains of derivations and lemmas), and vocabulary nodes (S32) relate to nodes in the same column. Dependencies computed from Lean will include edges within a column. [S15, S8, S32]
  - resolution: Allow edges within a column (drawn as arcs inside the column, or shown on hover), and ask whether the restriction was intended.
- S3/S4 describe the text box as the way to prompt the AI, with the A/D/G switch, but S18-S24 create nodes from it with no LLM involved, and S27 invokes the LLM only through the button. [S3, S4, S10, S18, S20, S22, S24, S27]
  - resolution: The text box plus switch creates informal nodes without the LLM. The LLM runs only on explicit actions (the button on a selection, 'formalize' on a node) and through a conversation strip for answers and feedback. Offer an opt-in setting to formalize automatically on create.
- S7 defines a DERIVATION as purely derivable from the assumptions, but the switch (S4) and moves (S16) let the user create a node in DERIVATIONS, or move one there, before any proof exists. [S7, S4, S16]
  - resolution: Keep the kind assigned by the user but compute the status (IC-6). An unproved DERIVATION is shown as 'claimed' and triggers or offers an LLM proof attempt; it becomes a full derivation only once verified.
- When the button's proof succeeds (S28-S29) and is accepted (S33), does the goal stay in GOALS marked as proved, or move to DERIVATIONS? S8 defines a goal as not yet reached, and S16 says a goal moves to derivations 'once it's proven', but not whether this happens automatically. [S8, S16, S28, S29, S33]
  - resolution: When a verified proof is accepted, move the node to DERIVATIONS (or offer a one-click move) and keep a 'was a goal' badge as history. Never move a node without verification.
- S5 calls assumptions axioms, which are global in Lean, but S25/S28 assert that a *selected subset* suffices. With global axioms, a proof may silently use assumptions that were not selected. [S5, S25, S28]
  - resolution: Check the axiom footprint against the selection (IC-1, IC-21), or encode assumptions as hypotheses in the signature of the goal theorem.
- S32 has the LLM create vocabulary nodes (structure `Cynder`, Prop `isCharacter`), but the panel has exactly three columns, one per kind (S11). S7 forbids new assumptions while S29 requires signatures, and vocabulary declared with `axiom` counts as new axioms in Lean. [S32, S11, S7, S29]
  - resolution: Introduce a vocabulary/definition sub-kind, shown in the ASSUMPTIONS column or as chips or a collapsible strip. Prefer encodings that add no axioms (`structure`, `inductive`, `opaque`), and ask the user (IC-4).
- S6 says assumptions should be annotated with a rationale, but the fourth assumption in the walkthrough (S24) has none. [S6, S24]
  - resolution: Treat the rationale as strongly encouraged but optional: allow creating an assumption without one, show a 'no rationale' indicator, and ask for it later. Always ask for it on assumptions the LLM suggests.
- The markup example (S37) has only `natural_name` and `type`, but other sentences call for a rationale (S6), an NL description that may be a docstring (S40), arrows (S15), a link to the Lean code (S35), and nodes without code (S38). A docstring cannot stand alone without a declaration, and the NL text would end up in two places. [S37, S6, S15, S35, S38, S40]
  - resolution: Define markup schema v1 with `id`, `type`, `natural_name` (the user's statement verbatim), `rationale` (for assumptions), an optional `description`, optional intended edges, a `decl` link, and provenance. Keep the markup as the single source of NL text, and optionally copy it into a generated docstring for formalized nodes.
- S39 rejects `sorry` for nodes without code because it implies an uninhabited representation, which suggests `sorry` would be appropriate once a node is formalized but unproven. Yet S37 represents a GOAL with a `def`, a statement-as-definition that needs no `sorry` at all. [S39, S37, S8, S29]
  - resolution: Separate statement from proof (IC-24): informal means comment only; formalized means `def stmt : Prop`; proved means a theorem inhabiting it. Allow `sorry` only temporarily, and never count it as proved.
- S35 says each node corresponds to something in a Lean file, but the map also has state with no natural place in Lean (the layout from S2, user-drawn arrows from S15), and Lean files will contain declarations that are not nodes (direct edits, S42). [S35, S2, S15, S42]
  - resolution: Every node gets a markup block, but not every Lean declaration is a node. Store the layout in a sidecar file keyed by node id; store intended edges in the markup or the sidecar (decide per IC-9); show unmarked declarations as 'untracked'.
- Click and drag each do two jobs: click selects (S25) and expands (S40); drag moves nodes (S2, S16) and draws arrows (S15). [S2, S15, S16, S25, S40]
  - resolution: Give each action its own affordance: click or a checkbox to select (with a modifier for multi-select), a chevron or double-click to expand, drag the body to move, drag from a port to draw an arrow. Provide keyboard equivalents for all of them.
- S30 has the LLM ask questions 'along the way', but the walkthrough reads as a single button-then-diff flow (S27, S31). The only input surface is the text box with the A/D/G switch (S4, S10), and the kind marking means nothing for an answer. [S30, S27, S31, S4, S10]
  - resolution: Add a conversation/question strip with multiple-choice cards and a free-text 'Other' option, backed by AskUserQuestion or a custom ask_user tool. While a question is pending, switch the input box to 'answer' mode and disable the A/D/G switch.
- S41 marks only whether a node has a Lean representation (the blue aura), but S7, S8 and S16 depend on whether it is proved. A formalized but unproved goal and a proved derivation would look the same. [S41, S7, S8, S16]
  - resolution: Keep the blue aura for 'has a Lean representation' as requested, and add separate status badges or icons: proved, unproved, broken, claimed.
- The walkthrough selects only assumptions plus a goal (S25; S28: 'the assumptions must be enough'), but S8 says goals are reached via ASSUMPTIONS and DERIVATIONS. Can derivations be selected as premises? [S25, S28, S8]
  - resolution: Allow derivations in the selection as lemmas. The sufficiency check then becomes: the footprint must lie within the selected assumptions together with the footprints of the selected derivations.
- S9 asks for a pluggable LLM ('slot in an LLM'), but the required Claude route through the subscription means driving Claude Code, an agent runtime with its own tools, while other providers expose plain completion APIs. Anthropic's policy also bars third-party products from offering claude.ai login. [S9]
  - resolution: Define the harness interface at the agent level: a task goes in; events, questions and a diff come out. Expose the extension's tools via MCP so other agents can reuse them. Ship a Claude Code adapter for personal subscription use, and keep an API-key adapter path for anything distributed.
- S43 asks whether an LSP is right, but the node markup lives inside `.lean` files (S35) that Lean's own language server already serves, and the direct editing in S42 happens in those same files. [S43, S35, S42]
  - resolution: Recommend a headless core library plus a CLI (graph export for scripts), used by the extension. Defer a markup LSP, or go Lean-native with attributes, commands and Lean server RPC (IC-19, IC-20).
- 'The directory that VSCode is currently in' and 'the current directory' (S2, S35) are the user's model workspace, whereas 'this directory' in S51 is where the extension's code is implemented (/home/zhengyew/telelean). [S2, S35, S51]
  - resolution: Keep the extension source in /home/zhengyew/telelean. The model workspace is whatever folder VS Code has open when the extension runs. Ship a sample model project (the Spyro walkthrough) for testing and for the usage directions.
- S54 says to log every prompt 'in a new bundle', yet S53 notes that bundle_1 already holds prompt1.md. Where do the response to prompt 1 and its requested documents go, and how are mid-turn prompts bundled? [S53, S54, S55]
  - resolution: Follow the convention already used in bundle_2 (promptN.md, responseN.md, and extra documents such as responseN_modelinfo.md). The response to prompt 1 and its documents go in bundle_1, and every later prompt, including mid-turn ones, gets its own bundle. Check this against the referenced spectec example.
- The user is expected to 'mostly work in the extension window' (S42), yet expanding a node to see its Lean definition (S40) and switching to the diff of the Lean files (S31) both need Lean views. It is unclear whether these appear inside the panel or as regular VS Code editors. [S42, S40, S31]
  - resolution: Show Lean snippets inline in the panel (read-only, syntax-highlighted) when a node is expanded. For full-file views, open VS Code's native diff editor or editor in a side split, launched from the panel.
