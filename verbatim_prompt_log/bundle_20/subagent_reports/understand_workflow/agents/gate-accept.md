## 1. Pipeline: what runs, in which order

- **`Engine.runCheck`** (runner/src/gate/engine.ts:393-469): G0 = core `checkFileChanges(B files, ws/ files)` (407-408); **any G0 finding stops before Lean runs** (409-411) → sync build mirror, one Lean job (build + generated check file) (413-421) → `classifyFacts`: timeout/oom = counted `budget` finding; sandbox/low-memory/cancel = uncounted `environment` (428-432) → project models: S (fresh facts), B = commit `base` or `ctx.baseCommit` (Accept's `accept-base`), with B's facts **only when B is the run's base commit** (436-437), A = newest `adopt` commit (438-439), R = round start (440) → core `evaluateRules` (441-451) → **fail closed**: Lean errors with no `build` finding get one (453-454).
- **Purposes** (core/src/gate/types.ts:182-196): `check` (check_lean: report everything, block nothing), `freeze`, `gate-proved` (finish proved), `gate-other` (any other finish status).
- **`freezeNow`** (engine.ts:549-620): runCheck(freeze) → `computePermittedAxioms(model, selection, B)` + `frozenSnapshot` (569-576) → G4 challenge (578-604) → commit `freeze` (617). **At most one freeze per round**: manager.ts:1983 throws `"already frozen in this round; statements change only after the person's feedback"`.
- **`gateNow`** (engine.ts:668-701): judges exactly one committed state (`judgedCommit` 645-649: the `normalise` commit, else a `checkpoint`); purpose `gate-proved` iff status proved; `not-frozen` fallback (679); **G4 only when status is proved, the round has a freeze and there is no other finding** (684-689). The RunManager normalises first (manager.ts:2142-2158).
- **After the gate**: pass → `gate-pass` commit, edits after finish discarded (manager.ts:1086-1098, 2174-2183). Fail below the cap → notice + retry. At the cap / no finish / caps → revert to newest `gate-pass` | `freeze` | `base` (runner/src/shadow/types.ts:69 `PASSING_COMMIT_KINDS`), normalise, re-check with purpose `check` (non-blocking), proposal from that state (manager.ts:1101-1129).
- **`checkBase`** (engine.ts:483-529): the user's files must build before Claude is contacted (no G0 on the user's text); B's facts kept in `<runDir>/base-facts.json`.
- **UI names of the steps** (webview/src/model/run.ts:362-368): G0 "allowed Lean only", G1 "build", G3 "what it rests on", G4 "statement unchanged" (tooltip "Check G4: Lean compares the proved statement with the one frozen before the proof"), G5 "your words untouched" (tooltip "Check G5: your cards' sentences, reasons and settings are untouched").

## 3. Permitted set, the user's declarations, what is frozen

### 3.1 The permitted set — exact formula (core/src/gate/permitted.ts:84-122; contract core/src/gate/index.ts:74-91)
`all = sort(distinct(standard ∪ signature ∪ selected ∪ presuppositions ∪ derivationFootprints))`, every category passed through `drop` = minus T.holds and sorryAx (permitted.ts:111):
- **standard** = `STANDARD_AXIOM_NAMES` = propext, Classical.choice, Quot.sound (core/src/facts.ts:17; mirrored in comparator.ts:27).
- **signature** = `signatureAxioms(model)` (permitted.ts:35-47): every facts entry of kind axiom, **not owned by a card** (neither a statement nor a `.holds`), whose `typeSort` is not `Prop`, and which is either vocabulary of kind sort/predicate/function/constant (`SIGNATURE_KINDS`, :25 — the TL111 flag is ignored, so the user's own shape-violating items count) or no vocabulary item at all, typed by Lean, outside every subject's files (library root: user-only because of G0 `outside-subject`). Project-wide.
- **selected** = for each premise ∪ adopted ghost (≠ T) with a statement, a `.holds`, no `holds-mismatch`, whose `.holds` is an axiom: `n.holds` (`contribution`, :50-59). Independent of card type, **independent of what n now says**.
- **presuppositions** = `lean.presupposes` (= Ax(statement) ∩ presupposition axioms) of T and of every chosen card, usable or not (:95, :101).
- **derivationFootprints** = for a chosen card proved (not conditional) by a non-axiom `.holds`: Ax(.holds) \ {sorryAx}, dropped whole if it contains T.holds (circular); **given B, only for the user's own proof**: same statement in B and `.holds` text identical to B's, B's footprint when B has facts (`footprintSinceBase`, :61-76). A proof Claude wrote/changed never widens the set it is judged against.
- **unusable** = chosen cards contributing neither (summary only).
Used by: F (engine.ts:569-572, computed with B), the footprint rule (rules.ts:509), G4, the ghost check (engine.ts:770-779). Spyro normative: 13 names (3 STD, 5 signature, 2 presuppositions, 3 selected `.holds`); the proof's footprint is 11 of them.

### 3.2 Whose declarations count as the user's (protected)
- **B** is exactly the user's files at run start (commit `base`) or at Accept after drift (commit `accept-base`; no B facts then) (core/src/gate/types.ts:203-211; engine.ts:404-405, 436-437; runner/src/gate/types.ts:79-85).
- Protected by `existing-changed`: every named declaration in B — statements, `.holds` axioms and theorems, vocabulary, definitions, lemmas, instances — except T.holds. Also: the user's lines are exempt from G0; the user's unchanged sorry from `sorry-axiom`; the user's axioms from `new-axiom` (known in B) and `vocabulary-shape`; the user's definitions/presuppositions are never questions (`inBase`, rules.ts:158, 824); the user's proved derivations feed DF. D-21 (02_design_decisions.md:350-352): "Lean you write counts as signed off by you".
- telelean's adopted ghost blocks/declarations are held to A (rules.ts:384-407, 1003-1031).
- **Not protected**: Claude's own formalisations from earlier rounds of the same run (not in B) — only `statement-changed` within a round after F, and G4 for T's closure (report 3.6 "Rounds", 3.7 item 7).
- **Known breadth** (report 3.7 item 7): `existing-changed` and pre-freeze `new-axiom` exempt T.holds by name (rules.ts:113-116), so in a non-proved round Claude can delete the user's existing proof of T, or turn it into `axiom T.holds : T` before a freeze, with no finding.
- The user's `example`s are not protected against removal (only added ones are judged) — harmless (nothing can use them).

### 3.3 What "existing declarations unchanged" compares (rules.ts:343-383)
For each entry of `declTables(B).byName` (decls.ts:36-58: named declarations, first occurrence wins, files in path order, `mutual` skipped, `example`s excluded, anonymous instances under Lean's automatic `inst…` name): skip T.holds; missing in S → `removed`/`target`; `entry.text` = `file.text.slice(decl.span.start, decl.span.end)` (docstring and attributes through the last line) must be identical (`changed`/`target`); then, **only when B has facts**, normalised facts `type` (`#check`) and `value` (`#print`) must be equal (`meaning`: catches `open … in`, section variables, new declarations that change what unchanged text elaborates to). Misses (3.7 item 1): changes that print identically (instance arguments hidden), e.g. `instance (priority := high) myAdd : Add Nat := ⟨fun _ _ => 0⟩` before the freeze.

### 3.4 What "your words byte-identical" (G5) protects
Blocks matched per file by node id and occurrence; for each COMPARED_FIELD the list of **raw** values of that key's lines must be identical (rules.ts:66-69, 912-928), so even whitespace/escaping changes to `natural_name`/`rationale` count. It also protects provenance (`origin`, `session`, `worded_by`), declared support (`premises`), kind (`type`), notes, extensions, version, ids, pins and bindings, and forbids adding/removing/moving blocks. Board sentence: "it changed your words on “…”" (describe.ts:217-219). System prompt: "Never change any field of a block (including `lean:` lines), never add or delete blocks, never change a declaration that existed before the run (except the target's `.holds`)".

### 3.5 What freeze_statements freezes (permitted.ts:125-145; engine.ts:549-620)
- `permitted` (Perm(F), with B); `targetStatement`;
- `declarations`: every facts entry of the **subject's** files whose kind is not `theorem` (statements, vocabulary, definitions, instances), with normalised kind/type/value → `statement-changed`;
- `axioms`: every axiom of the **whole project** (facts + syntactic) → after F `new-axiom` refuses any other;
- the G4 challenge: a copy of the mirror minus T.holds and every declaration transitively referring to it (`removalClosure`, engine.ts:164-193), plus a generated module `theorem T.holds : T := sorry` (the only sorry telelean writes), built and exported to `frozen.ndjson`;
- then commit `freeze`, stage → prove, a second freeze in the round refused.
**Not frozen**: theorems (proofs may be reworked); new definitions and `noncomputable opaque` constants can still be added after F (held only to `footprint`); the freeze is per round (Feedback/adoption start a new round; Feedback moves R to the head and needs a new freeze, manager.ts:1490-1522).

## 4. Definitions, presuppositions and the vocabulary rule

### 4.1 Why "A definition can quietly carry a belief, so Accept needs your yes for each" (Review.tsx:161-162)
A `def` body is a definitional equation, not an axiom: `#print axioms` never lists it, so `footprint`, `new-axiom` and G4's axiom check are blind to it; G4 runs with `definition_names: []`; the shape rule does not judge definitions. Whatever the body says becomes true "by definition".

**Example 1** (the gate's own cheat table, project-report.md:2210; Spyro, literal reading). Vocabulary in B: `axiom Character : Type`, `axiom Game : Type`, `axiom HasDarkPast : Character → Prop`, `axiom IsPG : Game → Prop`, `axiom GoodAddition : Character → Game → Prop`, `noncomputable opaque cynder : Character`, `noncomputable opaque newSpyro : Game`. Selected: "PG games cannot have characters with dark pasts" (code-less), `cynder_dark_past`, `new_spyro_pg`; goal `cynder_not_good := ¬ GoodAddition cynder newSpyro`. Claude writes:
```lean
/-- c is in game g -/
def InGame (c : Character) (g : Game) : Prop := GoodAddition c g   -- the smuggled belief
/-- PG games cannot have characters with dark pasts -/
abbrev pg_no_dark_past : Prop := ∀ (g : Game) (c : Character), IsPG g → HasDarkPast c → ¬ InGame c g
axiom pg_no_dark_past.holds : pg_no_dark_past
theorem cynder_not_good.holds : cynder_not_good :=
  pg_no_dark_past.holds newSpyro cynder new_spyro_pg.holds cynder_dark_past.holds
```
Every rule passes: the only new axiom is a selected ASSUMPTION's `.holds`; the footprint is the same 11 names as the honest normative run; G4 accepts. The statement review even looks faithful ("cannot have" ≈ `¬ InGame`). The belief "being in a game = being a good addition to it" — exactly the gap the honest literal reading leaves (the goal does not follow) — lives only in the def body. Only the definition question ("Your statements rely on it: PG games cannot have…") exposes it.

**Example 2** (a code-less goal made a one-premise consequence): goal "Cynder would not be a good addition to the new Spyro game" without code, `GoodAddition` not yet in the vocabulary. Claude writes `def GoodAddition (c : Character) (g : Game) : Prop := ¬ HasDarkPast c`, `abbrev cynder_not_good : Prop := ¬ GoodAddition cynder newSpyro`, `theorem cynder_not_good.holds : cynder_not_good := fun h => h cynder_dark_past.holds`. Footprint ⊆ Perm; "proved from your premises"; the theory "a good addition is one without a dark past" was never selected. (Had GoodAddition existed in B, `existing-changed` would refuse the redefinition — cheat row "`axiom GoodAddition` turned into `def GoodAddition c _ := ¬ HasDarkPast c` → existing-changed (its footprint lies inside Perm)".)

### 4.2 How flaggedDefinitions are computed (rules.ts:807-834, called at 793)
- Vocabulary = every declaration in a subject's modules bound to no card, classified from Lean's facts (core/src/project/vocabulary.ts:200-279). Kind `definition` = def, abbrev, structure, inductive, class, and any instance except the presupposition instance `instance : Nonempty T := T.exists` (classified `hidden`, :264-270).
- `lean.uses` (statement closure): BFS from the statement over facts `refs`, collecting vocabulary items, recursing through other cards' statements and through definitions (core/src/project/build.ts:483-506). Each item's `usedBy` = cards whose `uses` or `presupposes` contain it; a definition in any card's `uses` gets flag `definitional-choice` (build.ts:780-791).
- **Flagged** = every vocabulary item **whose name is not known in B** (rules.ts:824) that is (a) a `definition` on a statement path — `usedBy` non-empty (any card, selected or not), or flag `definitional-choice`, or in the union of chosen cards' `uses`, or referred to by a vocabulary item that is not itself a definition/lemma (e.g. a structure typing `noncomputable opaque c : Pair`) — or (b) any new `presupposition`. Each → `FlaggedDefinition {name, kind, code, gloss, usedByStatementsOf}` (types.ts:232-240) → `DefinitionQuestion d1, d2, …` (runner/src/proposal/service.ts:171-182).
- The proposal uses the passing gate's list (manager.ts:1097), or after a revert the re-check's (1128).
- **Important mechanical dependency**: `flagged` keys on *new names*. An existing name changed in place (e.g. vocabulary `axiom HasDarkPast` turned into a `def`) is never a question; today that is covered by `existing-changed` refusing the change.

### 4.3 Which need a yes, which are exempt
- **Need a yes**: every new definition on a statement path; every new presupposition.
- **Exempt**: definitions/presuppositions known in B (the user's, or accepted in an earlier run); proof-only definitions (D-4, 02_design_decisions.md:133: "Proof-only definitions are conservative and need none" — a def no statement reaches cannot change what a statement means, and any axiom it uses is caught by `footprint`); lemmas; the presupposition instance; pure-signature vocabulary (sorts, predicates, functions, constants): **auto-approved but revocable** (`VocabularyReview`, service.ts:59, 256-263; Review.tsx:95-96 "Claude added this vocabulary. Plain types, predicates and constants pass the simple vocabulary rule, so they are approved unless you revoke one (revoking sends Feedback)."; "Revoke…" prefills "Please don't add the vocabulary item `X` (“gloss”): ").
- **Docs vs code**: D-4 (02:133) says instances and coercions on a statement path need endorsement, and the system prompt says "Any other `def`, `structure`, `inductive` or `instance` is shown to the person as a question"; the code flags only definitions reachable by identifier references, so type-class-resolved instances/coercions are never flagged (report 3.7 item 1, verified gap) and proof-only defs are not questions.

### 4.4 Presuppositions ("X exists") and why they need endorsement
`axiom T.exists : Nonempty T` for a project sort T (vocabulary.ts:241-242) plus the plumbing `instance : Nonempty T := T.exists`. Lean accepts `noncomputable opaque c : T` only with an inhabitant, so every statement naming c depends on T.exists (`#print axioms Spyro.cynder_dark_past` = [Classical.choice, Spyro.Character, Spyro.HasDarkPast, Spyro.Character.exists]). They are permitted **automatically**: presup(T) and presup of every chosen card are in Perm (permitted.ts:95, 101), and any non-proof declaration may use any presupposition (rules.ts:554). So a new presupposition is a belief that reaches proofs **without any card** — an existence claim with logical content (existential import). Example: the user holds `abbrev all_unicorns_white : Prop := ∀ u : Unicorn, White u` (true vacuously if there are none); the goal "the unicorn in my garden is white" makes Claude introduce `noncomputable opaque gardenUnicorn : Unicorn`, which forces `axiom Unicorn.exists : Nonempty Unicorn`; `theorem garden_white.holds : White gardenUnicorn := all_unicorns_white.holds gardenUnicorn` passes the footprint rule (Unicorn.exists ∈ presup(T)) — "proved", but only because unicorns were assumed to exist (presupposition failure, "the King of France is bald"). Hence every new presupposition is a question (rules.ts:829-830), shown as "existence assumption" (Review.tsx:126), and the prompt says "The person confirms each new `T.exists`".

### 4.5 The vocabulary shape rule (vocabulary.ts:200-279; gate rules.ts:601-614)
- `axiom T : Type` → sort (exactly `Type`; no args, no universe).
- `axiom X : Nonempty T`, T a sort → presupposition.
- axiom whose type is a Prop → unmarked axiom (TL104 hidden assumption), never vocabulary (new ones: `new-axiom` `belief`).
- `axiom`/`opaque P : T₁ → … → Tₙ → Prop` → predicate (n ≥ 0, so `axiom P : Prop`); every Tᵢ a sort, no implicit/instance binders, else TL111 `shape-violation`.
- `opaque c : T`, `opaque f : T₁ → … → T` over sorts → constant/function; declared with `axiom` → TL111 ("declare it `noncomputable opaque` so its existence presupposition shows").
- any other axiom/opaque (`Empty`, `PLift False`, `Type 1`, `Sort u`, non-sort types) → `other` (TL111); never signature.
- def/abbrev/structure/inductive/class/other instances → definition (§4.2); theorem without card → lemma.
Gate: every vocabulary item not known in B with `shape-violation` or kind `other` fails: "Vocabulary may only be sorts `axiom T : Type`, predicates `axiom P : T₁ → … → Prop` over sorts, and constants or functions as `noncomputable opaque`." Blocks: `axiom Character : Prop` used as a sort; a constant of type `{g : Game // IsPG g}` (its presupposition *is* the belief); predicates over `PLift p`; silent existence via `axiom c : T`; `Sort u` instantiated at Prop. **Only new names are checked**: existing items are exempt.

### 4.6 How the yes is enforced
Webview: one step "Definitions (N)" (Review.tsx:156-169), lead "Claude introduced this definition/these definitions. A definition can quietly carry a belief, so Accept needs your yes for each; a no is Feedback for Claude."; per item "Yes, I endorse it" / "No…" (146-149), "Your statements rely on it:" (132); "No…" prefills Feedback "I don't endorse the definition `name` (“gloss”): " (store.ts:1484-1493). Accept disabled until all yes (Review.tsx:267-279, title "Answer every definition question with yes first (a no is Feedback)"; hint "Accept needs your yes for every definition question.", 294-298; `definitionsApproved`, webview/src/model/run.ts:499-502). Host: `acceptNow` refuses unless every definition id is sent: 'Answer every definition question: a “no” is feedback.' (manager.ts:1651-1652). Approvals are **not persisted** (no decisions.json entry): the endorsement is the Accept itself.

## 6. Safety analysis of the new specification

### 6.1 The trust-model shift
Today the boundary is **mechanical and total**: everything in B — all the user's cards, words, Lean, beliefs, proofs, vocabulary — is immutable to Claude (`existing-changed` + G5); Claude may only **add** (vocabulary, statements for chosen code-less cards, `.holds` axioms of selected ASSUMPTIONs, proofs, incl. `theorem p.holds` for selected GOAL/DERIVATION premises); every addition is held to the selection (`new-axiom`, `footprint`, G4); and human review is needed only for meaning (statements Claude wrote) and definitions/presuppositions. The spec replaces "immutable = everything pre-existing" by "immutable = FROZEN", makes any unfrozen card editable, creatable and deletable by Claude, and relies on the review. A session started by "These suffice" freezes **nothing** (only "initiate edit session" freezes non-selected cards, INITIATING 2). Unless compensated, every attack `existing-changed` and G5 block today becomes possible and is caught only if the user reads the right item.

Two meanings of "proved" must be kept apart: (1) the **board chip**, recomputed by Lean on the real files after Accept ("The board never shows 'proved' without Lean"; build.ts status) — it stays Lean-true but may rest on things the user never approved (its footprint shows them; a hidden axiom appears as `axiom:<name>` with TL103 and suppresses "self-evident", build.ts:610-658); (2) the **run's claims** — report card verdict and "Rests on", the history label "These suffice → proved: …", attempts.jsonl `verdict: proved`, the lifecycle reason "Lean proved it from the selected premises", and (new) the review table's "accepted". (2) is what the gate certifies, **and only for exactly the judged file state**.

### 6.2 Mechanism by mechanism
**(a) Partial acceptance.** Impossible by construction today. A subset of items is a file state the gate never judged. Accepting a proof while declining (or later adjusting) any item in its dependency closure — the target's statement, a selected premise's formalisation, a definition/vocabulary item/presupposition in a statement closure, a lemma it calls — yields either a state that does not build (board: ill-formed / not checked, not a false "proved") or, worse, one that builds with a different meaning (the declined item replaced by Claude's next version or the user's TRANSFORM) while the table says "accepted" and the report says "proved from your premises". Accepting a statement while declining the definition its meaning rests on lets a belief in if the definition stays because something else needs it. ⇒ acceptance must be dependency-closed (telelean computes dependencies from Lean refs/`uses`/footprints), declines must propagate to dependents, and the exact final state must be re-gated before it reaches the user's files.

**(b) Per-card/per-field FROZEN.** Safe only if mechanical: the gate must refuse changes to frozen fields (G5 + `existing-changed` generalised from "all of B" to "the locked set"); the lock set must live outside Claude's reach (Claude's file tools are confined to ws/ and denied `.lake`, `.telelean`, `.git`, runner/src/llm/confinement.ts:28 — a `frozen:` field inside a block would be editable unless G5 protects it); it must be snapshotted per Claude turn (users may toggle "at ALL times", FROZEN 4-5). **Frozen text is not frozen meaning**: a frozen statement changes meaning through unfrozen vocabulary, definitions or instances it uses — exactly what `existing-changed`'s text+meaning check and G4's closure comparison protect today. Locking a statement must lock (or meaning-check) its closure. And `flagged` only asks about *new* names (§4.2), so an in-place change of an existing vocabulary item would be neither refused nor asked once `existing-changed` is relaxed for unfrozen items.

**(c) User-written Lean in TRANSFORM.** The user's own Lean is legitimately their belief (D-21), so a def the user writes is signed off. Risks: (1) template insertion without the single-term rule (g0.ts:233-330) lets a field close the declaration and add others (`True` + newline + `axiom evil : False`); (2) ill-typed frozen text breaks its whole module (Lean's unit of failure) and Claude may not fix it → every gate attempt fails at G1 (deadlock); (3) if the text names things that do not exist yet ("fuzzy" vocabulary), Claude's later definitions decide what the user's frozen text means → they must be questions; (4) B is fixed at run start today, so user text added mid-session would be judged as Claude's (G0 tokens, `new-axiom` for an `axiom` the user typed) and never protected by `existing-changed` — B must advance with each user edit (as `accept-base` does at Accept) **with B's facts rebuilt**, or the `meaning` check is lost.

**(d) "Fuzzy" fields auto-filled by Claude.** A sentence Claude writes is Claude's words: `worded_by: agent` must be written by telelean (today G5 forbids Claude touching `worded_by`; if Claude may edit blocks it could leave its sentence marked as the user's, shown in the user's style instead of `AgentText`). A fuzzy **type** set to ASSUMPTION by Claude makes Claude author a belief (impossible today: `new-axiom` allows only `.holds` of the user's selected ASSUMPTIONs; new cards only via "I hold this"). Fuzzy Lean on a user sentence is today's "Formalize" (meaning review). Fuzzy vocabulary bodies are Claude definitions (questions).

**(e) Deleting cards others depend on.** M1's delete has "Card only", which keeps the Lean: "“Card only” keeps the Lean declarations: without the card, `axiom …holds` becomes an unmarked axiom, a hidden assumption Lean still takes as given" (webview/src/dialogs/Dialogs.tsx:186-190; core/src/edit/planDelete.ts:22-36 `leavesUnmarkedAxiom`). If a Claude-proposed "Delete" used those semantics, proofs resting on the card stay "proved" with footprint `axiom:…holds` (TL103) — a belief with no card. A full delete breaks dependents visibly (`needs-confirmation`, planAction.ts:165-176). A deletion inside an inference's selection must withdraw its verdict; deleting a dependency of a frozen card changes that card's status without editing it.

**(f) "Shaky" regeneration.** Hands Claude the card — for a user's ASSUMPTION, the user's sentence and belief. Splitting/rewording creates Claude-authored beliefs. Safe only if every regenerated card is an item needing explicit acceptance, beliefs are marked Claude's, and nothing is reported proved from them before acceptance. The "not the exact configuration" rule has no soundness content (and can only be checked textually).

**(g) Mid-stage "These suffice".** Today: one run per folder, one target, selection fixed at start (runner/src/run/preflight.ts:44-57, 86-88). Needed: (1) each inference has its own Selection, freeze, Perm and G4 — a shared/union set lets T2's proof use T1's premises or another target's claimed `.holds` (`permittedAxioms` excludes only its own target's claim, permitted.ts:57, 111); (2) the target's and selected premises' existing statements locked **for the inference** even if unfrozen — otherwise Claude weakens the target in the formalise phase and the freeze then fixes the weakened text, so G4 passes; (3) the verdict rests on items still "in review" (Claude's premise formalisations, new vocabulary, definitions): it must be conditional on them and withdrawn when any is declined or changed; (4) the per-round freeze discipline weakens: Claude revises statements while knowing earlier proofs (3.7 item 7), which the spec makes routine. Also: to prove a frozen target, its proof field must be unlocked while its statement stays locked — per-field freeze maps exactly onto today's freeze semantics.

**(h) Restoring frozen status at session end.** Changes no file, so no "proved" becomes false at that moment. But afterwards everything not frozen before the session — including formalisations and beliefs the user just accepted — is editable by the next session's Claude. Today those are in B for the next run and protected. Cards created in the session have no "before" status (spec gap).

**(i) User edits of Vocabulary and "Claude suggests" cards.** Vocabulary items are not cards (computed from declarations bound to no block, vocabulary.ts:285-371), so locks must be keyed by declaration name. A vocabulary edit changes the meaning of every statement using it, frozen ones included, and can break frozen proofs: warn with `VocabItem.usedBy`. If Claude fills a fuzzy body it is a Claude definition → question. A ghost's checks ("closes the gap (checked)", `aloneEntails`) hold only for the exact checked text (engine.ts:738-783; adoption writes exactly it); a TRANSFORM voids them. Ghosts as "regular new cards" must keep: Claude never writes a belief into the files itself; single-term rule for every template insertion; `worded_by: agent`; the "gives the goal on its own: it may simply restate it" flag; adoption as an explicit per-item act.

**(j) Claude editing any unfrozen card.** The core regression. Today forbidden by `existing-changed` (any B declaration) and G5 (any B field). Newly allowed: the user's sentences (the specification itself), the Lean of the user's ASSUMPTIONs (their beliefs), the target's statement, `premises:` (declared support, from which TL107 "used-undeclared" is computed), `type:` (proved Derivation → Assumption converts a proof into a belief; GOAL → ASSUMPTION asserts the goal), provenance, other cards' proofs (footprint changes). Each must at least be its own clearly-marked item (diff against the user's original words/Lean), never auto-applied, never silently group-accepted; proofs resting on a changed item must be re-gated after its acceptance.

### 6.3 Strongest concrete failure scenarios
(Each passes every gate rule that would remain once "unfrozen ⇒ editable" replaces `existing-changed`/G5 for unfrozen items.)
1. **A vocabulary redefinition makes a selected belief inconsistent; the frozen card's text never changes.** B: `axiom HasDarkPast : Character → Prop`, `abbrev cynder_dark_past : Prop := HasDarkPast cynder`, `axiom cynder_dark_past.holds : cynder_dark_past` (the card may even be frozen). Vocabulary is not a card and is unfrozen in a "These suffice" session. Claude changes `HasDarkPast` in place to `def HasDarkPast (_ : Character) : Prop := False` and proves `theorem cynder_not_good.holds : cynder_not_good := cynder_dark_past.holds.elim`. `new-axiom`: nothing new; footprint {cynder_dark_past.holds, signature, Character.exists} ⊆ Perm (the premise is selected); `flagged` does **not** ask (HasDarkPast is a name known in B, rules.ts:824); `vocabulary-shape` skips known names; `existing-changed` meaning check would not see `cynder_dark_past` change (it prints `HasDarkPast cynder` either way); F and G4 are taken after the change. Report: "proved from your selected premises", consistency "unchecked". Today: `existing-changed` refuses the change to HasDarkPast.
2. **Belief replacement in a selected premise.** A1 "PG games cannot have characters with dark pasts", earlier formalised/accepted as `∀ g c, IsPG g → HasDarkPast c → ¬ InGame c g` with `axiom pg_rule.holds`; unfrozen (session via These suffice, or status restored after the earlier session). Claude changes A1's Lean to `… → ¬ GoodAddition c g` (and, if allowed, rewords A1's sentence to match) and proves the goal in one line. `pg_rule.holds` is in Sel whatever it says; the statement review shows sentence and Lean agreeing (Claude wrote both). Today: `existing-changed` + G5 `natural_name`.
3. **Target weakening.** T `abbrev cynder_not_good : Prop := ¬ GoodAddition cynder newSpyro` unfrozen; Claude rewrites it as `¬ GoodAddition cynder newSpyro ∨ True` before the freeze and proves `Or.inr trivial`; G4 compares against the weakened freeze; "proved" shown under the user's goal sentence. Today: `existing-changed` (+ G5 `lean`/`binding` against re-pointing, + G4 after F).
4. **Definition approved in bulk.** "One item for all the vocabulary" or a group accept (REVIEW 4) covers `def InGame c g := GoodAddition c g` (§4.1) together with harmless sorts; the per-definition "Yes, I endorse it" is gone.
5. **Partial accept with a declined dependency.** The user accepts the proof of cynder-not-good and declines "Formalize pg-no-dark-past" with "Adjust", writing their own Lean; the accepted (frozen) proof cannot be touched by Claude; it breaks (deadlock until the user unfreezes) or, if what it relied on changed compatibly, builds with another meaning; the table still says "accepted"; if accepted items are applied like today's no-drift Accept, nothing re-gates.
6. **Claude-authored belief used before acceptance.** New card "Cynder is evil" with fuzzy type/Lean (or produced by gap-filling or a shaky split): Claude makes it an ASSUMPTION `abbrev cynder_evil : Prop := ∀ g, ¬ GoodAddition cynder g` + `axiom cynder_evil.holds`, narrower sentence than Lean; a mid-stage These suffice uses it; if in-review cards count as selected, "proved" rests on a belief never adopted. Today: `new-axiom` `belief`, G5 `block`; beliefs from Claude only via the gap check and "I hold this".
7. **Deletion that hides a belief.** "Delete cynder-dark-past" applied block-only: `axiom cynder_dark_past.holds` stays as an unmarked axiom; dependent proofs stay "proved" with footprint `axiom:Spyro.cynder_dark_past.holds` (TL103/TL104).
8. **Cross-inference permitted set.** Two inferences in one session (T1 from {P1}, T2 from {P3}) judged with one selection: T2's proof uses P1.holds and is reported "proved from {P3}"; or T1 and T2 each use the other's pending `.holds`.
9. **Lock in the wrong place / at the wrong time.** FROZEN stored as a block field that Claude edits; or a freeze toggled during Claude's turn judged against the live set (spurious failures) or silently not applied.
10. **Template injection in a user field.** A TRANSFORM Lean field holding `True` + newline + `axiom evil : False` written after `abbrev s : Prop :=` adds an axiom proving anything; as "the user's text" it would also escape G0 and `new-axiom` if B simply advances to include it.
11. **(Existing, amplified)** the T.holds exemption: in a stage that does not finish `proved`, Claude may delete the user's proof of T or replace it by `axiom T.holds : T` before a freeze (3.7 item 7); many stages per session repeat this window.
12. **(Existing, amplified)** post-drift re-gate ignores new flagged definitions (§5 (i)); with user TRANSFORM text naming things Claude defines, this becomes the normal path.

### 6.4 What must stay mechanical (requirements to fold into the spec)
- **R1** Only gated states reach the user's files: the exact final state (and any state applied earlier) passes G0, G1, G3, G5 and, per "These suffice" target, freeze + G4. No "no drift, no check" shortcut unless the applied files equal the judged ones byte for byte.
- **R2** Acceptance is dependency-closed; declining/changing an item resets every accepted item relying on it to "in review" (text may stay frozen; verdicts are recomputed).
- **R3** FROZEN = a lock set enforced by the gate (G5 per field + existing-changed text+meaning per declaration), stored outside ws/, snapshotted per Claude turn; locking a statement locks (or meaning-checks) its closure; `flagged` must also flag *changed* definitions, not only new names.
- **R4** Default-locked regardless of how the session started: user-worded `natural_name`/`rationale`; ASSUMPTION statements and `.holds`; `premises:`, `type:`, `id`, provenance; the statements of a running inference's target and selected premises. Unlocking any is a per-field user act; the resulting change is a separate, prominently labelled item, excluded from group accept. Any sentence Claude writes gets `worded_by: agent` from telelean.
- **R5** Only the user adds beliefs: cards Claude creates or turns into ASSUMPTIONs (gap-filling, fuzzy type, shaky regeneration, ghosts) are "adopt" items; their `.holds` is in no permitted set until accepted; proofs resting on them are shown as conditional; `aloneEntails` stays visible.
- **R6** Definitions and presuppositions stay separate per-item endorsements (not in "one item for all the vocabulary", not group-acceptable), recomputed on the final state (closes §5 (i)).
- **R7** One Selection, freeze, Perm and G4 per inference; no union; no other target's claim permitted without explicit selection.
- **R8** User-written Lean fields: single-term rule + scratch Lean check at "submit transform"; B advances to include them, with B's facts rebuilt.
- **R9** Delete = block + statement + `.holds` (proofs archived), dependents listed and confirmed (`planDel` `brokenDependents`), affected verdicts withdrawn; never block-only for a Claude-proposed delete.
- **R10** Terminology: the spec's FROZEN collides with `freeze_statements` ("Statements frozen (round n)", `RunView.frozen`, G4's "the one frozen before the proof", codes `not-frozen`, `statement-changed`); "Lean definition" (REVIEW 2) collides with Lean `def`s and the "Definitions" questions; "accepted" collides with Accept and attempts.jsonl `resolution: accepted`. Suggest "locked/lock" and "Lean statement".

## answers

Q1 "Fully explicit" checkbox: it is in each "Statement" step of the end-of-round review (packages/webview/src/run/Review.tsx:55-58, tooltip "No notation, every argument and universe shown, no coercion arrows"). It switches the Lean proposition shown under "Lean statement" between Lean's default #print and a #print made under `set_option pp.explicit true in set_option pp.notation false in set_option pp.universes true in set_option pp.coercions false in` (packages/runner/src/gate/scratch.ts:111-112, rendered by engine.renderStatements into StatementReview.explicit). It only changes what is displayed, one statement at a time (store review.explicit[nodeId]); it changes nothing in the files or in Accept. Why it exists: the default printing hides implicit and instance arguments and coercions. Those are exactly what telelean's text comparisons cannot see (project report 3.7 item 1: a new instance can change what identical-looking text means), so the explicit form shows which instance, coercion or universe a statement really uses.

Q2 "Claude suggests" vs "Statement 1", "Statement 2": the Statement N steps (Review.tsx:22-25; reviewSteps in webview/src/model/run.ts:474-484) are one step per card whose Lean statement is new or changed in Claude's working copy compared with your files at run start (service.ts:211-239). They are Claude's formalisations of existing cards (the target, the selected premises, adopted suggestions), already written in the files that Accept would apply. Each asks "Does the Lean say what the sentence says?" and is tagged "new statement" or "changed statement". There is no per-statement accept: Accept is all-or-nothing. "Claude suggests" cards (GhostView, core/src/run.ts:235-254; webview/src/run/GhostSuggestion.tsx) are proposed NEW premises, i.e. new beliefs, that Claude offered through propose_assumption after the freeze when the goal did not follow. Claude never writes them into the files. telelean checked with a scratch Lean file that they, together with your selected premises, prove the frozen goal ("closes the gap (checked)"), and flags "gives the goal on its own: it may simply restate it" when none of your premises was needed. They are not part of what Accept applies. "I hold this" (with an optional reason) makes telelean write the card (worded_by: agent) into Claude's working copy, add it to the target's premises, freeze again and start a new round in which Claude must prove the goal again; "No" declines it. Once adopted, a suggestion's statement appears as a Statement step of the next proposal, in Claude's wording.

Q3 Where definitions appear on the main board: definitions are not cards, so they have no node and no arrows in the graph. They appear (a) in the Vocabulary group, which the docs place as the first item of the Assumptions column, collapsed by default (project report 2.2.4). It has a section "Definitions" (webview/src/labels.ts:67), and items get the flag "definition on a statement path" (webview/src/board/VocabularyGroup.tsx:39, tooltip "A definition your statements rely on (D-4: needs your endorsement)"); an item's chevron shows its code and the cards that use it. (b) On any card whose statement relies on a definition: the chip "definitional choice" (webview/src/model/cardData.ts:168, tooltip "Its statement relies on a definition (D-4: needs your endorsement)"), and the definition's name in the card's "uses:" line. (c) During a run's review, only in the "Definitions (N)" step (Review.tsx:156-169), with "Yes, I endorse it" / "No…". New existence assumptions (T.exists) show there as "existence assumption"; on the board they appear under Presuppositions as chips such as "assumes characters exist", and as presup:… entries in footprints.
