DESIGN (USER DECISION, turn 25). It supersedes the to-be-redone clause of AF4 and D2-61, and D2-60's "can be set back to review by hand" rule.
- D1. **"To be redone" counts as finished for the review.**
  - It is never undecided (§4.7). So it does not hide the results, and it does not block Submit. A meaning item is undecided only while it is in review.
  - Fix every rule that reads undecided-ness: the reveal (reveal.ts `resultsState`); Show results' force ending when an item "becomes undecided"; ADV-1's `decided` force and D2-23; reconcile's force ending; Submit's gate and its texts. Grep for every use of `isUndecided`.
- D2. **No Back to review for any item to be redone**, whether its content was kept or taken out.
  - Core refuses it, in `itemGates` and in `backToReview`, with a new core text. For example: "Claude redoes it at Submit review. To review it yourself now, set back to review what it depends on, or use Undo."
  - The webview shows no Back to review link on such items. It shows that sentence instead.
  - Accept stays refused (in review only).
  - Leave core's Decline permission for such items unchanged (RV-3), and add no Decline button.
- D3. **Automatic return.**
  - When an item stops being declined through Back to review (un-Shaky, un-reject, and the plain un-decline of an arrow item), every item that is to be redone because of it comes back with it, in the same action. "Because of it" means its id is in `redo.because`, and nothing else keeps the item to be redone.
  - It comes back to "in review", never to accepted: RV-5 accepts nothing as a side effect. The one exception: a Shaky item that a Reject cascade took out kept its Shaky decline, so it comes back to "declined Shaky", with its note.
  - Remove the returning id from `redo.because`. The item stays to be redone while any remaining cause still keeps it down.
  - Apply this transitively: an item that returns releases the items that are to be redone because of it.
  - Un-reject's inverse-merge writes (V2A-C2, `settleMergedBack`) stay as they are today. Only the statuses the items return with change.
  - The action's cascade notice lists them. For example: "Back in review with it, since they depend on it: …". It never names a hidden item (D2-64).
  - Undo restores everything exactly, so record every touched item.
  - Edge cases to handle, each with a test:
    - **DO-0 question change.** A Result that is to be redone because DO-0 took a source out of its question (`leftQuestion`) does NOT return when the arrow is un-declined: its question changed, so Claude must redo it. Neither do the items that are to be redone because of it. If you need a field that says why `redo` was set, add an optional one, for example `kind: 'cascade' | 'question' | 'judge' | 'take-out' | 'queue'`. Choose and document how records without it are read.
    - **Non-cascade reasons.** Items made to be redone by the judge's revert (§4.11, reconcile), by Submit's take-out (D2-57) or by RV-3 at a queue's end never return automatically.
    - **Two causes.** A Shaky decline of X and a Reject of Y both took Z down. Un-Shaky X leaves Z to be redone, because Y still keeps it down. Un-reject Y then returns it.
    - **Hidden Results.** A hidden Result returns silently (D2-64): no event or text names it.
    - **Results shown.** While the results are shown, items that return to review are undecided again. The results hide again and Show results' force ends, as for any item that becomes undecided.
    - **Undo, Redo, reload.** Undo and Redo of such a Back to review (UN-4–UN-6), and a reload in the middle (the persisted state).
- D4. **Show the cause.**
  - An item to be redone says why, in its detail and as its list row's tooltip: "↻ to be redone: it depends on ‹label›, ‹declined Shaky | rejected | to be redone›", one line per listed cause.
  - `ItemView.redo.because` already carries the listed ids. Add each cause's state, or compute it in the webview from the session's items.
  - When no listed item caused it (the judge, Submit's take-out, a queue's end, or a hidden cause), say "telelean took it out: ‹reason›" instead.
