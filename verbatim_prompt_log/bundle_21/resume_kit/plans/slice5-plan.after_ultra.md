## 2. Contracts (integrator's; builders implement them as written)

### 2.1 Tokens (core `refs/tokens.ts`, 5a)
```ts
import type { CardField, VocabField } from '../freeze/types.js';   // slice 3
export type RefTarget = { kind: 'card'; card: string; field?: CardField } | { kind: 'lean'; name: string; field?: VocabField };
export interface RefSpan { start: number; end: number; target: RefTarget }
/** `#[card:ID]` / `#[card:ID:FIELD]`: ID per ID_PATTERN, FIELD a CardField. `#[lean:NAME]` / `#[lean:NAME:FIELD]`: NAME a
 *  fully qualified Lean name, identifier characters and dots only (never whitespace, `:`, `[`, `]`, `#`, `«`, `»`, U+2039 or
 *  U+203A), FIELD a VocabField. Anything else is plain text. */
export function refToken(t: RefTarget): string;               // throws for a target no token can name (D5-2)
export function parseRefToken(token: string): RefTarget | undefined;
export function refsIn(text: string): RefSpan[];               // well-formed tokens only, in order
export function refKey(t: RefTarget): string;                  // canonical: multisets compare by it
/** Each `#[card:` or `#[lean:` that does not start a well-formed token, with its text up to the next `]` or the line's end. */
export function malformedRefs(text: string): string[];
/** The text a new card's id is derived from (§2.2): each token replaced by its card id, or its Lean name's last component. */
export function idSource(sentence: string): string;
```
- Tokens count only in a card block's `natural_name:` and `rationale:` values and in session prose (answers, Shaky notes, Instructions); glosses, notes after `---` and Lean text never hold one (D5-11). `formatFieldValue` already writes them raw (no `/-`, `-/` or leading `"`).
- Every reader of tokens (core, the runner, the webview's `refs/`, RefText) uses only these functions, never a pattern of its own; a property test checks that RefText makes a chip for exactly core's spans (5f1). A `lean:` token resolves by exact match of its fully qualified name, never by short name or suffix.

### 2.2 Ids (core `ids/`, `edit/ids.ts`, 5a; runner 5b)
```ts
// core ids/registry.ts — `.telelean/subjects/<S>/ids.json` (paths.ts `idsPath(S)`)
export interface IdsFile { format: 'telelean-ids'; version: 1; ids: string[] }        // sorted, unique
/** `salvaged` (the reason, for TL204): the text was not this format, and `ids` are every double-quoted string in it that
 *  matches ID_PATTERN (a merge conflict gives the union of both sides; a stray string only reserves one id more).
 *  `unreadable` (the reason, for TL203): a non-empty text with no such string. */
export type IdRegistry = { ids: readonly string[]; salvaged?: string } | { unreadable: string };
export function parseIdsFile(text: string | null): IdRegistry;                        // null (no file) → { ids: [] }
export function serialiseIds(ids: Iterable<string>): string;
/** Every card id the subject's files name: `id:` lines, the ids the build gave its cards, `premises:` entries, card tokens. */
export function namedIds(m: ProjectModel, subject: string): string[];
/** The same from one file's text: written ids, `premises:` entries, card tokens and the parser's file-level derived ids.
 *  An over-approximation (the build may suffix a derived id), which only reserves more. */
export function namedIdsInText(path: string, text: string): string[];
export function foldText(s: string): string;      // slugOf's transliteration, lower-cased, marks removed (RF-4's matcher)
// core ids/allocate.ts
/** Taken: every block id of every parsed model file (blocks outside a subject and duplicates included, as `add-node`
 *  avoids today); `namedIds(m, s)` for every subject s of m, so an id that a `premises:` entry or a token still names is
 *  never given, even before it is recorded; every id of every registry; D3-54's record ids; and `extra`. Throws
 *  ActionError('internal', REF_TEXTS.idsMissing) without `registry[subject]`, and ActionError('refused',
 *  REF_TEXTS.idsUnreadable) while any registry of the model folder is unreadable (D5-17). */
export function takenIds(m: ProjectModel, subject: string, s: { registry: Readonly<Record<string, IdRegistry>>;
  records?: readonly string[]; extra?: readonly string[] }): (id: string) => boolean;
// core edit/types.ts: PlanContext + ids?: Readonly<Record<string, IdRegistry>>   (add-node and apply-transform refuse without it)
// core edit/ids.ts (F1, D5-4)
/** Writes the `id:` of every card of `subject` whose id is derived, or of `cards` only, as the build gave it (the node
```

## 3. Design

### 3.1 Invariants
- **I1.** telelean never gives one card id to two different cards in the project, nor, within a subject, one a card had before, while every registry of the folder is readable (RF-2 b). The same card coming back (Undo, History revert, a premise item written again, D5-20) keeps its id.
- **I2.** A reference names its target only by card id or Lean name; every name shown, or sent to Claude, is computed from the current model, a docstring mirror inside a session aside (D5-7) (RF-2 a, c).
- **I3.** A frozen card's references hold their targets, present or gone, in slice 3's one table and one whole-state check, with ES-2's exceptions applied inside it; refuse, never repair (RF-5 a). The person's own change to held content is the held value (D5-19).
- **I4.** Claude never adds a reference, nor gives a deleted target a new declaration; new tokens come only from the person's text, as telelean recorded it (D5-8, D5-21).
- **I5.** Nothing about references shows anything a hidden Result holds (RV-6): names come from the masked model, candidates from the view's graph, and the person's tokens, session prose included, are validated on the model the person sees.

### 3.2 Ids over time (5a, 5b; D5-3, D5-4, D5-17, D5-20)
- **Recorded.** Before every write of its common write path, ModelWorkspace records the subject's `namedIds` in the model before the write and `namedIdsInText` of each changed file's new text; a session's start records B's; every in-session allocation records its id before the id is written anywhere. Opening a board writes nothing (AP-12). Allocation also avoids every block id of every parsed file and every id the current files name (§2.2), so an id that a `premises:` entry or a token still names is never given before it is recorded; in a session it avoids every id B and the session's records name. What is left unrecorded is an id that existed only between two writes, made by hand, that no file names any more (D5-18).
- **Monotonic.** Undo, Redo and History revert never take an id out (the registry is not on the board stack); a rolled-back step, a declined premise and an Exit leave theirs in; a premise item written again takes its own id back (D5-20); any other replayed write allocates again and burns its first id.
- **F1.** A derived id depends on the other blocks: with A (`id: cynder-dark`) and an id-less B with the same sentence (derived `cynder-dark-2`), deleting A would make B derive `cynder-dark`, and every reference to A would pass to B. So every plan that changes a model file of a subject also writes the `id:` of every card of that subject that lacks one (`writeSubjectIds`, through the EditSession hook every planner shares), with D3-54's `lose`: the plan that deletes A writes B's `id: cynder-dark-2`. Layout-only plans write none. Sessions already write them (D3-37's `ids` commit, then Apply). The one exception is the board step after Exit or an empty Apply with keep ticks (D3-16): it keeps writing only the kept cards' ids (`planIdWrites` with `cards`), as its confirmation says.
- **No migration.** Nothing is rewritten at upgrade: ids.json appears at the first write or session after slice 5, and a subject's derived ids are written at its first board write, inside that action's Undo step and History entry (the guide says so). Until then, and after that write is undone, a hand deletion can still pass an id to an id-less card with the same sentence (D5-18).

### 3.3 What the person sees (5c1, 5c2, 5f1, 5f2; D5-5, D5-6)
- A token shows as a chip (§4.3) wherever its text is shown as the card's own (the face, "because:", details, review rows, answers, notes, Claude's words), and as its 'plain' rendering everywhere else, through `nameOf`. A label nests its target's own references up to three levels ("…" deeper, or on a cycle).
- A card token resolves only within its subject: another subject's card shows "deleted card" with TL124, a missing one with TL125; telelean's own inputs refuse both (§2.4, §2.7), so they come only from hand edits. A deleted card's id never comes back as another card's (I1), only as itself, by Undo or History revert; a Lean name comes back only through the person's own edit (D5-21; by hand outside a session, D5-18).
- Review rows render both sides with the Proposed (masked) resolver, so a row differs only where the stored text differs; a chip whose target is named differently in your files says so in its tooltip (§2.8).
- In a session, every name, chip and candidate on the Proposed view and in the session's panels comes from the masked model or graph, and `refProblems` (session prose, the premise Accept's Why, slice 4's drafts) runs on the model the person sees: a hand-typed token naming a hidden card is refused exactly as one naming no card.

### 3.4 What Claude reads (5c1, 5c2, 5e; D5-7)
- Every turn and every tool result passes the two choke points (§2.7): the context bundle, step and feedback turns, Shaky notes, "Ask me about" notes, Instructions (S4), answers, Earlier answers from decisions.json, gate findings, freeze texts and thrown tool errors. So Claude reads ‹sentence› [card ID], never a raw token outside a raw span.
- **Raw spans.** Every text that tells Claude a sentence or Why value to keep or restore exactly quotes it in a raw span, so its stored form survives the rendering: G5's quoted sentence and Why lines; slice 3's frozen texts, its FROZEN BY THE PERSON values and `personChangedFreezes`; slice 4's transform turn ("frozen: keep exactly: ‹value›"); the feedback turn's "kept: the person froze it" parts; `heldField`'s value; the tokens in the `reference` texts. The wrappers strip the markers after rendering; a marker in the person's own text is dropped first. The person never sees a marker: §2.7's copies go through `renderForPerson`.
- The files Claude reads with its own tools keep the stored form; the system prompt line (§2.8) explains it.
- **Docstrings** (D5-7). telelean writes `mirrorText` wherever it writes a D-9 mirror (normalise, adoption, D-9's follow on the board, slice 4's typed write), and normalise requires it of every docstring that is new or changed since B. Outside sessions, every board plan that changes a model file of a subject also rewrites each D-9 mirror of that subject whose docstring `isMirrorOf` its sentence but differs from `mirrorText`, in the same Undo step and History entry (a follow-on edit, like F1's ids). The hook reads both on the plan's result, never on the model the plan started from: it re-parses the files the plan changed (markup only, no Lean job), so the resolver sees each card's sentence as the plan leaves it, new and deleted cards included, and rewording a referenced card re-mirrors its referrers in the same plan. A freeze action (`set-freezes`) writes ids only and never re-mirrors (FZ-9: freeze changes change no file; slice 3's id writes, D3-16, and F1's are their one exception). Inside a session, a mirror unchanged since B is left as it is, even when a name in it changed since.

### 3.5 Claude never adds a reference (5c2; D5-8, D5-21)
For every card block of the session's subject in the judged state, `referenceFindings` checks:
- **`added`:** for `natural_name` and `rationale`, the multiset of tokens lies within B's value's (empty for a new block) plus those of the values telelean recorded for the person on that field: live typed units (S4: a `line` unit; a `premise` unit's `naturalName` on the `natural_name` of the card its item's ledger `premise` entry wrote), and the Why telelean wrote on a written premise card (the ledger `premise` entry's `rationale`, recorded when the write is planned; it counts while the entry stands, whatever the item's status: accepted, declined Shaky, cascaded to be redone with its content kept). So Claude may keep, reorder or drop the person's tokens, never add, forge or move one.
- **`docstring`:** a declaration of the subject whose text, docstring included, is new or differs from B's holds no token, unless it is a value telelean recorded for the person.
- **`revived`:** a `lean:` token in a sentence or Why of B, of any subject, whose target B lacks and the judged state has, unless the person's live typed text declares that name, or uses it while no frozen card's reference holds it (S4; D5-21). A name a frozen card's reference holds is held as absent (§3.6): that is a `held` finding, with no exemption for a typed use, which only the person's own typed declaration revalues (D5-19), and slice 4's analysis refuses a transform that would need Claude to declare it (§3.6). A name that a `held` or `other-subject` finding already reports is left to it (one message).
- At step purposes, slice 3's two-value rule applies (§2.4).
- The tools refuse at once: `propose_assumption`'s sentence and `why_needed`, and an `add_card` sentence (if built), with §2.8's texts. The check sits beside the tool's other checks, never in `adoptionPlan`, which also writes the person's typed premise sentence (D4-14).

### 3.6 References hold their targets (5d; D5-9, D5-10, D5-19, D5-21, D5-22)
- **Holders:** every frozen sentence or Why, whatever its reason. Expected at B (standing, foreign, session-start, own `{ from: 'base' }`): `heldFields` over B. Own freezes, accepted items and slice 4's TransformFreezes: their stored held maps, now computed by `holdingMap` with the frozen sentence and Why targets as `fields` (own freezes by the runner's `freeze()`, with §2.5's `{ from: 'base' }` test; accepted items through `freezeAtAccept`, with `acceptCovers`' sentence and Why targets); a TransformFreeze of a sentence or Why by `pendingHolds` from the typed write while it is pending, and by `transformHolds` on the model of whichever judgement values it (§2.5: the typed judgement, a later judge-apply, or the queue end). A TransformFreeze's map binds as D5-19 says (below).
- **What is held** (D5-9): `#[card:c]` holds c's sentence; `#[card:c:sentence|why|kind|stance|source]` that field, as text; `#[card:c:statement]` c's statement declarations by their held values (meaning, and text without the docstring) with their meaning closure, or, while c has none, the empty statement (kept empty, FZ-2); `#[card:c:dependencies]` c's Dependencies: no arrow into c removed or added, its mark unchanged (compared by `deps`); `#[lean:n]` n's declaration (held value and closure) and its gloss; `#[lean:n:declaration|gloss]` that one; `#[card:c:proof]` nothing (FZ-4: no proof is held). A held sentence or Why holds what its own tokens hold, each target once. A target that is gone is held as absent (D5-21): no card or declaration may take its place.
- **ES-2's exceptions, inside the check** (FZ-4: held never overrides them). `refExceptions` comes, at step purposes, from the running step's inference only (its target, the ends of its selected arrows, and whether its question is its mark), and at `stage`, at `final` and in the backstop from every inference; so a change one step was allowed stays allowed afterwards (at later steps through the two-value rule), and no step gets another inference's exceptions. An arrow added into such a target passes a held Dependencies key, and when that target's question is its mark, the mark may go with it (AR-5: the accepted premise replaces it, as part of the person's Accept); removals are still compared, and so is the mark otherwise. A held empty statement of a card at an end of such a selected arrow may be filled. A target's proof is never held (above).
- **The check:** slice 3's step 3 compares every held key, Lean name or field, with `heldValueOf(current, key)`, the keys of the TransformFreeze maps that bind (below) included; its two-value rule, `fresh`, `conflict` and one-message rule are unchanged, since they dispatch by key.
- **The person's own changes** (FZ-3 bullet 2e, FZ-1; D5-19). A held key that a live TransformFreeze covers (a field key that is its target; a Lean name bound by the card whose statement is its target, or named by the vocabulary item whose declaration is its target), typed or follow-on (a field a detach wrote, §3.7; a trashed card's field), is compared only through that TransformFreeze: its own table entry when the key has a reason (slice 3's step 2: its pending text, or the value of the judgement that valued it), and in every case slice 4's typed units, which keep what telelean wrote in place (D4-33); every holder's expectation of it but an accepted item's is set aside. In their place, that TransformFreeze's own held map (its `held` while pending, its valued map after; §2.5) holds what the new words refer to. It binds when its key has a reason of its own, or when it sets aside some holder's expectation, with those holders as its holders (`via` its card): so a frozen or held field's new references are held, and an unfrozen, unheld field's hold nothing. heldFields' walk stops at such a key and continues through that map, never through B's version beyond it, so what the old words referred to (a target the person's change dropped, or trashed) is no longer held through them. This is derived at every judge and stored nowhere, so it goes with the TransformFreeze (a rollback, a Retry, the person's Unfreeze of that field, the Reject of its typed item, the session's end). An accepted holder whose `frozen.held` names the key leaves accepted through slice 4's confirmed Submit cascade (RV-5 bullet 3), which sees detached and trashed fields as keys of `typedKeys` and `plan.keys`. `frozenChangesOf` lists a held row only for an expectation not set aside. A stored map (an own `{ from: 'state' }` freeze's, a TransformFreeze's) is flat: what it reached through a field the person changes later stays held until that map goes (its Unfreeze, the session's end), an over-hold that fails closed (D5-19's residual). Outside a session nothing is needed: a standing freeze names a target, not a value.
- **During a transform step** (S4). From the typed write on, a TransformFreeze of a sentence or Why holds its references (D5-19 says when its map binds): the runner sets its `held` at the typed write with `pendingHolds` on the `typed` commit, follow-on ones included, and once a judgement values it (slice 4's typed judgement before Claude's turn, when its references' declarations all have keys there; else a later judge-apply, or the queue end), its map is `transformHolds` on that judgement's model, for the rest of the session. The check compares those keys like any held key, never excused by S₀ in the step that wrote them (S₀ is before the typed write), pending or valued. So in the step that writes it, and in every later one, Claude cannot change a field the person's new sentence refers to, nor one that a detached sentence still refers to through its other tokens. `transformScopeOf` (its `sessionFrozen`, computed at the step start in `run/step.ts`) leaves out of `open` (and out of `arrowsInto`, for a held Dependencies field) every key reference-held at S₀ (heldFields, and the own, accepted and TransformFreeze maps): a held field, and a Lean statement or vocabulary declaration whose declarations are held names; and every field the transform's typed and detached sentences and Whys refer to, with every statement and declaration in the meaning closure of the declarations they refer to (through the view's model). The turn lists them under HELD; the window, which computes the same on the view's state, shows such a field "held by “‹A›” (it refers to this)", and a fuzzy one is a problem (§2.8). A TR-13 statement or definition dependent left to Claude whose declarations are reference-held (by a card frozen for a reason other than accepted, as D4-21 counts, since an accepted holder returns to review through the Submit cascade; or by this transform's typed and detached sentences and Whys) is a problem too (§2.8's "“‹d›” relies on ‹x›, but …" texts): Claude could not fix it.
- **Absent names** (D5-21). A held key expected absent through a reference (a Lean name that a dangling `lean:` token names, held by a frozen card directly or through held sentences and Whys) is sent to Claude with `revived`'s text (`CLAUDE_REF_TEXTS.revived`), never slice 3's held text, and shown to the person with §2.8's `revived` text, under `held`'s code. In slice 4's analysis (S4), a MUST DEFINE name held so is a problem (§2.8): Claude would have to declare it, and the frozen card would then refer to Claude's declaration. A typed declaration of the name in the transform takes it out of MUST DEFINE (TR-12 c) and is revalued through its own TransformFreeze (D5-19).
- **Around the check:** `frozenChangesOf` emits held field rows (D3-48's dialogs, D3-49's keep set); `unmeetable` maps a field key to its card's lines in `snapshot.blocks`; `unfreezeRequestProblems` answers a `{ card, field }` item held by a reference with its holders; `deleteCardProblems` refuses a card with a held field; `proposeArrowProblems` refuses an arrow into a card that is not the running step's target and whose Dependencies a reference holds, and `removeArrowProblems` one into any card whose Dependencies a reference holds (§2.8's texts); a whole-model step's `fuzzyStatements` leave out an empty statement held empty, as they leave out one frozen empty; the views carry field holds (`StateJudgement.held`, and `boardFreezesView` outside sessions), so a field shows its chain mark; the backstop runs the same check on F, with `refExceptions` from every inference.
- **Memo.** Each field's one-level holds on B and heldMap(B, …) are memoised per B; heldFields' walk is assembled from the entries and the live TransformFreezes at every call, so a freeze, an Unfreeze, an Undo, a Redo or a TransformFreeze changes the holds at the next judge.
- **Other subjects** (D5-10): at every purpose, `otherSubjectRefHolds` keeps at B the declarations of the session's subject that other subjects' sentences and Whys reference, with their meaning closure and glosses, absent ones included, under `existing-changed`'s token `other-subject`. The view shows them "held by “‹A›” of ‹S› (it refers to this)". It binds Claude only (FZ-1): a value telelean recorded for the person (S4's typed units) is not refused.
- **A premise not written yet** (D5-22): an accepted Add premise's Why holds its references only once its card is written (its write's step 4 computes `frozen.held`). While an accepted Add premise whose Why holds a token is not written (its write due after a failure), Formalize for dependencies, Retry step and Submit review are refused with §2.8's text.

### 3.7 Deleting or changing a referenced card (5c1, 5c2; D5-12)
- **The board's Delete** (outside sessions; Delete anyway): the dialog lists the cards whose sentence or Why refers to the card (`referencedByIn` on the view's graph), frozen ones marked; their references then show "deleted card".
- **Claude's deletions:** a Delete item (`delete_card`) and a vocabulary removal item list their referrers on the masked model (`ItemDetailView.referencedBy`), so accepting one says which references will show "deleted card".
- **A transform** (TR-13, S4): its dependents analysis adds, for each trashed card or vocabulary item, `referencedBy` with the `reference` via (a referrer in the window counts by its draft's text). A dependent through a reference needs no choice of its own and is never a frozen-dependent problem (D5-19). Unless it is trashed too, telelean's follow-on edit detaches its tokens to the trashed target (`detachRefs`): a unit owned by the trashed target's typed item (so one Reject brings back the card and every reference it detached), which may touch a frozen card (TR-15). Every field it writes is a follow-on key (`typed: false` in `plan.keys` and `typedKeys`, D4-34) and gets slice 4's follow-on TransformFreeze: no reason of its own, no "frozen: you typed it" row, no keep tick. So every holder's expectation of that field takes the detached words (D5-19), what the detached field still refers to is held in their place only when the field is frozen or held (§3.6), and the Submit cascade sees the key. The trashed card's own fields are among `plan.keys` too (§2.6), so every expectation of them, a stored map's included, is set aside as well. The words come from the target's label in the judged state, or in B (`planTypedWrite`'s `base`) when its current sentence is Claude's (it differs from B's and from every live typed unit), so Claude's wording never becomes the person's text. When its current sentence is Claude's and B lacks the target (a card Claude made in this session: a written premise, an `add_card` card), the referrer is not detached: the window shows the problem "“‹A›” refers to “‹c›”, which Claude made in this session: take the reference out of “‹A›” in this transform, or delete “‹A›” too." (§2.8) until its draft holds no such token or it is in the trash. Its row reads "Its reference becomes words: ‹text›." (`TransformDependent.reference`, `choices: []`, "Delete it too" offered); the cards that refer to a detached field are warnings ("Refers to it, and will read: ‹text›."), as for any changed field (below); the end confirmation lists the detach under the trashed card as telelean's follow-on edit, never as something the person typed.
- A card whose referenced field changes but stays (a detached field included) is a warning ("Refers to it, and will read: ‹text›."), frozen or not: its reference keeps resolving, and its hold takes the person's value (D5-19). A card of another subject that refers to a trashed vocabulary item is a warning too ("“‹card›” of ‹S› refers to it, and will show “deleted card”."): its subject's files are not this transform's.
- **Tokens to trashed cards.** A draft's own token to a card in its trash, or in a queued transform's, is refused (`refProblems`' `trashed`). At Submit review, a queued transform whose typed text holds a token to a card that another queued transform trashes is stale (slice 4's §3.8 step 2), with §2.8's text.

## 4. The UI (webview; 5f1, 5f2)

### 4.1 RefInput and RefPicker (D5-5, D5-14)
- The field shows the stored form, as GitHub's editor shows `#123`; a live line below it, "Shows as:", renders the chips (inert while editing: tooltip only) and the preview's problems.
- **Opening.** A typed `#` opens RefPicker only at the field's start or after whitespace or an opening ( [ “ " ‘; a pasted `#` never does, nor one typed during IME composition. The query is the text after `#` up to the caret, spaces included. The picker closes by itself when its query matches nothing and ends with a space, leaving the text as typed (as after Esc).
- **Focus.** RefPicker is a listbox that never takes the focus: the input keeps it, with role=combobox, aria-expanded, aria-controls, aria-autocomplete=list and aria-activedescendant on the highlighted row; rows are role=option and show the kind glyph. The picker's root (not only its rows) and the "Shows as:" line prevent mousedown's default, so a press anywhere on them never blurs the input, and InlineEdit's blur-commit never fires mid-pick.
- **Where it renders.** Through Popover's `container` (slice 4) into the nearest open `<dialog>` or `.tl-popover` that holds the input, else into document.body; never inside the canvas layer. It is placed from the input's client rect, follows the `tl-canvas-view`, scroll and resize events, and closes when the input leaves view. Popover gains `keepFocus` for it: no focus move on open, no tabIndex.
- **Keys.** While the picker is open, RefInput listens for keydown on window in the capture phase, before Popover's and Modal's document-level and native handlers. It ignores every keydown while `event.isComposing` is set or `keyCode` is 229, so the Enter that commits an IME composition commits it and nothing else. Otherwise it takes ↑ ↓ Enter Escape, ← only in the field list, and → only in the card list with the caret at the end of the query, with preventDefault and stopPropagation, so InlineEdit's commit, the A|P box's form submission, a dialog's Enter-to-confirm, a modal's cancel, a Popover's Escape and slice 2's list keys never see them; any other ← or → moves the caret as usual, so a typo in `#query` can be fixed. ↑/↓ move; → (or a click on ›) shows the highlighted card's fields, those of its kind; ← goes back to the cards; Enter inserts `refToken` in place of `#query`, by selecting that range and `document.execCommand('insertText')`, so the browser's own undo takes it back (UN-4 4b); Enter with no row closes the picker and inserts nothing; Tab closes it without preventDefault, so the focus moves as usual; the first Esc closes only the picker and leaves `#query` as typed (RF-3), and the next Esc goes to the host as before (CM-2); Backspace past `#`, or a blur, closes it. The integrator's Playwright run checks that the webview records the insertion for undo; if it does not, RefInput's own one-step undo of its last insertion is added then (noted in §8).
- **Preview.** RefInput runs `refProblems` on the view's graph (`resolverOfGraph`, `leanUnknown: 'allow'`), shows each problem under "Shows as:", and neither Enter nor a blur commits while one exists: after a blur, InlineEdit stays open with the problem shown, so a click elsewhere never sends text the host would refuse and throw away (UI-16's case); Esc still cancels. A refusal's text may differ from the host's for another subject's card (the host names the subject).
- RefInput is used only on prose fields; no Lean field opens it (RF-3).

### 4.2 Candidates and search (RF-4, ★D6; D5-13)
- **Candidates:** the view's graph: this subject's axioms and propositions (never a provisional card, nor the card being edited) and every vocabulary item of the band, own and foreign (TR-10 c); in a session, the Proposed view's masked graph (I5); in the transform window, never a card in its trash or in a queued transform's trash.

## 5. Undo and persistence
- **Board stack:** an edit with references is the same edit-node or add-node step; F1's `id:` lines and the re-mirrors of stale docstrings (D5-7, names as the step leaves them) join that step and its History entry; a freeze action's step writes ids only, never a docstring. ids.json is never on the stack, so Undo, Redo and History revert never shrink it.
- **Session stack:** unchanged; references in answers, notes and Instructions belong to their existing actions; a premise item's card keeps its id through the Undo and Redo of its Accept (D5-20).
- **ids.json:** monotonic, atomic, one queue per file, only growing in an open window; a missing file is empty; one that is not its format is read leniently and rewritten cleanly at the next record (TL204); an unreadable one is never overwritten, refuses every allocation and session start in the folder (TL203), and recording skips it (D5-17).
- **run.json:** held maps may hold field keys; a pending TransformFreeze's `held`; `ItemRecord.cardId`; the ledger `premise` entry's `rationale` (all additive). Allocations go straight to ids.json.
- **Reload:** a RefInput's text persists as its field's text already does (ES-6); Claude's resolver is a markup-only model of ws/ until the first check (§2.7).
- **Reversal:** the slice-5 patch (AP-4), after finishing or exiting open sessions (their held maps, `cardId`s, pending holds and premise rationales). ids.json stays, ignored by older code; tokens stay in the files as text, shown raw by the older board; F1's `id:` lines and rendered mirrors stay (valid markup).
