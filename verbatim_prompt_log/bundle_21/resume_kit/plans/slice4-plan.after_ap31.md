*Designed for the simplest sound mechanism (the lesson of AP-24 and AP-31). A transform is data, a draft. One pure analysis decides what it changes, what it needs and what blocks it; one pure planner writes it. **What you type is carried out at once**, as one decision of the session: telelean writes it into the working copy through slice 2's write queue, judges that state with a build, and takes the write back whole when the judgement finds a failure on visible content that the state before it did not have. Your edits belong to each card's ordinary review item, badged "you typed it" from telelean's own ledger; your typed fields become ordinary own freezes. **Only Claude's part waits for Submit review**: a scope (the fields you left to Claude, slots, instructions, the tick), carried out by one ordinary step whose S₀ is the judged head, so slice 2's step limits, rollback, reconcile and backstop, and slice 3's one freeze table and one check, apply unchanged, with one baseline. Outside a session the window is a provisional session (a real run, so slices 2–3's lock, base, freezes, stack, reload and Exit apply); a transform that needs no Claude ends it and is written as one board step, after a confirmation. Anything that would need repairing is refused with a sentence.*

**Slice 4 = ★D8 (a) item 4, the transform window:**
- **Transform cards…** (a labelled Context Menu button and a right-click entry): with no session, it opens the window in a provisional session, with every other card of the subject frozen (ES-3, INITIATING 2; D3-1 made real); in a stage, on the Proposed view, it opens a window whose typed part is carried out when you submit it and whose part for Claude waits for Submit review (RV-9, ES-9; D4-45).

- **`draftFromModel(i: { model: ProjectModel; graph: TlGraph; subject: string; keys: string[]; mode; items?: readonly ItemRecord[]; drafts?: readonly ItemDraft[]; base?: ProjectModel; ledger?: readonly LedgerEntry[]; targets?: readonly string[]; frozen?: Readonly<Record<FreezeKey, readonly FreezeReasonView[]>>; locks?: Readonly<Record<FreezeKey, string>>; queued?: readonly QueuedTransform[]; masked?: boolean }) → { draft, original, claude, previous, locked, left: Array<{ key: string; reason: string }> }`.** Exact copies (TR-1) from the view's model, masked while the results are hidden (RV-6). A premise window's card comes from its item's draft (`drafts`, `ItemContent.premise`). Starting states: your copied Sentence, Why, Stance and Source open; the Lean statement, Dependencies and a vocabulary declaration kept (S11); a gloss open; an empty field kept empty; Proof `keep`; a value of Claude's (the working copy differs from B and from every live ledger value of that card and field) open, in `claude` (D4-9); a field the session freezes (any reason in `frozen`) kept, its chip showing those reasons (§3.2); a Delete item's card in the trash; a target's locks (§3.4). Locks: a statement that is not `abbrev n : Prop := ‹term›` ("This statement is not a plain abbrev: change it in its file once no edit session runs (your files must not change while one does)."); a lemma's declaration ("A lemma is a proof, and a transform writes no proofs (TR-14): trash it, or change it in its file once no edit session runs.", D4-37); in a session, each field `locks` names, which another subject relies on ("“‹A›” of ‹S› relies on it: change it outside a session.", D4-57; the runner fills `locks` from `otherSubjectHoldsOf`, §2.9). `left`: another subject's vocabulary ("Vocabulary of another subject can be frozen, but not transformed.", TR-10 c; slice 5 adds referencing), a provisional card, a card the view does not show, and a card or vocabulary item that a queued Claude part holds ("“‹c›” is in Claude's part of “‹label›”, queued for Submit review: drop it first to transform this card again.", D4-59).
- **`typedLeanProblems(i: { field: 'statement' | 'declaration'; text: string; name?: string }) → string[]`** (TR-12 a, S10). A statement passes g0's single-term rule (`termProblems`, exported, with the statement wording). A declaration is exactly one declaration (`markup/decls.ts`) named `name`, with a keyword among `axiom def abbrev structure inductive class instance opaque` and no other command, in which `scanForbiddenText` finds nothing (`init` attributes and hygienic names included, AP30-1); COMMAND_WORDS and GHOST_COMMAND_WORDS hold every command keyword of the pinned toolchain (4a), so no command hides inside a declaration's span. An `axiom` passes the shape rule's textual part (its type is a sort, or an arrow type ending in `Prop` or a type name; "over sorts" is checked on the elaborated facts, §3.3, IMP-27); never a theorem (a lemma's declaration is locked, D4-37; a declaration whose elaborated type is a proposition is refused on the scratch's facts, §3.3, R2-11); never a Prop axiom ("A Prop axiom here would be a belief no card holds: add an axiom card instead.", D2-40).
- **`originalKeyOf(original)`** (R2-6): hashes the copied values only: the set of keys and, per key, its Kind, Lean name, each field's value (canonical text; Dependencies as the sorted entries and the mark) and whether Proof is offered; never `kept`, `trashed`, Claude's marks, locks or masks, which follow the session (its freezes, items and targets).

### 2.5 Protocol (core `protocol.ts`; types and validators in 4a, routing in 4h)
Every message takes `requestId`, is answered by `actionResult`, is in `RUN_MESSAGE_TYPES` (the ES-9 lock never refuses it), and has a hand validator that returns a fresh object, drops unknown fields (`origin`, `claude` marks and `consented` never survive, D4-27, D4-49) and refuses `__proto__` keys.

| Message | Payload | Validator rules |
|---|---|---|
| `openTransform` | `{ subject, from, runId?, stage? }`; `from` is `{ kind: 'cards'; cards; vocab }` or `{ kind: 'decline'; items: [{ item, rev }]; instructions? }` | cards: ids; vocab: Lean names (`leanName()`); together 1–`LIMITS.transformCards`, distinct; items: 1–`transformCards`, distinct, rev 0–`LIMITS.revision`; instructions ≤ `LIMITS.instructions`, may span lines; `runId` and `stage` both or neither, and neither only with `cards` (the provisional start) |
| `saveTransformDraft` | `{ runId, window, rev, draft }` | window a token; rev 0–`LIMITS.revision`; `transformDraft()`; answered with the window's new `analysis` |

`transformDraft()` checks only the draft's shape (IMP-28): format and version exact; cards 1–`LIMITS.draftCards`, keys `card:‹id›`, `vocab:‹leanName›`, `new:‹0–9999›` or `premise:‹item id›`, distinct; a vocabulary card (a `vocab:` key, or a `new:` key with `leanName` and no `kind`) has only `declaration`, `gloss`, `trashed` and, when new, `leanName` (a Lean identifier ≤ 200 characters); an axiom or proposition card has `kind` and only CF-2 fields; a premise card has only `sentence`, `why` and `statement`, never `trashed: true`; sentence, why and gloss one line ≤ `textLength`; stance and source their enums or null; statement and declaration ≤ `LIMITS.leanText`, may span lines, no NUL; dependencies' sources ≤ `listLength`, distinct, never the card itself, never with `fromNothing`; proof `keep` or `clear`; `nextNew` above every `new:` key; instructions ≤ `LIMITS.instructions`; dependents ≤ `listLength` entries, each a `DependentChoice`. ### 3.1 The provisional session (ES-3, INITIATING 2, EDIT SESSIONS 1; D4-2)
- **Opening.** "Transform cards…" with no session posts `openTransform { subject, from: cards }`: Current view; at least one card or vocabulary item of the board's subject; no provisional card.   - the session at phase `transform`, stage 0, `claudeStarted: false`, with slice 3's freeze snapshot and `start.transform` = the selection (§3.11);
  - the window record, from `draftFromModel` on the board's model (= B), with its analysis.

  RunState is `review`, so `runLocksBoard` locks every board of the folder (ES-9). No consent, no Claude, no Lean.
- **In phase `transform`** the runner reads B as the board's ProjectModel and facts (ModelWorkspace, whose files equal the base commit; drift refuses Submit), so nothing is built. Freeze actions work (FZ-9), with values `{ from: 'base' }`, since the working copy is B.
- **A session with no inference** (a transform-started one, until a Formalize; IMP-4): its `CheckContext.selection` is `{ subject, target: '', premises: [], adoptedGhosts: [] }`, which the engine's `validateContext` accepts at session purposes (4g); `RunView.target` is `''` and `premises` `[]`, and `PersistedRun.selection` likewise (4h). ### 3.2 Field states, changes, the outcome and the problems (TR-1, TR-4, TR-5, TR-15)
- **States are the transform's own** (D4-10, D4-31; F3, UI-5, UI-11). Each field's chip shows its effective state:
  - **kept**: "kept as it is (this transform)", or, for a value you typed, "frozen: you typed it" (your own freeze once carried out, D4-52);
  - **kept empty**: "left empty (this transform)", or, for a field you emptied and kept empty, "frozen empty: you emptied it";
  - **open**: "open: Claude may change it"; **fuzzy**: "Claude fills this"; a field you cleared: "Claude rewrites this (it keeps its old value until then)" (D4-55);
  - a field the session freezes (any reason but accepted, or held: `claudeMayChange`): "frozen in this session (‹reasons›)", with the rose lock; its chip offers neither open nor fuzzy ("Frozen in this session (‹reasons›): unfreeze it first."); a field frozen only by accepted items: "accepted: returns to review when you submit", and open and fuzzy stay offered (D4-21: the decision's confirmation returns those items to review);
  - a field another subject relies on, in a session: locked (§3.4, D4-57).

  Typing a value that differs from the original sets kept, and a typed non-empty value cannot be set open ("You typed it: it stays frozen. Put back the copy, or clear it, to let Claude change it.", D4-31); clearing a field whose original was not empty makes it fuzzy, "Claude rewrites this" (TR-5, D4-55), and the chip can make it kept empty, a typed empty value; a field edited back to its original value takes its original state back (UI-11). The window's Context Menu Freeze and Unfreeze are real session freeze actions (§4.2) that also set the chip: Freeze sets kept or kept empty; Unfreeze removes the session's reasons and sets an untyped field open or fuzzy; on a field kept only by its chip, Unfreeze is a draft edit that sets it open or fuzzy ("Opens it for this transform: it is not frozen in this session."); on a value you typed it is disabled with D4-31's text. Only real freezes are called "frozen" (D4-10).
- **Changed** (TR-1 b): a field value that differs from `original` (Dependencies compared entry by entry), a new or trashed card, a Kind change, a cleared proof, a dependent's choice other than `keep`. State changes alone never count.
- **Needs Claude** (TR-15), any of: a fuzzy field (a cleared field and a slot included); instructions not blank; "Claude may add cards"; an open Lean statement on a card whose sentence changed; a dependent left to Claude (`claude`). Each gives a reason (`TRANSFORM_TEXTS.reasons`). Typed Lean that names something not defined is a problem, never a reason (D4-54). D4-39's may-break proofs are no reason of their own: the Lean they come from already is.
- **Outcome.** Start context: needs Claude → `claude-step`; else changed → `direct`; else `start-session`. Stage context: needs Claude → `carry-out-claude`; else changed → `carry-out`; else `nothing` (the window closes; a decline window's items stay in review, TR-9 b). A premise window never needs Claude: changed → `carry-out`, else `nothing` (§3.7, D4-58).
- **Problems** block Submit:
  - every TR-12 (a) failure; the TR-12 (b) and (c) problems of §3.3 (the scratch's own, an unknown name, a typed piece relying on a declaration the window leaves to Claude, a typed piece using a name that this draft deletes or that a Reject's cascade takes out, R2-7 and D4-62, a typed proof, R2-11); a cycle over drawn, solid and draft arrows (AR-3); a typed Dependencies source that a Reject of the decision takes out (§3.4): "“‹W›” is taken out with “‹A›”, which you trash: remove it from “‹Y›”'s Dependencies, or keep “‹A›”." (D4-62);
  - a dependent with more than one choice and none chosen (`choices.length > 1` and its key not in `draft.dependents`), or with a choice its context does not offer (§3.4); a dependent with exactly one choice takes it (a session target's Keep it; a direct dependent with no D-11 rewrite, which the direct confirmation lists, §3.6), and one with none is listed only (arrows, may-break proofs, slice 5's `reference` dependents; §2.1); in a session, a frozen holder of what you change (D4-53): "“‹c›” relies on ‹x› and is frozen (‹reasons›): unfreeze it, or delete it too.", with [Unfreeze them]; a field left to Claude that `claudeMayChange` refuses: "You asked Claude to fill it, but it is frozen in this session (‹reasons›): unfreeze it, or type it." (a fail-safe: the chip refuses it, above), or "…but frozen ‹cards› rely on it: unfreeze them, or type it." for a held one;
  - in a session, a change, a trash or a field left to Claude that another subject relies on (D4-57): "“‹A›” of ‹S› relies on it: change it outside a session." (a fail-safe: the field is locked);
  - a new vocabulary name that is not an identifier or clashes; a kept empty sentence on a card that is not new;
  - a new card with a typed field but a fuzzy sentence: "Type the sentence of a new card whose other fields you fill, or clear them to let Claude make the whole card." (D4-15); a typed arrow from or into a slot; a vocabulary card whose gloss you type while the write leaves it without a declaration (a new card's fuzzy declaration, or a dependent's declaration the write empties): "Type the declaration of a vocabulary card whose gloss you write, or leave both to Claude." (D4-15, R2-8 generalised; R5 removes the other case, since a cleared declaration is not emptied);
  - an axiom made a proposition with neither a typed source nor the mark: "An axiom becomes a proposition only through what it follows from: add an arrow into it, or mark it Follows from nothing." (D4-36);
  - a changed Lean statement on a card whose proof is kept: "“‹c›”'s proof proves its old statement: clear it (prove it again after the session, with Formalize for dependencies)." with [Clear the proof] (D4-20); not on a session target whose proof is its Result's, which is taken out to be redone instead (§3.4, IMP-9);
  - §3.4's refusals for kinds and session targets.

### 3.4 TR-13, TR-11 and session targets (D4-13, D4-19, D4-20, D4-21, D4-39, D4-48, D4-53, D4-57, D4-62)

So a window card that relies on it is a dependent like any; every other dependent of it is in the cascade. The one exception is a taken-out card whose files' version relies on what the window itself changes (a declaration you retype).   - "Delete it too" moves the dependent into the window's trash; its own dependents join the list. Restoring it from the trash removes it from the draft, and it returns to the list with no choice (LC-18). It is refused on a card or vocabulary item that a queued Claude part holds ("“‹c›” is in Claude's part of “‹label›”, queued for Submit review: drop it first to transform this card again.", D4-59, D4-43), and the runner's window checks refuse such a key in the trash (§3.7).

### 3.5 The write (`planTransformWrite`, 4c)
One composition on EditSession, in this order, in session mode (the decision write) or direct mode (`apply-transform`). Every value it leaves is recorded, in session mode, in the ledger `transform` entry: per owner and target `fieldText(after)` for every key of `writes`, and the exact `lines`, each with the item that owns it (`item`: a follow-on value or line takes the item whose change caused it, such as a trashed card's Delete for the `premises:` entries its trash removes elsewhere; §2.2). D-11's spans (direct mode, step 5) were computed on the unedited text: each is mapped through `EditSession.mapOffset`, and the plan refuses (`unsafe`) when an earlier edit replaced it (IMP-23).

0. **The Rejects' take-outs** (session mode; §3.4, D4-62). Steps 6 and 8 say what `reject` holds. Slice 2's cascade over `session.deps` gives `rejectOut`, which never holds an item of `inWindow` and never passes through one. `planItemRevert` reverts each item of it once, first, so every later step plans on their B versions; step 9's `redo` leaves them out.
1. **New cards** (not slots): a block in the subject's Inbox module as `add-node` writes it, with an explicit id from `newCardId`. On a Redo, that is the id `session.reuseIds` recorded for its key when no card of the model holds it (the same card coming back, §5.1), before any reserved test. Otherwise it is `deriveId` (taken: B, the working copy, the ledger's cards, the ids the freeze records name (D3-54) and the draft's other ids; TR-2 c). The block gets the typed fields, and no `worded_by`. A typed statement goes in an abbrev after the block, with its `lean:` pin and the D-9 mirror of its sentence as its docstring, plus `axiom n.holds : n` for an AXIOM. Session mode: a ledger `card` entry (`step: transform:<id>`, `transform`, `kind`); its bound declarations belong to its card, as every card's do.
2. **Vocabulary:** new declarations at the end of the subject's vocabulary module namespace, in the scratch's order (what a declaration uses first, §3.3), each with a `created` entry in session mode; a changed one by `replace-decl`, its docstring kept; a gloss by `set-docstring`.
3. **Field lines** by `setField`: sentence, Why, stance, source. A typed sentence on a `worded_by: agent` block drops that line (CF-6, G5; a `lines` entry). Session mode never rewrites an existing statement's D-9 mirror (D4-56); direct mode keeps D-9's board follow (the mirror updated when the docstring equals the old sentence, as `edit-node` does).
4. **Statements of existing cards:** `replace-decl` of the abbrev, written with the mirror of the card's sentence as the window leaves it (part of your typed value, D4-56); or, for a card without one, an insert with its pin (and a `.holds` axiom for an AXIOM).
5. **Kinds:** P→A through `planKind` (`holds-theorem-to-axiom` or `add-holds-axiom`; the incoming entries and the mark removed); A→P (through a typed source or the mark, D4-36) sets `type:` and keeps the axiom as pending. Direct mode: D-11's rewrite for dependents marked `rewrite`.
6. **Dependencies:** `premises:` entries added and removed per the draft's diff; the mark set or removed (never together with entries, B.6). Session mode: removing an arrow Claude proposed (an arrow item in review or accepted) is that item's decline (DO-0) in the decision (`reject`, its cascade taken out in step 0), so its entry goes by slice 2's machinery, never as yours.
7. **Cleared proofs:** `remove-holds`, archived in direct mode: unproved, never pending (TR-4). Session mode: the removal is recorded as a ledger `proof-broken` entry (`step: transform:<id>`), so its item is slice 3's Proof broken item, labelled "Clear proof ‹card›" (§3.10), and D3-47's and D4-20's Formalize refusals apply.
8. **Trash** (TR-3 b): `delete-node`'s pieces (the block, its statement, its `.holds`, archived in direct mode, and the entries naming it in other cards' `premises:`), or `remove-decl` for a vocabulary card. Session mode: trashing Claude's Add (an item in review or accepted) is that Add's Reject in the decision (`reject`). Its cascade is taken out in step 0: its dependents in review, to be redone or declined Shaky are reverted and become to be redone, accepted ones lose their Accept too, and the window's own items are never touched. The preview shows them in `touched` and `rejectAccepted`. Claude's arrow items into or out of a trashed card are declined with it (DO-0, `reject`, their cascades in step 0 too), so their ledger entries stop counting by slice 2's rule. An item in review that the write leaves with no draft is withdrawn, `replaced-by-transform` (`replaced`, D4-51).
9. **Dependents** (session mode, D4-48): `claude` → the dependent's Lean emptied (a card statement: its abbrev, pin and an AXIOM's `.holds`; a vocabulary declaration: removed), each a key of Claude's part with its old text (`reformalise`), its ledger value marked `emptied` (an allowance, never a value of yours: you typed nothing there); `mark-broken` → a ledger `proof-broken` entry (`step: transform:<id>`): the proof and `proofMaterialOf` taken out; the targets' Results and the hidden Results the runner computed (`redoHidden`, D4-46) in `redo`, but those step 0 took out, their content back to B's version (`planItemRevert`). `keep` writes nothing.
10. **Cleared fields are not written** (D4-55): the old value stays until Claude's part replaces it. A field kept empty after you emptied it (a typed empty value) is written empty (a statement: its abbrev, pin and an AXIOM's `.holds`).
- **Its own freezes** (session mode, §3.11): `freezes.own` gets one entry per key of `writes` with `why` `typed` or `deleted`, and one per `follow` key that has a reason in the table (accepted ones excepted: the cascade clears them); `freezes.replaces` lists every key of `writes` that has a standing, foreign or session-start reason.
- It never edits a line or declaration that holds Claude's content, except to replace it whole (a line, a declaration's body, a typed statement's abbrev with its docstring). Slots and `keep` choices are not written. Any `problems` (a LeanOp that could not apply, a span an earlier edit replaced, a cycle) refuse the whole plan.

### 3.6 The direct path (ES-3, TR-15 outside a session; D4-3, D4-16)

### 3.8 Submit transform in a stage: the decision (RV-5 b3, RV-12, D2-64, D3-48; D4-45–D4-48)
1. **Gates:** phase `stage`; no step runs or is queued; not judging; the window is the open one and `rev` is current; its `basis` is the stage judgement's commit (TW-1 keeps it so).
2. **TR-12** (a), then (b) (the scratch, reused while the typed Lean is unchanged since the window's last check; kept in the window record).
3. **The analysis**, again, on the stage judgement's state (masked while the results are hidden), with the scratch. Any problem refuses, with the problems in the answer ("‹n› problems block Submit: ‹first›"); an outcome that differs from `expect` answers `needs-confirmation` (`outcome`). Then **D3-48's check** (D4-62): slice 3's `frozenChangesOf` runs on the stage judgement's drafts, with the table as the decision would leave it. Its `out` is everything the decision takes out: its Rejects with their cascades (`rejectOut`, computed as §3.5 step 0 computes it) and `redo`. Its rows, listed as slice 3's decline lists them (no row from a hidden Result or its part), join the confirmation. They are the frozen content that these take-outs would change and that no holder problem of the window covers, since they are no TR-13 dependents (§3.4); left unasked, they would only show as the take-back's `frozen`, after a build.
4. **The confirmation** (RV-5 b3, D2-64, D3-48). When `cascade`, `rejectAccepted`, `takeOut` or step 3's frozen rows are not empty, the answer is `needs-confirmation` (`cascade`), slice 2's dialog, its entries slice 2's CascadeEntries, each with its fate (`to`). It holds:
   - "These accepted items return to review, because your transform changes what they rest on: …" (`cascade`);
   - "These accepted items lose their Accept and are taken out to be redone: …" (`rejectAccepted`: slice 2's Reject rule and text, D4-62);
   - "These results are taken out to be redone: …";
   - slice 3's "These are frozen and would change: ‹list›." (`freeze.frozenChanges`, `yours` false), with [Unfreeze them and submit]. That resends with `confirmed.unfreeze` naming exactly the listed keys and item holders, which the decision unfreezes as D3-48's `unfreeze` does, in its own FreezeDelta (`TransformDecision.unfreeze`). "Keep them frozen at your version" is not offered here (D4-62). A resend that does not name them asks again.

   While the results are hidden, the confirmation always comes when `hiddenNotice` is set (the write writes any Lean, adding, changing or removing a declaration, since a new declaration or instance can break a hidden accepted Result too; or it changes or removes something that existed before the window), with D2-64's sentence, "The results are hidden now: a result you accepted that rests on these loses its Accept too. You will see it when the results are shown.", naming no Result, whether or not the visible list is empty. When `drops` is not empty (the decision's Rejects, of an Add you trashed, an arrow you removed or Claude's arrows of a trashed card, cascade to a source of a queued Claude part), the same confirmation asks D4-43's question for each such part: "This also takes out “‹c›”, which Claude's part of “‹label›” holds: drop that part with it?". Cancelling leaves the window open. Resending with `confirmed.cascade`, `confirmed.drops` naming exactly the parts asked about and `confirmed.unfreeze` naming exactly the frozen rows listed (a different list asks again), goes on; the decision drops those parts in its own records (`drops`, restored by its Undo).
5. **The decision write** (`SessionWrite` `transform`; §2.10 A1), the write queue's next write, in slice 2's write order with a Lean job and a test between its third and fourth writes. While `idsCommit` is absent, slice 3's recorded ids write is queued just before it (§2.10 A24, §3.1), so it plans on written ids:
   1. *Write step 1:* run.json gets `inFlight` (`{ action: { kind: 'transform', window }, parent: head }`).
   2. *Write step 2:* the runner plans, on the head and the records as they are now (a replay plans again): the Results to take out (`redoHidden`: on the real, unmasked state, every Result whose current proof or statement relies on what the write changes, by §3.4's walk; while the results are shown it equals the analysis's `takeOut`, and while they are hidden it is never shown, D4-46); `planTransformWrite` in session mode, with the real itemDeps (`session.deps`, for `rejectOut`); the analysis's `unaccept` (its `cascade`, recomputed on the records now, Results included, never an item of `reject` or `rejectOut`); and the reducer's `transform` action, which checks it and gives the decision's records. The statuses come in this order (D4-62, recheck-03): `reject` with `rejectOut`, slice 2's Reject and DO-0 cascades (taken out and to be redone, an accepted one losing its Accept); `unaccept`; `redo`, but what `rejectOut` holds; the Claude part's sources declined `transform`, with a Shaky decline's cascade (their dependents in review, including the ones `unaccept` returned, become to be redone, not reverted; hidden Results silently, D2-64; §2.10 A12); the confirmed `unfreeze` (D3-48's, in the FreezeDelta); and the confirmed `drops` dropped. The reopened records follow: every record of an item that owns a key the write changes and is declined by Reject or plainly, withdrawn, or to be redone with its content taken out, but those the decision itself declines or takes out (`reject`, `rejectOut`, `redo`), back in review, "updated", its rejected versions kept (§2.2, §2.10 A22), so the judge-apply that follows never takes your carried-out content out again as slice 2's "back although declined": a Reject, then a transform of the same card, keeps what you typed in review, and so does the Redo of a transform whose items the Undo withdrew. Then come the ledger entries, with the values that `rejectOut` and `redo` drop, by item (`transformValues`, §2.2); the FreezeDelta with the own freezes still unvalued, `replaced` and `unfreeze`; the part queued; and the stack action. The files go into ws/.
   3. *Write step 3:* the shadow commit `decision`, labelled "Transform: ‹label›".
   4. **Its Lean job:** `engine.judge` on the head, with a build, and the freeze table as the decision leaves it without its own freezes, which this judgement values (so they are not compared in it; the reasons it replaced are gone). When build errors are attributed to the parts of Results hidden from the person, those Results are reverted to your files' version in a further commit of the same write and the state judged again, at most once per Result (slice 2 §3.6's loop, inside the write), and join `redo` silently. A shown Result that fails is a visible failure (the test below).
   5. **The take-back test** (`transformTakeBack`, D4-46): the failures of this judgement on visible content that the parent's judgement (the stage judgement, `judged`) did not have:
      - a build error, or a declaration without facts, outside the parts of hidden Results;
      - a typed piece with scratch `consts` whose constants in place differ from them, the scratch namespace's names mapped to the names written: "“‹c›”'s Lean elaborates differently where telelean wrote it than when you checked it: ‹names›." while the results are shown, the fixed sentence below while they are hidden (S4M-1; D4-23's comparison, made here once);
      - a typed declaration that is a proof in place (`isProof`; R2-11, for a piece the scratch could not elaborate);
      - `other-result` on a typed piece (slice 2's rule, D2-50): its constants in place include proof material or a target's `.holds`, which are hidden from the person while the results are hidden. This catches a piece that uses session names (no scratch `consts` to compare) and resolves, where it is written, to a hidden proof-phase declaration, instance or coercion;
      - a failed probe (D2-75: fail closed, as a premise write does);
      - a frozen, held or other-subject problem, or an `unowned` difference;
      - while the results are shown, a B.1 or B.2 failure of a Result the decision did not take out.

      A failure the parent already had never counts; a hidden Result's failure never counts (it was taken out silently by the Lean job, D2-64). A failure is matched with the parent's by its code, token, file and declaration name, a build error by the declaration whose range holds it, never by its position or its message text: a stage that did not pass may have build errors, and an error the write only moved down a line is still the parent's. While the results are hidden, every take-back problem that comes from Lean (a build error, a declaration without facts, the typed meaning, a typed proof in place, `other-result`) is one fixed sentence on its card and field, quoting no Lean message and naming no constant: "“‹c›”'s Lean does not build, or does not mean what you checked, where telelean writes it (Lean's details are withheld while the results are hidden)." (D4-46); a kept dependent that breaks keeps §3.4's own fixed text. If any counts, the write is taken back whole: ws/ returns to the parent (a `revert` commit), and one run.json write sets `head`, clears `inFlight` and sets the window's `takenBack` with the problems (each on its card and field where it has one); nothing else is recorded. The window stays open with them; TR-9's Cancel still closes it with no change.
   6. **Otherwise, write step 4:** one run.json write: the decision's records; its own freezes valued from this judgement (`valueOwnFreezes`: `{ from: 'state', commit, value, held }`, or `{ from: 'base' }` by slice 3's test; §3.11), with `madeAt`; the stack action (with its commits and `takenOut`); the window cleared; `head`; `judged` and `judged-facts.json` (written before run.json names them, as a premise write stores its judgement); `inFlight` cleared. It enqueues, next in the queue ahead of anything queued meanwhile, the `judge-apply` of this judgement, with no new Lean job: reconcile (the decision's items, wholly yours or mixed; its sources and the items it touched, "updated"; withdrawals `replaced-by-transform` and `changed-back`, D4-51) and the judge's own reverts, as after any decision (slice 2 §3.5–§3.6).
6. **The answer:** `{ ok: true, transform: { outcome, queued? } }` once that judge-apply is recorded; `{ ok: false, code: 'refused', transform: { takenBack } }` after a take-back.
- **A decision that writes no file** (a transform that only leaves fields to Claude, adds instructions or ticks the box, and changes nothing itself) is a records-only write through the same queue: no commit, no Lean job, no take-back; its one run.json write records the part, its sources' declines, any confirmed `unaccept`, the stack action and the window cleared.
- **What the decision does, in one recorded step:** writes your typed part; declines Claude's Adds you trashed and arrows you removed (Reject, DO-0), their slice-2 cascades first, which take out their dependents once (D4-62); unfreezes the frozen content they change that you agreed to (D3-48); drops the queued parts you agreed to (D4-43); takes out to be redone the Results that rely on what changes (D4-19); returns the confirmed accepted items to review (`frozen` cleared, slice 3's R2-4), and the declined, withdrawn or taken-out records of the items it writes (A22); makes your own freezes and replaces the reasons they override (§3.11); records the ledger `transform` entry; and, with a Claude part, queues it and declines its sources `transform` (by key, never a Result or a Result's part, with a Shaky decline's cascade; §2.10 A12).
- **The typed part builds on its own** (D4-48, D4-54): dependents are kept (and must build), emptied for Claude, marked broken or deleted; typed Lean uses only names that exist and nothing the window leaves to Claude; cleared fields are not written (D4-55). So a build error after the write is a real failure of your edit, shown on its card.
- **Hidden results** (D4-46). The take-back reads only visible failures, and the confirmation's trigger only the draft (`hiddenNotice`), so two states that differ only in a hidden Result give the same analysis and confirmation (twin tests, §6). While the results are hidden, a take-back problem from Lean is a fixed sentence with no Lean message and no constant named (step 5.5). One bit remains, logged with D2-69's channel: hidden declarations occupy names, and hidden instances, coercions and declarations that shadow a name you use take part in elaboration where your Lean is written. So a typed piece (a new name equal to a hidden proof-phase declaration's; a statement that such a declaration elaborates differently, which the typed-meaning comparison or `other-result` then finds) is taken back in one twin only, with the same fixed sentence.
- **Crash or reload** (D4-47). Slice 2's `inFlight`: `recover()` reverts ws/ to `head` (the parent) and, for a `transform` write, does not run it again: it clears `inFlight`, keeps the window record (which only step 4 clears) and sets its `takenBack` to `{ interrupted: true, problems: [] }`, which the window shows as "telelean was interrupted while carrying out your transform: nothing was changed. Submit it again." A crash during the ids write that precedes it (A24) is recovered by slice 3's rule for that write, and leaves the window as it was. Once step 4 is recorded the decision stands; a crash before its `judge-apply` is recovered as any judged state is (D2-72).
- **Undo** is the session step's (§5.1), until the next seal.

### 3.9 Claude's part (RV-12, TR-14, TR-15; D4-25, D4-35, D4-59, D4-60)
1. **Queued** by the decision (§3.8) or by the provisional claude-step (§3.1), as a scope (§2.2): the window's open, fuzzy and cleared keys (new cards' through the decision's ids), the emptied dependents' Lean with its old text, `arrowsInto` (Dependencies open, cleared with removal allowed, or fuzzy), slots, the tick, the instructions and the may-break proofs; never a key `claudeMayChange` refuses (D4-57). Its sources are declined `transform` while it is queued (D4-8). §2.2's `QueuedTransform.items` defines them once, by key: the `card:`, `vocab:` and `decl:` items that own content under its `open` keys, and Claude's arrow items into its `arrowsInto` cards. They are never a `proof:` item (a Result or a Proof broken item), and never a Result's part (an Add arrow, an Add premise, a proof-phase `decl:`). Those there when the decision is planned are declined by the decision itself; a decline window's items are among them only when they own content there. Every record that reconcile creates or updates under those keys while the part is queued is declined by reconcile, with an event (§2.10 A12). The decision's own new items under those keys are among the latter: the `judge-apply` that follows the decision creates them. A `transform` decline cascades as a Shaky decline does: the sources' dependents in review become to be redone, not reverted, hidden Results silently (D2-64), and slice 2's own rules rework them at Submit review. So nothing Claude's part may change can be accepted before the part runs (its step would then change accepted content), and nothing there blocks Submit review. A Result or a Result's part stays out of every decision and event the part makes, even on its cards (a session target whose sentence or Why you leave to Claude, D4-19). It stays decidable by slice 2's rules, and is reworked by them when it rests on a source (recheck-03).
2. **At Submit review.** Gates: slice 2's (nothing in review, the results shown, no step, not judging), plus no window open. For each queued part, the runner recomputes its scope (`transformScopeOf` on the current state, `claudeMayChange` without `acceptedReturn`, on `holdIndexOf` and `otherSubjectHoldsOf`): keys that no longer exist leave it, and a freeze or hold made since wins. Every key it loses is listed in the stage report, "Claude's part of “‹label›” left out ‹fields›: ‹reason›." (the reason: deleted since; frozen (‹reasons›); held by frozen ‹cards›; relied on by another subject), so no field you asked Claude to fill stays empty unreported. D4-39's may-break walk, and with it `dependents.proofs` and the turn's "results you must not break", are computed again on the current state, the results now shown (they were computed on the masked view when the part was queued). A part with nothing left is dropped, its sources returning to review, with a stage-report note "Claude's part of “‹label›” had nothing left to do: ‹reason›." `planSubmit` then orders the parts, the rework parts (step 7) and slice 2's Submit steps (§2.10 A10), with D2-57's take-out and D3-49's keep set (own freezes count as frozen, declined `transform` as Shaky). In a session whose conversation has not started (`claudeStarted` false: only a transform-started one, LC-10), the host asks the egress consent first; the runner opens the conversation, with the context bundle, before the first step (D4-27). Submit seals (UN-5) in its `queue-start` write, as slice 2's does.
3. **The step:** kind `transform`, target `transform:<id>`, S₀ the judged head (which already holds your typed part), StepScope with `transform` = the scope and `openItems` = its sources. It is computeItems' `active` step with `transform` (R2-3): its new declarations are statement-phase `vocab:` and `decl:` items with it as origin, never proof material, and it makes no Result draft. Every judgement of it takes the run's `subject` (§2.10 A21), and judgeState treats its scope as §2.9's 4d note says: no inference for `transform:<id>`, none of the active target's rules, its new declarations judged against the vocabulary layer. The turn (§2.8). Claude works with the tools of §2.8. Normalise (core `gate/normalise.ts`, IMP-5; the runner passes it the scope and the live entries) pins the statements of `open`, new cards' included (as slice 2 pins `fuzzyStatements`), writes the step's ledger arrows and `card` blocks (with their kind and slot), and writes `worded_by: agent` for a sentence Claude changed, compared with S₀. Gate attempts (`gate-other`: no target, no comparator; up to 3) judge every rule of slices 2 and 3 with the scope, from one baseline:
   - **step limits** against S₀: every declaration and block line keeps its text and meaning, except the `open` keys, `arrowsInto`'s arrows, `mark_proof_broken`'s removals, the cards `add_card` made, and new declarations: plain vocabulary (the shape rule), and, with `mayAddCards`, definitions, instances, coercions and presuppositions (items like any; without the tick `transform`, `new-definition`, D4-35); every item of S₀ outside `openItems` keeps its content key (slice 2's frozen-items rule, unchanged);
   - **frozen and held** (slice 3): your own freezes on the fields you typed hold their text and meaning ("frozen: you typed it"), so Claude's change of one, or putting your files' version back, fails;
   - **G5:** Claude changes no `type:`, `follows_from:`, `premises:` (telelean's ledger writes) or `worded_by` (normalise's, CF-6), the live `transform` entries' `lines` counting as telelean's; in a new block of yours, no line appears but Claude's fields of `open` keys and normalise's pins (S4M-3);
   - **B.3** with §2.8's arrows; **B.4**; **new-axiom** (D2-40 included; allowance 1 asks a `.holds` to be still bound to its card, so an axiom a trashed card bound counts as new); **`transform` (`no-proofs`, `new-definition`)**; **stray-command**; **`rejected-repeat`**, with DO-3's identical set per part in a rework part;
   - every inference is judged, and other inferences' findings never count against Claude (RV-11).
4. **`finish`** says `done` or `cannot`; `cannot` passes when the gate passes, and its gap is reported (A3). The state must build: whatever the part's changes break is fixed, marked broken (may-break proofs) or refused (TR-13: nothing is left broken).
5. **Not passing** (it fails, gives up, is cancelled or hits a cap): the step goes back to its `step-start`, with its own ledger entries dropped (slice 2). What you typed stays: it is before S₀ (D4-45). The part stays queued with `lastFailure`, its sources declined `transform`; the stage report and its row say "Claude's part of “‹label›” did not run: ‹reason›", with Retry step, and list each dependent the decision emptied for it that is still empty ("Claude did not re-formalise “‹c›”: it has no Lean statement now.", or "…: ‹name› has no declaration now." for vocabulary; D4-48), as they do when the part is dropped. **Retry step** recomputes its scope (step 2) and runs it again; it refuses a part no longer queued. A failure ends the queue as slice 2 says (the rest not run). You can also drop the part and accept or reject what you typed alone.
6. **Step end:** ledger `created` (phase `statements`) and slice 3's `changed` entries; the part leaves `queued` (its id stays in `SessionRecords.steps`); at the queue's end every source returns to review first, with or without a draft, "updated" when its key changed (slice 2's F5 rule, generalised), and then A4's withdrawal applies: a source left with no draft (a cleared field Claude rewrote to your files' version) is withdrawn, "changed back to your files' version", never slice 2's "disappeared" problem (§2.10 A4, A12). A cleared field Claude left as it was is listed in the stage report: "Claude did not rewrite ‹field› of “‹c›”, which you cleared: it keeps its old value." (D4-55). So is a dependent the decision emptied that Claude left empty, with `done` or `cannot`: "Claude did not re-formalise “‹c›”: it has no Lean statement now." (D4-48). Claude's parts write no AttemptRecord: their outcomes are in the stage reports (LC-19).
7. **Rework parts** (D4-60). At Submit review, each Shaky or to-be-redone item whose origin is a transform (`transform:<id>`: its decision or its Claude part) is reworked by a part telelean queues on its cards (`from: 'rework'`): its scope is what the item owns, less the keys `claudeMayChange` refuses (your typed fields stay frozen), with no slots and no tick; its instructions are the Shaky note or the redo reason; DO-3's identical-set check applies per Shaky set, and D2-15 holds (no splits or merges). Shaky is refused only when that rework part would have nothing to change: the runner, before the reducer runs (a Redo included), computes its scope (`transformScopeOf` with the item as a rework source, on the stage judgement's state, `holdIndexOf` and `otherSubjectHoldsOf`) and refuses when every key the item owns is refused by `claudeMayChange` (frozen by any reason, held, or relied on by another subject): "Every field of it is frozen (‹reasons›): unfreeze the fields Claude may redo, then decline it Shaky." Were an empty part to get through, step 2 drops it with its note. There is no separate rework step kind.

### 3.10 Items: yours and Claude's (RV-1, RV-4, RV-7, TR-15; D4-49–D4-51)
- **Ownership is slice 3's, card-granular, unchanged** (D4-49): `card:<c>` owns c's fields (sentence, Why, stance, source, kind, the Lean statement with its mirror, pin and an AXIOM's `.holds`, the `premises:` entries and mark the person wrote), its Delete also c's arrows out; `proof:<c>` a Result or a Proof broken item (a proof you cleared is a `proof:<c>` Proof broken item labelled "Clear proof ‹card›", and one the decision marked broken for you, D4-48, is labelled "Proof broken ‹card›" as slice 3's are); `decl:` and `vocab:` vocabulary; `arrow:` Claude's arrows. That `item` is its card's own item, but for the `premises:` entries a trash removed from other blocks, which belong to the trashed card's Delete (§2.2). A Claude part is the `active` step while it runs, and its `created` and `changed` entries resolve through `transformSteps` (R2-3). - **Wholly yours** (D4-49, D4-50): `whollyYours` reads an item's draft against B and the live ledger: every difference is either a field whose `fieldText` in the state equals the newest live ledger value for that card and field whose `item` is this item, or a block line or `premises:` entry in the live `lines` of this item (a `proof:` item counts by its card's Proof field, its proof material going with its `.holds` as `proofMaterialOf` says; a `decl:` or `vocab:` item by its declaration and gloss; a Delete by its card's fields, all absent, and the lines its trash removed); a derived `id:` line equal to the card's derived id (the session's ids commit, D3-37) and a `lean:` pin equal to the one normalise writes for the card's binding are ignored. - **Classes** (§2.10 A8): a wholly-yours item takes a plain Accept, which a group Accept takes, whatever its RV-7 class; one with a declaration in the entry's `unconfirmed` (session names, D4-32) is marked `typed-unconfirmed`, shows its Lean in fully explicit form, and takes its own Accept. A mixed item is classified as today. Losing "wholly yours" (Claude changed it after your Unfreeze) counts as its badges growing: an accepted item returns to review (D2-23). Nothing is ever accepted for you (D4-49).
- **Reveal:** your typed statement items are statement items like any: while in review, they keep the stage's results hidden (AP-24).
- **RV-5** edges as for any item: a typed statement that uses Claude's vocabulary in review depends on it.

## 5. Undo and persistence

### 5.1 The session stack (UN-4, UN-5)
- **A transform decision** is one step, "Transform: ‹label›", recording its item changes with their revs (the records it reopened included, §2.10 A22), the written premises its cascade took out, its FreezeDelta (own freezes, `standingCleared`, `startCleared`, `replaced`, and a confirmed `unfreeze`), its ledger entries, the values that `rejectOut` and `redo` dropped (`transformValues`, by item), its queued Claude part, the parts it dropped (`drops`, D4-43), the force it ended or started, and its commits (LC-13, IMP-7). **Undo** (D2-73) goes through the reducer's checks: it merges its commits' inverse patches onto the head (`mergeFile`), newest first, refused on a conflict ("This transform can't be undone any more: ‹file›."); restores the statuses (RV-5's list, as for any Undo; the records it reopened go back to their decline, with no draft once the merge has run), the freezes, the ledger (its entries removed, and the values its take-outs dropped put back), the parts it dropped and the force; removes its Claude part, refused once that part's step ran (a seal stops Undo anyway); then the judge runs as after any decision. A Result the judge took out after the decision (hidden, silently) stays to be redone, and Submit review reworks it. While the results are hidden, the Undo's answer depends only on visible items (slice 2's fixer-2a rule 3): a hidden Result whose part of the merge conflicts is left to be redone, silently, never a reason to refuse. **Redo** carries the recorded window out again as a new decision write (§3.8 steps 2–5) on the current state, with its stored scratch (B never moves): a problem refuses the Redo with its text, and a take-back refuses it with the problems. Its new cards take back the ids its action's ledger `transform` entry recorded (`ids`), which the Redo passes to `planTransformWrite` as `session.reuseIds`, when no card holds them, before any reserved test (§3.5 step 1). So freezes, moves and references made on them survive Undo and Redo (D5-20's rule for premises; slice 5's registry keeps those ids from every other card). Its reducer action reopens the records the Undo left withdrawn or declined (A22), so its items are in review and its own freezes are met, never taken out again by slice 2's "back although declined".
- **`drop-transform`** is one step; its Undo puts the part back, with its sources' declines (refused when a source's content left ws/, D4-43); its Redo drops it again.
- **`edit-premise`** is one step; its Undo restores the earlier draft and the item's state.
- A decision that dropped parts with D4-43's confirmation records them (`drops`), and one whose Rejects or take-outs dropped ledger values records them (`transformValues`); its Undo restores both with its other effects. An un-reject records the values it restored (`transformValuesRestored`, A23), which its Undo drops again.
- Opening, saving and cancelling a window are not steps. The window's freeze actions are slice 3's freeze steps, whose FreezeDelta records `startCleared` and `replaced` (an Unfreeze's Undo restores them, LC-2, IMP-6). The window's draft edits have their own timeline, never a session step (D4-41, §4.5). Text fields keep their own undo (UN-4 4b).
- Submit review with Claude's parts seals, as with any Claude step (UN-5); a provisional session's stack is discarded with it (UN-6), and the provisional claude-step's queue-start seals its decision.

### 5.2 The board stack (UN-2)
- `apply-transform` is one board step: Undo restores the files, the freezes.json delta and layout.json, as for any plan; History keeps its snapshot (AR-7: a replaced proof stays in History).

### 5.3 run.json, webview state, reload (ES-6)
- run.json v2 gains, additively: `PersistedSession.transform` (§2.2: the window, the queued parts, `nextId`), `claudeStarted`, `starting`, `PersistedStep.kind` `transform` (with `transform` and `rework?`), the ledger `transform` entry and the `card` entry's `transform`, `slot` and `kind`, `PremiseDraft.editedBy` and `wordedBy`, `OwnFreeze.transform`, `SessionFreezes.start.transform`, `startCleared` and `replaced`, and `SessionWrite` `transform` in `inFlight`. `recover()` reads absent fields as empty, but an absent `claudeStarted` as true (a session from before slice 4 started its conversation; LC-10, IMP-19); no migration.
- **An interrupted decision write** (D4-47): `recover()` reverts ws/ to `head`, clears `inFlight`, keeps the window record and marks it interrupted (§3.8). **A provisional claude-step between its decision and its queue-start** (`starting`): `recover()` applies any judgement that is due, then makes the `queue-start` write, then waits for Resume. **An interrupted Claude part's step:** slice 2's Resume (`--resume` and the resume turn), or Cancel step, which takes the part back to its start (your typed part stays). A part whose first turn was never sent is started, not resumed; no Resume needs a conversation for a step that has none.
- The webview autosaves the draft 400 ms after the last edit, one save in flight, coalesced, and at once on Cancel and `visibilitychange`; a Submit waits for the save in flight, then sends with its rev (UI-9). It keeps a crash copy in its state (`updateState({ transformDraft: { runId, window, rev, draft } })`, debounced 150 ms). When `session` arrives, a window the store lacks opens with the host's draft, or with the crash copy when it has the same runId and window and a rev ≥ the host's (then saved again); a window the host closed closes. The window's draft-edit timeline is not kept across a reload (D4-41).

### 5.4 Reversal hazard
Reversing slice 4 while a session holds a window, a queued Claude part, a `transform` ledger entry or own freezes a decision made leaves run.json fields the older code refuses: finish or Exit such sessions first. Reversing AP-31 (back to `slice4-plan.after_ultra.md`) after sessions were made with this design needs the same: its typed units and transform freezes cannot be derived from a `transform` entry. The AP entry says so.
